### 2.1 검색 문장(B-01) 전후 — 2026-10-16

> 이 절의 수치는 위 표(10-03)와 직접 비교하지 않습니다. 같은 노트북이지만 DB 컨테이너 메모리 상한(1.5GB, compose 기본)과 커진 데이터(분류·사용자·IP 를 채워 7.4GB) 때문에 본문을 읽는 조회와 첫 실행이 느리게 나옵니다. 전후 비교는 이 절 안에서만 합니다.

|---|---|---|

  - 문장 쪽은 옛 짝 뒤에 돌아 캐시에 유리했습니다.
  - '후' 측정 중에는 점검 보고서 정기 실행이 '7일 원본 필드'와 겹쳤습니다. 지금은 벤치가 끕니다(`WLM_REPORT_SCHEDULER=off`).
- **결론:** 같은 뜻의 검색은 느려지지 않았습니다. 구조(같은 SQL)로 보장되고 실측도 같습니다.

**새 기능 (후, ms)**

| 시나리오 | 문장 | 첫 | 반복 | 결과 |
|---|---|---:|---:|---:|
| 7일 · 백로그 예문 | `event_id:4625 ip:10.1.2.3 -user:user7 level:경고 "잘못된 암호"` | 5 | 2 | 1건 |
| 30일 · IP | `ip:10.1.2.3` | 5 | 2 | 13건 |
| 24시간 목록 · PC 제외 | `-host:PC-0042` | 7 | 3 | 100건 |
| 7일 건수 · 수준 제외 | `-level:정보,상세` | 641 | 79 | 14.8만 |
| ↳ 같은 결과의 포함 조건 | 옛 파라미터 `level=1,2,3` (`level:심각,오류,경고` 와 같은 SQL) | 12 | 12 | 14.8만 |
| 7일 건수 · 계정 제외 (값 없는 행 유지) | `-user:user1` | 2,419 | 849 | 116만 |
| 7일 · 메시지 단어 AND | `계정 user1234` | 332 | 32 | 100건 |
| 24시간 · 구절 제외 | `-"로그오프"` | 4 | 3 | 100건 |
| 7일 · 원본 필드 제외 | `event_id:4625 -f.StringInserts.5:user77` | 23 | 4 | 100건 |
| 30일 건수 · PC 제외 (최악) | `-host:PC-0001` | 1,239 | 240 | 497만 |
| 30일 · 짧은 단어 AND | `다시 부팅` (따옴표 없음) | 22,243 | 22,830 | 100건 |
| 실시간 매처 (백로그 예문) | | | | 이벤트당 1.3µs |

- **포함 조건이 있으면 제외는 거의 공짜입니다.** 색인으로 줄인 뒤 거릅니다.
- **제외만 있으면 색인을 쓰지 못합니다.**
  - `-host:PC-0001` 30일 건수는 전체 건수(199ms)와 비슷합니다. (host, ts) 색인 전용 스캔에서 거릅니다.
  - `-user:user1` 은 사용자 색인을 쓰지 못해 7일 본문을 병렬로 읽습니다(EXPLAIN: Parallel Seq Scan, 1.1초).
  - `-level:정보,상세` 는 같은 결과의 포함 조건보다 6배 느립니다.
  - 화면 린트가 '제외 조건만으로 긴 기간'을 안내합니다.
- **짧은 단어:** 따옴표 없는 `다시 부팅` 은 `다시` AND `부팅` 입니다.
  - 2글자 단어는 trigram 을 만들지 못해 GIN 색인이 전체를 훑습니다. 그런데 플래너는 결과를 15건으로 잘못 추정해 이 길을 고릅니다.
  - EXPLAIN 결과, 색인이 행 150만 개를 내고 손실 비트맵으로 본문 전체를 다시 확인했습니다. 30일에 28.8초, 버퍼 68만 개를 읽었습니다.
  - 같은 말을 따옴표로 묶으면(`"다시 부팅"`) 0.56초, 버퍼 5천 개입니다.
  - 옛 `q=부팅` 처럼 2글자 단어 하나도 같은 SQL 이라 B-01 전부터 있던 한계입니다. 문장에서는 띄어 쓴 단어가 AND 가 되어 더 자주 만납니다.
  - 결과가 드문 짧은 단어는 기간이 짧아도 느립니다. 발생 시각 색인을 거꾸로 훑으며 행마다 본문을 확인하기 때문입니다. 캐시가 빈 상태에서 1일 범위 10초대, 결과가 없는 7일 범위는 1분 넘게 걸렸습니다.
  - 대응: 화면 린트('2글자 이하 단어는 … 따옴표로 묶어 보세요', '구절로 합치기' 빠른 고침)와 검색 시간 상한(§2.2)을 둡니다.
  - 2글자 색인(pg_bigm 등)은 DB 이미지를 바꿔야 해서 보류합니다.
- **실시간 매처:** 이벤트당 1.3µs 입니다. 초당 1만 건을 수집해도 CPU 1.3% 입니다.

### 2.2 검색 시간 상한 (ADR-035)

- 화면 검색·통계·대시보드·수집 PC·규칙 미리보기의 쿼리는 `WLM_SEARCH_TIMEOUT_SEC`(기본 30초)를 넘으면 DB 가 멈추고, 화면에 그 화면에서 할 수 있는 방법이 나옵니다(503).
- 이런 조회는 한꺼번에 **연결 6개**까지만 씁니다(`db.SEARCH_SLOTS`). 풀 10개 중 4개는 수집·알림 엔진·상태 확인 몫으로 늘 남습니다. 자리를 기다리는 시간에도 같은 상한이 걸립니다.
- **왜 필요한가:**
  - 위 짧은 단어 검색처럼 끝나지 않는 쿼리는 브라우저를 닫아도 DB 에서 끝까지 돕니다. 실측으로 끊긴 쿼리가 3분 넘게 남았습니다.
  - 연결 풀(10개)은 수집과 함께 씁니다. 상한만 있고 자리 제한이 없을 때, 느린 문장 20개가 몰리면 수집이 풀 대기 30초 뒤 실패(500)했습니다(검토에서 재현). 에이전트는 다시 보내지만 그동안 수집이 밀립니다.
- **영향:** 쿼리마다 `set_config` 왕복이 한 번 늘어납니다(0.1ms 안팎). 위 표의 시나리오는 모두 상한 안에 들어옵니다(가장 느린 '30일 · 짧은 단어 AND' 23초 — 캐시가 비면 넘을 수 있음).
- **규모가 크면:** 하루 수백만 건(§5 의 두 번째 줄)부터는 30일 집계(수집 PC 30일, 원본 필드 값 분포 7일 이상)가 30초를 넘어 503 이 될 수 있습니다. 상한을 올리거나(`.env`, 0 = 없음) 시간별 집계 테이블(BACKLOG B-09)로 대응합니다. 상한이 없어도 그 화면은 수 분씩 걸려 쓰기 어렵고 수집 연결을 잡습니다.
- 벤치(`tools/bench/bench.py`)는 실제 시간을 재려고 상한을 끕니다.
- 쓰기(PC 삭제)·알림 엔진·점검 보고서·수집·로그 보관에는 상한을 걸지 않습니다.

### 2.3 TLS 핸드셰이크 (B-06, ADR-036) — 2026-10-16

Windows 에이전트는 `net.keepalive: off` 라 보낼 때마다 새로 연결합니다. 그래서 '연결마다 새 핸드셰이크 + 하트비트 POST' 를
초당 50/100/200회, 30초씩 보내 평문(6976)과 TLS(6977, ECDSA P-256)를 비교했습니다. 같은 시간에 화면 `/healthz` 를 0.5초마다 쟀습니다.

| 초당 새 연결 | 평문 p50 / p95 | TLS p50 / p95 | 오류 | 화면 `/healthz` p95 (평문 / TLS 부하 중) | api CPU (한 번 표본) |
|---:|---:|---:|---:|---:|---:|
| 50 | 13 / 19ms | 19 / 23ms | 0 | 16 / 20ms | 8% / 16% |
| 100 | 19 / 25ms | 20 / 27ms | 0 | 21 / 18ms | 15% / 17% |
| 200 | 14 / 25ms | 17 / 27ms | 0 | 21 / 18ms | 25% / 18% |

- 초당 200회는 PC 1,000대가 5초마다 새로 연결해 보내는 양입니다. 한 프로세스(ADR-006)로 오류 없이 받았고 화면도 느려지지 않았습니다.
- CPU 는 `docker stats` 를 한 번만 찍은 값이라 흔들립니다(200 에서 평문이 더 높게 나옴). 수천 대 규모는 실서버에서 잽니다(BACKLOG B-25).
- Linux 에이전트(keep-alive 사용)는 연결을 재사용합니다. 서버 keep-alive 는 75초(`WLM_INGEST_KEEPALIVE_SEC`)로 Fluent Bit 의 유휴 연결(30초)보다 길어, 실측 중 재사용 연결이 끊기는 오류(`broken connection`)는 없었습니다.

## 3. 해석

- **로그 검색(목록·조건·메시지 부분일치):**
  - 반복 조회는 대부분 **0.1초 이내**이고, 캐시에 없는 첫 조회도 1초 안팎입니다.
  - 기간보다 '조건에 맞는 행이 얼마나 드문가'가 속도를 좌우합니다. 드문 이벤트일수록 인덱스로 바로 찾습니다.
  - 메시지 검색은 trigram 인덱스(pg_trgm)가 받쳐 줍니다.
- **원본 필드 검색(`f.경로`):**
  - 인덱스가 없어서 기간 안의 행을 직접 확인합니다. 7일(약 120만 건)에 0.3초(튜닝 후)입니다.
  - 30일이면 1~2초를 예상합니다.
  - 자주 쓰는 필드가 생기면 컬럼으로 올리거나 식 인덱스를 추가합니다(§5).
- **집계(건수·시계열·상위값):**
  - 행 수에 비례합니다. 초당 약 300만 행을 처리합니다.
  - 대시보드 기본(24시간)은 0.1초 안팎입니다.
  - 30일 시계열은 500만 행에 1.5초입니다. 이 규모에서는 감당할 만하지만, 수천만 행부터는 느려집니다(§5).
- **대시보드 부하:**
  - 실시간 갱신은 DB 를 다시 조회하지 않습니다(SSE, ADR-010).
  - 전체 동기화는 60초마다 위젯 수만큼만 실행됩니다.

### 시도했다가 채택하지 않은 것 (ADR-017)

- **방법:** 발생 시각 조건에 `received_at >= since - 1일` 을 함께 붙여 파티션을 가지치기했습니다.
- **결과(②):**

| 시나리오 | ① 반복 | ② 반복 |
|---|---:|---:|
| 7일 시계열 | 586 | 11,349 |
| 30일 건수 | 406 | 4,801 |
| 7일 건수 · 오류 | 13 | 1,531 |

- **원인:** 조건 하나가 늘면서 인덱스만 읽던 조회가 테이블 본문까지 읽게 바뀌었습니다.
- 로그 로테이션으로 DB 파티션이 3~4개로 유지되어, 가지치기로 얻을 이득도 작습니다.
- 그래서 되돌렸습니다.

| 설정 | 4GB (기본) | 8GB | 설명 |
|---|---|---|---|
| `WLM_PG_SHARED_BUFFERS` | 512MB | 1GB | DB 캐시. 기동 때 잡고 돌려주지 않음 → '메모리가 안 줄어드는' 것처럼 보이는 게 정상 |
| `WLM_PG_EFFECTIVE_CACHE_SIZE` | 1536MB | 3GB | 실제로 잡는 메모리 아님(실행 계획 추정치) |
| `WLM_PG_WORK_MEM` | 16MB | 32MB | 정렬·집계 1단계당. 병렬 작업자 × 동시 조회만큼 곱해짐 |
| `WLM_PG_MAINTENANCE_WORK_MEM` | 128MB | 256MB | 인덱스 생성·VACUUM |
| `WLM_PG_PARALLEL_WORKERS` | 2 | 4 | CPU 코어 수의 절반 |
| `WLM_PG_MAX_CONNECTIONS` | 40 | 40 | api 풀 최대 10 + 관리 여유 |
| `WLM_PG_SHM_SIZE` | 512m | 1g | 병렬 조회용 공유 메모리 (Docker 기본 64MB 는 부족) |
| `WLM_DB_MEM_LIMIT` | 1536m | 3g | db 컨테이너 상한. 넘으면 페이지 캐시부터 비움 |
| `WLM_API_MEM_LIMIT` | 768m | 1g | api 컨테이너 상한. 넘으면 api 만 재시작(에이전트가 재전송하므로 유실 없음) |
| `MALLOC_ARENA_MAX` | 2 | 2 | 고정. Python(glibc) 이 해제한 메모리를 OS 에 돌려주게 함 |
| `random_page_cost` / `jit` | 1.1 / off | 같음 | SSD 기준, 짧은 조회 위주 |

**메모리를 볼 때 주의:** `docker stats` 의 MEM USAGE 는 파일 캐시(페이지 캐시)를 포함합니다.
캐시는 필요하면 커널이 바로 비우는 메모리라 '새는' 것이 아닙니다. 실제 사용량은 `free -m` 의 `available` 로 판단합니다.
Windows + Docker Desktop(WSL2) 에서 돌리면 `vmmem` 이 캐시를 잘 돌려주지 않으므로 `%UserProfile%\.wslconfig` 에 상한을 둡니다:

```ini
[wsl2]
memory=3GB
[experimental]
autoMemoryReclaim=gradual
```

## 5. 용량 가이드

**하루 건수 = PC 수 × PC당 하루 이벤트.** 보안 감사 정책에 따라 크게 달라지므로, 도입 후 '수집 PC' 화면의 실제 수치로 다시 계산합니다.

| 규모 예 | 하루 | DB 90일 (행당 약 1.4KB) | 보관 파일 1년 (행당 약 80~250B) | 판단 |
|---|---:|---:|---:|---|
| PC 50대 × 5천 | 25만 | 2,250만 건 · 약 32GB | 약 1~3GB | 현재 구조로 충분 |
| PC 200대 × 1만 | 200만 | 1.8억 건 · 약 250GB | 약 6~18GB | 30일 집계 화면이 수 초로 느려짐 → 집계 테이블 도입 |
| PC 1,000대 × 2만 | 2,000만 | 18억 건 · 약 2.5TB | 약 60~180GB | 검색 엔진 추가 검토 (ADR-004: ClickHouse / OpenSearch) |

- 보관 파일 압축률은 벤치 데이터(반복 문구)에서 13배(80B/건)입니다. 실제 Windows 메시지는 다양하므로 5~8배(150~250B/건)로 잡습니다.
- **다음 단계 (필요해지면):**
  1. **시간별 집계 테이블:** 수집할 때 (시각, PC, 채널, 이벤트 ID, 수준)별 건수를 함께 쌓습니다.
     - 건수·시계열·상위값을 기간과 무관하게 수십 ms 로 만듭니다.
     - 원본을 보관 파일로 옮긴 뒤에도 1년 추세를 볼 수 있습니다.
  2. **원본 필드 인덱스:** 자주 검색하는 경로에 식 인덱스를 추가합니다(예: `((raw #>> '{StringInserts,5}'))`). 수집 속도가 조금 줄어듭니다.
  3. **검색 엔진:** ADR-004 의 전환 신호에 해당하면 `repository.py` 만 교체합니다.
