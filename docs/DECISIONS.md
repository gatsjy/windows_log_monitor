## ADR-001 수집 에이전트: Fluent Bit
- **상태:** 채택 (2026-10-03)
- **결정:** 모든 OS의 에이전트와 syslog 수신기에 Fluent Bit(Apache 2.0)를 씁니다.
- **이유:**
  - Windows 이벤트 로그(`winevtlog`), journald, 파일 tail, syslog 수신을 하나의 도구로 처리합니다.
  - 서버 장애 시 디스크 버퍼와 재시도를 기본으로 지원하고, 가볍습니다(C, 수 MB).
- **대안:**
  - Winlogbeat는 Elastic 라이선스 혼재 문제가 있습니다.
  - NXLog CE는 독자 라이선스입니다.
  - Vector는 Windows 이벤트 로그 지원이 약합니다.
  - OpenTelemetry Collector는 무겁습니다.

## ADR-002 저장소: PostgreSQL + JSONB 원본 보존
- **상태:** 채택
- **결정:** 공통 컬럼과 `raw JSONB` 를 함께 저장합니다.
- **이유:**
  - 유지보수 인력이 익숙한 SQL을 그대로 씁니다.
  - 백업 도구(`pg_dump`)가 표준이고, 트랜잭션·권한 관리가 성숙했습니다.
  - 원본을 보존하므로 정규화 규칙이 바뀌어도 다시 해석할 수 있습니다.

## ADR-003 파티션 키는 `received_at`
- **상태:** 채택
- **결정:** `events` 는 서버 수신 시각 기준 월별 RANGE 파티션으로 나눕니다. 시간 검색은 `ts` 인덱스로 합니다.
- **이유:**
  - 발생 시각(`ts`)은 PC 시계 오차, 과거 로그 일괄 전송 등으로 범위를 예측할 수 없습니다.
  - 그러면 DEFAULT 파티션 관리가 복잡해집니다.
  - 수신 시각은 항상 '지금' 근처라서 파티션을 미리 만들기 쉽습니다.
  - 보관기간 만료를 파티션 DROP 한 번으로 처리할 수 있습니다(빠르고 감사 기록이 명확).
- **대가:**
  - `ts` 조건 검색에서 파티션 프루닝이 안 되고, 월별 인덱스를 모두 탐색합니다.
  - 보관 1년이면 13개 파티션이라 허용할 만합니다.

## ADR-004 대용량 검색: 지금은 PostgreSQL, 필요할 때 검색 엔진 추가
- **상태:** 채택
- **결정:**
  - Elasticsearch/OpenSearch를 처음부터 도입하지 않습니다.
  - 이벤트 SQL을 `repository.py` 한 곳에 모아 두어 백엔드를 교체할 수 있게 합니다.
- **전환 신호 (하나라도 해당하면 검토):**
  - 지속 수집량이 초당 수천 건을 넘습니다.
  - 보관 데이터가 수십억 건 규모입니다.
  - 수개월 범위의 자유 텍스트 검색이 자주 필요하고, 응답이 수 초 이상 걸립니다.
- **후보:**
  - **ClickHouse** (Apache 2.0): SQL 그대로, 압축률 높음, 집계 빠름. 유지보수 관점 1순위입니다.
  - **OpenSearch** (Apache 2.0): 자유 텍스트 검색이 핵심일 때. JVM 메모리와 샤드 관리 부담이 있습니다.
  - Elasticsearch는 2024년부터 AGPL 선택지가 있지만, 같은 기능의 OpenSearch(Apache 2.0)가 라이선스 측면에서 단순합니다.
- **방식:** PostgreSQL은 메타데이터(agents, audit_log, 알림 이력)와 최근 데이터를 맡고, 검색 엔진은 대량 이벤트를 맡습니다.

## ADR-005 UI: 빌드 없는 순수 JS, 차트 직접 구현
- **상태:** 채택
- **결정:** 프레임워크, npm, CDN 없이 ES 모듈과 직접 만든 SVG 차트를 씁니다.
- **이유:**
  - 파일을 고치고 새로고침하면 바로 반영되어 수정이 쉽습니다.
  - 폐쇄망에서도 동작하고, 공급망(npm) 보안 점검 대상이 없습니다.
  - 차트 종류가 적어서(누적 막대, 가로 막대, 스파크라인) 직접 구현하는 비용이 낮습니다.
- **재검토 조건:** 화면 수가 크게 늘어 상태 관리가 복잡해지면 경량 라이브러리(Preact, MIT)를 검토합니다.

## ADR-006 실시간 스트림: 프로세스 내 브로드캐스트 (SSE)
- **상태:** 채택

## ADR-007 대시보드 정의: JSON 파일
- **상태:** 채택
- **결정:** `config/dashboards/*.json` 파일로 관리합니다. UI 편집기로 저장하면 파일이 바뀌고 `audit_log` 에 해시와 함께 기록됩니다.
- **이유:**
  - git으로 이력과 리뷰를 관리할 수 있습니다(변경관리 증적).
  - 사람과 AI 모두 편집기로 직접 고칠 수 있습니다.
- **보완 (2026-11-02, B-07 1단계 검토):** 검색 화면의 위젯 추가는 서버가 파일을 읽어 덧붙이고, 화면 편집기는 연 판본의 `ETag`(파일 sha256)를 `If-Match` 로
  돌려줘 그 사이 바뀌었으면 409 — 옛 JSON 저장이 다른 사람이 더한 위젯을 지웠다. NUL·짝 없는 서로게이트는 저장 전에 422(파일은 써지고 감사로그 jsonb 만
  실패해 기록 없는 변경이 됐다), 위젯 추가의 감사로그는 잘라서·조건은 해시로(지울 수 없는 줄). If-Match 는 압축 프록시가 바꾼 꼴(W/"…"·"…-gzip")·`*` 도 받는다
  (값이 파일 sha256 이라 바뀐 꼴도 지금 판본에서만 나온다). 드릴다운은 **누른 값의 키만** 변수 대신 — 위젯 자신의 조건에 같은 키가 있다고 변수를 빼면 검색이 위젯보다 넓었다.

## ADR-008 보안 로그 '감사 실패'를 경고로 승격
- **상태:** 채택
- **결정:** Keywords에 감사 실패 비트(0x10000000000000)가 있고 Level이 정보 이하이면 `level=3` 으로 저장합니다.
- **이유:**
  - Windows 보안 로그는 거의 모두 Level 0(정보)이라, 로그온 실패(4625) 같은 중요 이벤트가 정보 속에 묻힙니다.
  - 원래 값은 `raw.Level` 에 남아 있습니다.

## ADR-010 대시보드 실시간 갱신: SSE 증분 반영 + 주기적 전체 동기화
- **상태:** 채택 (2026-10-03)
- **결정:**
  - 대시보드가 `/api/live` 를 구독합니다. 새 이벤트를 1초 단위로 모아 위젯별 `live()` 로 제자리 갱신합니다.
  - 정확도는 `refresh_sec`(기본 60초)마다 하는 전체 재조회로 맞춥니다.
- **이유:**
  - 몇 초마다 폴링하면 위젯 수 × 접속자 수만큼 24시간 집계 쿼리가 반복되고, 그래도 몇 초씩 늦습니다.
  - SSE는 이미 실시간 화면에서 쓰고 있어서 추가 인프라가 없고, 깜빡임 없이 즉시 반영됩니다.
- **대가:** 브라우저가 모든 이벤트를 받습니다.
  - 초당 수천 건 규모가 되면 서버가 위젯 조건별로 집계한 값만 보내는 방식으로 바꿉니다(`/api/live` 에 집계 모드 추가).

## ADR-011 알림 엔진: 앱 내장, 규칙은 YAML 파일
- **상태:** 채택 (2026-10-03)
- **결정:**
  - 별도 서비스 없이 api 프로세스 안의 백그라운드 작업으로 30초마다 평가합니다.
  - 규칙과 알림 대상은 `config/alerts.yaml` 에 두고, 바뀌면 자동으로 다시 읽습니다.
  - 여러 인스턴스는 PostgreSQL advisory lock 으로 한 곳에서만 평가합니다.
- **집계 기준은 `received_at`** 입니다. `ts` 로 세면 장애 후 몰아서 들어온 오류를 놓치기 때문입니다.
- **중복 방지:**
  - (규칙, 대상) 별 `cooldown` 을 두고, `cooldown` 은 `window` 이상으로 강제합니다(같은 이벤트로 반복 알림 방지).
  - Oracle 은 ALERT_ID PK 로 재시도 시 중복 INSERT 를 막습니다.
- **재시도:** 실패하면 1분, 5분, 15분, 1시간 간격으로 다시 보내고, 5회 실패하면 `gave_up` 입니다. 이력은 `alert_deliveries` 에 남습니다.
- **대안:**
  - Grafana Alerting / Alertmanager: 메트릭 중심이고 별도 구성요소라 운영 부담이 늘어납니다.
  - ElastAlert2: Elasticsearch 가 필요합니다.

## ADR-012 비밀값은 환경변수로만
- **상태:** 채택 (2026-10-03)

- **이유:**

  - ISMS 2.7(암호화)과 2.5(인증정보 관리)에 대응합니다.

## ADR-013 인증: 자체 구현 서버 세션 (외부 IdP 없이)
- **상태:** 채택 (2026-10-03)
- **결정:**
  - 아이디/비밀번호와 서버 세션(DB)을 씁니다. 비밀번호는 scrypt(표준 라이브러리)로 해시하고, 세션은 HttpOnly·SameSite=Strict 쿠키입니다.
  - 역할은 관리자/조회자 2개입니다.
- **이유:**
  - 외부 의존성 없이 ISMS 통제(잠금, 세션 타임아웃, 비밀번호 정책, 접속기록)를 코드로 바로 보여 줄 수 있습니다.
  - 서버 세션이라 계정 비활성화나 비밀번호 초기화 즉시 강제 로그아웃이 됩니다(JWT 보다 단순).
- **유휴 판정:** 브라우저가 보내는 '마지막 조작 후 경과 초'로 판단합니다. 자동 새로고침이 세션을 연장하지 않게 하기 위해서입니다.
- **확장:** 사내 SSO(LDAP/AD, SAML/OIDC)가 필요하면 `auth/service.login` 앞단에 인증 공급자를 추가합니다.
  - 오픈소스 후보: Keycloak(Apache 2.0)
  - 세션·권한·감사 부분은 그대로 씁니다.

## ADR-014 알림 대상은 DB(환경설정 화면), 규칙은 YAML
- **상태:** 채택 (2026-10-03). ADR-011 의 '알림 대상도 YAML' 부분을 대체합니다.
- **결정:**
  - 수신자·수신 그룹·외부 연동(웹훅/Oracle)·메일 서버는 화면에서 관리합니다(DB).
  - 규칙은 계속 `config/alerts.yaml` 이고, `notify` 에 그룹·연동 이름을 씁니다.
- **이유:**
  - 받는 사람 목록은 운영자가 자주 바꾸고 화면이 편합니다.
  - 규칙은 리뷰·이력 관리가 중요해서 파일(git)이 낫습니다.
- **보완:**
  - 규칙 저장 시 없는 이름은 거부합니다.
  - 규칙에서 쓰는 그룹·연동은 삭제나 이름 변경을 막습니다.
  - 그룹·연동마다 '받을 최소 수준'을 둡니다.

## ADR-015 Oracle 접속: python-oracledb thin, 4가지 접속 방식, 조회는 읽기 전용
- **상태:** 채택 (2026-10-03)
- **결정:**
  - Oracle Client 설치 없이 thin 모드를 씁니다.
  - 접속 방식은 TNS 이름(tnsnames.ora 를 화면에서 편집), SID, 서비스 이름, 접속 문자열 4가지입니다.
  - 조회 쿼리 실행기는 SELECT/WITH 한 문장만 허용하고, `SET TRANSACTION READ ONLY` 로 실행하며 최대 500행입니다. 모든 실행은 감사로그에 남깁니다.
- **이유:**
  - 사내 DBA 가 주는 정보 형태(TNS 별칭 또는 SID)가 제각각이라 모두 받습니다.
  - 관리자가 연동 결과를 바로 확인할 수 있어야 하지만, 운영 DB 변경 위험은 없어야 합니다.

## ADR-016 로그 로테이션: DB(검색) → 압축 보관 파일(SHA-256) → 삭제
- **상태:** 채택 (2026-10-03)
- **결정:**
  - DB 보관기간(기본 90일)이 지난 월 파티션은 `jsonl.gz` 로 내보낸 뒤 DROP 합니다.
  - 해시는 메타 파일과 감사로그 양쪽에 남깁니다.
  - 전체 보관기간(기본 365일)이 지나면 파일도 지웁니다.
  - 필요하면 파일을 같은 파티션으로 복원하고, 일정 기간 자동 정리에서 제외합니다.
  - → **ADR-040 로 보완:** 보관 파일 형식 v2(공통 필드 포함, v1 은 복원 때 다시 구함), 기록 종류별 보관기간.
- **이유:**
  - 1년치를 모두 DB 에 두면 저장 공간, 백업 시간, 인덱스 크기, 검색 속도가 모두 나빠집니다.
  - 실제로 자주 검색하는 범위는 최근 몇 주입니다.
  - 보관 파일은 형식이 단순해서(JSON Lines) 이 시스템 없이도 읽을 수 있습니다.
  - 해시로 위·변조를 확인할 수 있습니다(ISMS 2.9.4).
- **대안:**
  - pg_dump 로 파티션 백업: 복원에 PostgreSQL 이 필요하고, 형식이 열려 있지 않습니다.
  - 객체 스토리지(MinIO, AGPL): 필요하면 `archive/` 를 그쪽으로 동기화합니다.

## ADR-017 시간 조건에 수신 시각 하한을 함께 거는 파티션 가지치기 — 기각
- **상태:** 시험 후 기각 (2026-10-03)
- **시도:** `ts >= since` 에 `received_at >= since - 1일` 을 함께 붙여 오래된 월 파티션을 건너뛰게 했습니다(파티션 키는 received_at, ADR-003).
- **측정 (500만 건, docs/PERFORMANCE.md):** 오히려 크게 느려졌습니다.
  - 7일 시계열: 0.6초 → 11.3초
  - 30일 건수: 0.4초 → 4.8초
  - 원인: 조건이 늘면서 인덱스만 읽던 조회가 테이블 본문을 읽게 바뀌었습니다.

## ADR-019 공통 필드(분류·사용자·IP)를 컬럼으로
- **상태:** 채택 (2026-10-04)

- **주의:** 원본은 그대로 `raw` 에 있습니다. 추출 규칙을 바꾸면 기존 행은 마이그레이션 UPDATE 로 다시 채웁니다.

## ADR-020 IIS·MSSQL 텍스트 로그는 서버에서 해석
- **상태:** 채택 (2026-10-04)

  - → **ADR-037 로 개정:** IIS 열 순서는 DB(`iis_layouts`)에 두고, 추정한 순서는 값 모양으로 확인합니다. MSSQL 여러 줄은 에이전트가 묶고 서버는 첫 줄로 해석합니다.

## ADR-027 메모리 기본값 4GB 서버 기준 + 컨테이너 상한
- **상태:** 채택 (2026-10-15)
- **결정:** compose 기본값을 4GB 서버에 맞춥니다(shared_buffers 512MB, 병렬 2, shm 512m). db·api 컨테이너에 `mem_limit`(1536m / 768m), api 에 `MALLOC_ARENA_MAX=2`. 에이전트는 `storage.max_chunks_up: 16` 으로 메모리 조각 수를 제한합니다.
- **이유:** 이전 기본값(8GB 기준)으로 4GB 서버에서 db 가 2GB 가까이 차지했습니다. shared_buffers 는 돌려주지 않는 캐시이고 `docker stats` 는 페이지 캐시까지 세어 '정리가 안 되는' 것처럼 보입니다. 상한을 두면 커널이 캐시부터 비우고, 넘쳐도 그 컨테이너만 재시작됩니다(에이전트는 디스크 버퍼로 재전송).

## ADR-029 알림 처리 기록과 무음: 상태는 알림에, 기록은 지울 수 없는 타임라인에
- **상태:** 채택 (2026-10-14)
- **결정:**
  - 알림에 처리 상태(`open` 처리 안 됨 → `acked` 확인함 → `resolved` 해결됨)와 처리자·처리 시각을 둡니다(009). 해결은 확인을 겸합니다(확인한 사람이 없으면 해결한 사람·시각으로).
  - 확인·해결·다시 열기·메모는 `alert_notes` 타임라인에 쌓습니다. DB 트리거로 **수정·삭제·TRUNCATE 를 막고**(009, 010), 알림이 보관기간 만료로 지워질 때만 함께 지워집니다.
  - **확인·메모**는 알림을 볼 수 있는 사람 누구나, **해결·다시 열기·무음**은 관리자 또는 `alerts.handle` 권한 그룹만 합니다.
    - '확인'은 넓게 열어 둡니다. 누구든 '보고 있다'를 남겨야 대응이 빨라집니다. 대신 누가 확인했는지 감사로그에 남고, 담당자는 **확인함을 처리 안 됨으로 되돌릴 수 있습니다**(다시 열기). 확인으로 대기열을 비우는 오용을 되돌리기 위해서입니다.
    - 해결된 알림은 '확인'으로 되살아나지 않습니다(권한 없는 다시 열기 우회 방지).
  - 상세에서 '같은 규칙·대상의 해결 안 된 알림도 함께 해결'은 서버가 한 문장으로 처리합니다(`with_related`, 개수 제한 없음).
  - **무음(silence):** 규칙·대상(비우면 전체)·기간·사유. 끝 시각은 **지금부터 30일 안**이어야 합니다(길이만 묶으면 미래 무음을 이어 붙여 늘릴 수 있음). 더 길게 끌 일이면 규칙을 끕니다(규칙 관리 권한, 변경 이력).
    - 무음 중에도 알림은 **기록하고 전송만 건너뜁니다**(`alerts.silence_id`, 전송 상태 `skipped`).
    - 무음이 끝난 뒤 이벤트가 **새로** 들어오면(문제가 계속되면) 재알림 간격을 기다리지 않고 다음 평가에서 다시 알립니다. 무음 중에 쌓인 이벤트(점검 잡음)만으로는 다시 울리지 않습니다. PC 수신 끊김(`agent_silent`)은 무음이 끝났을 때 여전히 끊겨 있으면 다시 알립니다.
  - 무음 해제는 행을 지우지 않고 끝 시각을 앞당깁니다 → 언제 무음이었는지가 증적으로 남습니다. 보관기간이 지나 무음을 지울 때도 개수를 감사로그에 남깁니다.
  - **조회 범위(ADR-025)와 함께:** 범위가 있는 사용자에게는 자기 알림에 걸릴 수 있는 무음만 보입니다(모든 규칙·모든 대상 / 내 PC 대상 / 내 분류의 규칙). 무음을 걸고 풀 수 있는 것은 볼 수 있는 규칙·대상 한 개뿐입니다. 이력 목록은 보이는 (규칙, 대상)으로 **LIMIT 전에** 거릅니다.
  - **CSV 증적:** 처리 기록을 포함해 내보내고, 로그에서 온 값이 `= + - @` 로 시작하면 앞에 `'` 를 붙여 엑셀 수식 실행을 막습니다(감사로그 CSV 도 같은 `app/csvexport.py`). 1만 건에서 잘리면 파일·응답 머리글·감사로그에 표시합니다.
  - 사이드바 숫자는 '확인하지 않은 알림 수'로 바꾸고, 누르면 그 목록을 엽니다.
  - 마이그레이션 이전 알림은 `open` 으로 둡니다. 처리하지 않은 알림을 처리한 것처럼 꾸미지 않기 위해서입니다.
- **이유:** ISMS 2.11.5(사고 대응)는 인지 → 조치 → 종료를 누가·언제 했는지 남기라고 요구합니다. 점검·배포 중 예상된 알림이 쏟아지면 진짜 알림을 놓칩니다.
- **대안:**
  - 재발한 알림을 기존 열린 알림에 합치기: 건수는 줄지만 '언제 몇 번 났는지'가 흐려지고 전송 이력과 맞추기 어려워 보류. 알림은 발생마다 한 행입니다.
  - 무음 중 알림을 아예 만들지 않기: 감사 증적이 사라져 채택하지 않음.

- **보완 (2026-10-30, BACKLOG B-35 1단계):**
  - **해결 뒤 재발:** 같은 규칙·대상의 마지막 알림이 해결됨이고 **해결 시각 뒤에 받은 새 이벤트**가 있으면 재알림 간격과 상관없이 다시 알린다.
    해결 직후 창에 남은 같은 이벤트로는 울리지 않는다(무음 끝의 `_resumed` 와 같은 방식). 확인함은 간격을 지킨다. 예전에는 해결한 서비스가
    다시 죽어도 간격(5분~2시간) 동안 알림이 없었다. SQL 의 재알림 간격 미리 빼기(ADR-045)도 해결된 알림은 남긴다.
  - **지난 알림 이후 건수:** 다시 알릴 때 '지난 알림(#n, 시각) 이후 이 대상에서 k건'(7일 안의 앞 알림만), 상세는 같은 대상의 가장 최근 알림이면
    '이 알림 뒤 같은 조건으로 k건 · 마지막 시각'을 지금 규칙 조건으로 센다(시간 상한 적용). 열을 더하는 대신 셀 때 세는 것은 주기마다 세는
    비용·이중 집계가 없게 하기 위해서다 — 대신 규칙을 고친 뒤에는 고친 조건으로 센다.
  - **지연 수신 표시:** 발생 시각이 집계 구간보다 한참(max(2×창, 창+1시간)) 앞선 이벤트가 섞이면 '지연 수신분 포함 — 발생 시각 x~y'.
    판정은 그대로 수신 기준이다(에이전트가 장애 뒤 몰아 보낸 것인지 PC 시계가 틀린 것인지 받는 사람이 안다).
  - 처음 알림의 본문(웹훅 json·저장된 payload)은 예전과 같다 — 앞 알림이 있을 때만 `previous_id`·`since_previous`·`recurred` 가 붙는다.

- **보완 (2026-10-30, BACKLOG B-35 2단계) — 자동 해결과 해소 통지:**
  - 규칙 키 `resolve: manual | auto`. `agent_silent` 는 auto 가 기본(하트비트가 돌아오면 끝난 것이 분명), 건수 규칙은 manual 이 기본이고
    기본 팩은 건수가 오르내리는 운영 규칙 둘(응용 프로그램 오류 다발·웹 서버 오류 급증)에만 auto 를 단다. 한 번 나는 이벤트(서비스 비정상 종료
    7031·7034)는 조용해져도 고쳐진 것이 아니라 뺐다(검토 — 서비스가 죽은 채 10분 뒤 '해소'가 나갔다). 보안 규칙은 사람이 해결한다 —
    검토하지 않은 보안 알림이 '해결됨'으로 보고서에 남지 않게. 서로 다른 값 수(distinct) 규칙은 auto 를 거부한다. manual → auto 는 탐지 약화로 알린다(ADR-043).
  - **풀림:** 건수 규칙은 지금 집계 기간의 건수가 기준 아래, `agent_silent` 는 끊겼을 때보다 새 수신이 있고 지금 끊김 판정 안.
    건수 규칙은 마지막 알림 뒤 max(집계 기간, 5분)이 지나야 본다(경계에서 알림·해소가 번갈아 나지 않게). PC 마다 세는 규칙은 그 PC 가 그동안
    하트비트를 보내고 있어야 한다 — 꺼진 PC 의 오류가 멎은 것은 회복이 아니다. 풀리면 그 규칙·대상의 해결 안 된 알림을 모두
    `resolved`(`resolved_by='system'`, `auto_resolved=true`)로 바꾸고 처리 기록 `auto_resolve`(조건 문구)를 한 트랜잭션에 남긴다.
    해결 시각은 건수를 센 주기의 시각 — 센 뒤 해결 전에 들어온 이벤트도 '해결 뒤 재발'로 잡힌다.
  - **사람이 다시 열면 존중한다:** 처리 기록에 reopen 이 있는 알림은 자동으로 해결하지 않는다(새 알림이 나면 그것부터 다시). 다시 열었는데
    다음 주기에 엔진이 도로 닫았다(검토에서 재현).
  - **해소 통지:** 그 알림을 받은 곳(보냄·보내는 중) 중 지금 규칙의 받는 곳에만, 가장 최근 알림에 한 줄. 무음 중이면, 또는 가장 최근 알림이
    7일보다 오래면(처음 켰을 때 묵은 끊김 알림이 쏟아지지 않게) 해결만 한다. 아직 보내지 못한 알림은 건너뜀으로 바꾼다(끝난 문제를 뒤늦게 알리고
    해소는 못 알리는 것보다 낫다). 대기열은 전송기(ADR-045)를 그대로 쓰고 `alert_deliveries` 의 키에 `action`(trigger·resolve)을 더했다
    (마이그레이션 019). 해소 행의 하루 만료는 넣은 시각(`queued_at`) 기준.
  - **보낼 때 다시 본다(`dispatcher._stale`):** 다시 열렸거나 사람이 해결했다, 같은 대상에 더 새 알림이 있다(재시도를 기다리던 지난 해소가 새 알림
    뒤에 나가면 같은 dedup_key 라 받는 쪽이 지금 열린 사고를 닫는다 — 검토에서 재현), 이번 문제의 알림이 그 곳에 전해지지 않았다(넣을 때 보내는
    중이던 알림이 결국 실패) — 이면 건너뛴다. 해소 문구의 '얼마나 갔나'는 함께 해결된 알림 중 처음 알림부터.
  - **사고관리 연동:** 웹훅 json 에 `dedup_key`(규칙·대상의 SHA-256 앞 32자, 구분자 포함)와 `event_action`, Oracle 바인드 `:dedup_key`·`:event_action`.
    Oracle 은 SQL 에 `:event_action` 이 있을 때만 해소를 보낸다 — 기본 INSERT 는 ALERT_ID 가 기본 키라 같은 번호를 다시 넣으면 실패하고, 받아도 새 사고로 보인다.
  - 보고서는 자동 해결을 따로 세고 '해결까지(중앙값)'는 사람이 해결한 것만 — 조건이 풀린 시각은 대응 시간이 아니다.
  - **대가:** 자동 해결 뒤 다시 맞으면 재발(1단계)로 바로 다시 알리므로, 오르내리는 운영 규칙은 재알림 간격보다 자주 울릴 수 있다(최소 5분 유지로 줄임).
    사람이 해결한 알림에는 해소 통지를 보내지 않는다. 무음이 걸린 동안 풀린 문제는 해소 통지가 없다(점검 중 잡음을 줄이는 쪽을 골랐다).
    PC 이름이 agents 에 없는 묶음(syslog 장비, IP·계정 묶음)은 살아 있는지 모르므로 건수만 본다. 019 뒤로 이미지만 되돌리면 옛 전송기가 해소 행을
    알림으로 보낼 수 있다 — 되돌리기 전에 대기 중인 해소 행을 건너뜀으로(AIRGAP §10).
  - **대안:** 해소를 새 알림 행으로 — 알림 수·보고서가 두 배가 되어 기각. 해소 통지를 모든 받는 곳에 — 받지 않은 알림의 '해소'는 혼란이라 기각.
## ADR-030 메신저 프리셋: 서비스마다 받는 모양으로, 공식 형식만
- **상태:** 채택 (2026-10-15)
- **결정:** 웹훅 형식에 `slack`·`teams`·`dooray`·`jandi` 를 더합니다(`app/alerts/messenger.py`). DB 변경 없이 연동 설정의 `format` 값만 늘립니다.
  - 형식은 각 서비스 공식 문서와 실제 응답으로 확인한 것만 씁니다(2026-10-15 조사·교차 확인). Slack 은 머리글 + 색 막대 첨부 안의 Block Kit, Teams 는 워크플로 웹훅의 Adaptive Card 1.4 봉투, 두레이는 평문 + 첨부, 잔디는 `body`/`connectInfo` + 전용 Accept 헤더.
  - Teams 는 Office 365 커넥터가 2026-05 에 종료되어 **워크플로 웹훅만** 지원합니다. 성공 응답 202 는 '접수'라서 실제 게시는 워크플로 실행 기록에서 확인하라고 화면에 안내합니다.
  - 클라우드 메신저 4종은 https 주소만 받습니다. 같은 주소로 보내는 최소 간격을 형식마다 둡니다(두레이 1.1초, Slack·잔디 1초, Teams 0.3초).
  - 받는 쪽 오류 본문의 토큰(주소 경로·쿼리·사용자 정보)은 넉넉히 읽어 가린 뒤에 자릅니다(먼저 자르면 경계에 걸친 토큰 앞부분이 남음). 모든 전송 오류 문구가 같은 가림을 거칩니다(AGENTS.md 절대 규칙 6).
  - 넘김(30x)은 따라가지 않고 실패로 남깁니다 — 따라가면 본문 없는 GET 이 '전송됨'이 되고 인증 헤더가 넘어간 곳으로 갑니다.
  - https 는 형식이 아니라 **호스트** 기준으로도 강제합니다(형식을 json·text 로 바꿔 우회하지 못하게).
  - 로그에서 온 값은 길이 제한이 없어 모든 칸에 상한을 둡니다(Teams 는 28KB 를 넘으면 202 를 받고도 게시가 실패해 알림이 조용히 사라짐).
- **이유:**
  - 받는 쪽에서 변환 서버를 따로 두기 어렵습니다(폐쇄망·병원). 서비스가 바로 보여 주는 모양이어야 운영자가 씁니다.
  - 두레이는 1초 1건을 넘으면 성공을 주고도 버려서 재시도로도 찾을 수 없습니다 — 보내는 쪽에서 간격을 지켜야 합니다.
  - 두레이·잔디·Slack 은 http 주소로도 받거나(두레이) 응답 없이 멈춰서(잔디) 토큰이 평문으로 나가거나 전송이 늦어집니다.
  - Slack 의 링크 버튼은 앱에 상호작용 설정이 없으면 누를 때 오류 표시가 떠서 글자 링크를 씁니다.
- **대안:** Teams 옛 MessageCard — 워크플로 템플릿이 `attachments` 를 돌며 카드를 올려서 실패하는 경우가 있어 쓰지 않습니다. 카카오워크·네이버웍스는 요구가 생기면 같은 방식으로 추가합니다.

## ADR-031 DB 백업: db 와 같은 이미지의 backup 서비스, 결과는 감사로그
- **상태:** 채택 (2026-10-16)
- **결정:** compose 에 `backup` 서비스(`postgres:17-alpine`, `deploy/backup/backup.sh`)를 둡니다. 매일 `pg_dump -Fc` + SHA-256 + `config/` 묶음, 최근 N개 보관, 매주 임시 DB(`<DB>_restore_check`)에 실제로 복원해 해시·마이그레이션 버전·주요 테이블 행 수를 확인합니다.
  - 결과는 스크립트가 `audit_log` 에 직접 INSERT 합니다(`backup.create/failed/verify/restore`). api 는 그 기록으로 화면 상태와 경고를 만듭니다 — 백업 파일을 api 컨테이너에 보일 필요가 없습니다.
  - 장애 복구는 `backup.sh restore <파일> --yes` 한 명령으로(해시가 맞는 파일만, 복원 사실도 기록). 손으로 치는 절차보다 실수가 적습니다.
    - 운영 DB 에 연결된 세션(api 등)이 있으면 거부합니다. `dropdb --force` 로 끊으면 api 가 곧바로 다시 붙어 반쯤 복원된 DB 에 쓰기 때문입니다.
    - 지금 DB 를 `before-restore-<시각>.dump`(+해시)로 먼저 남기고, 임시 DB(`<DB>_restoring`)에 복원이 끝난 뒤에만 이름을 바꿔 끼웁니다. 파일을 잘못 골랐거나 복원이 실패해도 되돌릴 수 있습니다.
  - 행 수는 `pg_dump --snapshot` 과 **같은 스냅숏**에서 셉니다(내보낸 스냅숏의 트랜잭션 안에서 psql `\!` 로 pg_dump 실행). 그래서 복구 시험이 '백업에 든 행 수와 정확히 같은가'를 볼 수 있습니다. 따로 세면 매시간 정리 작업이 그 사이에 지운 행 때문에 거짓 실패가 납니다.
  - 일정은 '시각이 지났고 오늘 아직 안 했으면'으로 돕니다(마지막 날짜는 `backups/.last-run`). 정확히 그 1분에만 돌면 긴 복구 시험이 다음 날 시각을 넘기거나 서머타임으로 그 시각이 없는 날 하루를 건너뜁니다.
  - 복구 시험·복원 전에 DB 디스크(db 볼륨을 읽기 전용으로 붙여 `df`)의 남은 공간을 봅니다. 모자라면 시험하지 않고 '실패(공간 부족)'로 남깁니다 — 운영 DB 디스크를 채우지 않게.
  - 보관 개수(`WLM_BACKUP_KEEP`)는 1 이상만 받습니다. 0 을 '무제한'으로 알고 넣으면 방금 만든 백업까지 지워지기 때문입니다. 방금 만든 파일은 어떤 경우에도 정리하지 않습니다.
  - 파티션 만들기·지우기는 잠금을 5초만 기다립니다(`partitions.DDL_LOCK_TIMEOUT`). pg_dump 가 events 를 읽는 동안 배타 잠금을 줄 서서 기다리면 그 뒤의 수집이 모두 멈추기 때문입니다. 파티션은 미리 만들어 두므로 다음 주기로 미뤄도 됩니다.
  - `.env`(암호화 키)는 묶지 않습니다.
- **이유:**
  - db 와 같은 이미지라 폐쇄망 반입 묶음이 늘지 않고, `pg_dump`·`pg_restore` 버전이 서버(17)와 항상 같습니다. api 이미지(Debian 의 PostgreSQL 15 클라이언트)로는 17 서버를 덤프할 수 없습니다.
  - ISMS 2.9.3 은 백업만이 아니라 **복구 시험 기록**을 봅니다. 파일이 있다는 것만으로는 복원된다는 보장이 없어서(잘린 파일·권한·확장 기능) 실제로 복원해 봅니다.
  - 키를 백업과 같이 두면 백업만 빼 가도 화면에서 넣은 비밀값(SMTP·Oracle·웹훅)을 풀 수 있습니다(ISMS 2.7.2).
- **대가:** 복구 시험 동안 DB 크기만큼 디스크와 I/O 를 씁니다(새벽, 주 1회). 부족하면 '공간 부족'으로 실패를 남기므로, 디스크를 늘리거나 `WLM_BACKUP_VERIFY_WEEKDAY=0` 으로 끄고 시험 서버에서 수동으로 합니다. 복원도 안전 사본과 임시 DB 만큼 공간을 더 씁니다(DB 가 망가져 덤프가 안 되면 `--no-safety-dump`).
- **대안:** 호스트 cron + 스크립트 — 설치마다 cron 설정이 필요하고 결과가 화면에 안 보여 보류. WAL 보관·특정 시점 복구(PITR) — 규모가 커지면 검토.

## ADR-032 정기 점검 보고서: 서버가 만든 하나의 문서를 저장·발송·열람, 사람이 '점검 확인'
- **상태:** 채택 (2026-10-16)
- **결정:** 앱 안의 작업(1분마다, advisory lock)이 정한 시각에 일간(어제)·주간(지난주 월~일) 보고서를 만들어 `reports` 에 저장하고 받는 곳(수신 그룹 메일·웹훅 요약)으로 보냅니다(`app/reports/`).
  - 같은 기간의 정기 보고서는 고유 색인으로 하나만 — 재시작·여러 대에서도 중복 발송이 없습니다. 꺼져 있다가 켜지면 가장 최근 기간만 만듭니다.
  - 내용(`payload`)은 만들 때 모두 담고 **고칠 수 없게**(트리거) 저장하며, 감사로그에 내용 해시를 남깁니다. 메일·화면·인쇄본은 모두 이 payload 를 서버의 같은 렌더러로 그린 HTML 입니다(화면은 sandbox iframe, CSP 로 스크립트 차단).
  - 담당자가 화면에서 **점검 확인**(의견·조치)을 한 번 남깁니다.
  - 받는 곳이 없어도 만들어 저장합니다. 보고서 자체가 점검 증적입니다.
  - 조회 범위가 정해진 사용자는 볼 수 없습니다(전체 PC·분류가 들어 있음).
  - 전송은 '적어 두고 보내기'입니다. 보고서를 저장할 때 받는 곳을 '보내는 중'으로 같이 적고, 결과는 덧붙입니다(덮어쓰지 않음). 자동 발송은 감사로그 `report.deliver` 에도 남깁니다.
    - 보내다가 서버가 멈추면 다음 주기에 그곳만 이어서 보냅니다(하루가 지나면 실패로). 고유 색인 때문에 같은 기간을 다시 만들지 않으므로, 이게 없으면 그날 보고서가 영영 안 갑니다.
    - 다시 보내기는 기본으로 못 받은 곳만 — 받은 사람에게 같은 메일이 또 가지 않게.
  - 비교는 '일주일 전 같은 시간'(일간 = 지난주 같은 요일)입니다. 바로 전날과 비교하면 PC 를 끄는 주말·휴일 다음마다 '로그가 줄었다'는 거짓 경고가 나서, 보는 사람이 경고를 무시하게 됩니다.
  - 추이 칸은 표시 시간대의 실제 시각(일간 1시간)·달력 날짜(주간 하루)로 나눕니다. 서머타임 날은 23·25시간이라 고정 길이로 나누면 칸이 빠지거나 뭉칩니다.
  - 렌더러는 예전 형식의 payload 도 그려야 합니다(고칠 수 없으므로). 예: 무결성 확인 결과 `bad` 가 개수(예전 CLI)든 파일 이름 목록이든 받습니다.
- **이유:**
  - ISMS 2.9.5 는 '정기적으로 점검하고 결과를 남길 것'을 봅니다. 자동 메일만으로는 사람이 실제로 보았다는 근거가 약해서 점검 확인을 따로 남깁니다.
  - 화면을 JS 로 따로 그리면 메일·인쇄본과 내용이 어긋날 수 있어 렌더러를 하나로 두었습니다.
  - 보고서마다 '점검 필요'(로그 0건, 로그 삭제, 백업 문제, 해결 안 된 심각 알림 등)를 맨 위에 모아, 매일 몇 초 안에 이상 여부를 판단할 수 있게 했습니다.
- **대가:** 주간 보고서는 7일치 이벤트를 몇 번 집계하므로 큰 DB 에서 수 초~수십 초 걸릴 수 있습니다(새벽·아침 1회). 보고서 표는 보관기간만큼 쌓입니다(1건 수 KB~수십 KB).
- **대안:** 대시보드 PDF 스냅숏 — 브라우저 렌더링이 필요해 폐쇄망·서버에서 어렵고, '점검 필요' 판단이 없어 보류.

## ADR-033 검색 문장: 새 파라미터 query, 같은 뜻이면 같은 SQL, 서버·화면 파서는 한 표로 시험
- **상태:** 채택 (2026-10-16, BACKLOG B-01)
- **결정:** 한 줄 검색 문장 `event_id:4625 ip:10.0.0.5 -user:svc_backup level:오류,심각 "잘못된 암호"` 를 새 파라미터 `query` 로 받습니다. URL·API·알림 규칙 `match.query`·대시보드 위젯 `query.query` 가 같은 이름·같은 문법입니다(PROJECT.md §4.1).
  - 기존 파라미터(`host … q f.*`)는 뜻·SQL 모두 그대로이고 `query` 와 AND 입니다. `q` 를 문장으로 다시 해석하지 않습니다 — 배포된 규칙의 `q: "…|IEX (|…"`, 옛 링크의 `q=다시 부팅`(구절)의 뜻이 바뀌기 때문입니다.
  - 파서는 표준 라이브러리만 쓰는 `server/app/querylang.py` 와 import 없는 `web/js/querylang.js` 한 쌍입니다(한 줄씩 같은 스캐너). 상수·오류 문구는 `@sync` 블록 하나 — 컨테이너 pytest 가 두 언어를 비교합니다.
  - **포함 조건은 기존 `EventFilter` 필드에 교집합으로 합칩니다** → 같은 뜻이면 SQL 이 바이트 단위로 같습니다(`same_sql` 시험, 옛 조건 80개 SQL 스냅숏). 새 색인·마이그레이션이 없고 '기존 검색보다 느려지지 않음'이 구조로 보장됩니다. 겹치지 않으면(`host:A host:B`) `never` → `FALSE`.
  - **제외는 `(포함식) IS NOT TRUE`** — 값이 없는(NULL·경로 없음·JSON null) 이벤트는 남깁니다. 백로그 초안의 `NOT IN`/`<> ALL` 은 NULL 행을 버려 `-user:svc_backup` 이 사용자 없는 대다수 로그를 숨기고, `NOT (raw @> …)` 는 타입을 엄격히 따져(숫자 4625 ≠ "4625") 포함식의 여집합이 되지 않아 기각했습니다.
  - `f.*` 는 지금처럼 글자 비교(`raw #>> 경로`)입니다. 실시간 매처의 글자 표현도 `#>>` 와 같게 — 배열·객체는 `', '`·`': '`, 실수는 PostgreSQL numeric 처럼 지수 표기 없이(저장 때 Python repr 이 그대로 jsonb 숫자가 되므로 `Decimal(repr(x))` 를 펼친다). 메시지는 PostgreSQL ILIKE(글자마다 towlower)와 맞춘 `fold`(İ→i, Σ→σ 후 소문자)로 비교합니다 — Python·JS 의 lower 는 어말 시그마와 İ 만 다릅니다(`casefold` 는 ß→ss 라 기각).
  - 엄격한 문법: 키처럼 생긴 이름 + `:` 는 키여야 하고(오타는 위치·힌트와 함께 오류), 와일드카드·괄호·`|`·`AND/OR/NOT` 은 예약해 오류로 알립니다. 나중에 넣어도 지금 문장의 뜻이 바뀌지 않게, 그리고 오타가 조용한 메시지 검색이 되지 않게. `C:\Windows`, `http://…`, `12:30`, `fe80::1` 은 따옴표 없이 메시지 단어입니다(콜론 규칙).
  - 위치는 코드 포인트(한국어 'N번째 글자'와 맞음), 입력 칸에서만 UTF-16 으로 바꿉니다. 오류는 처음 하나, 400 응답은 `detail`(문자열, 기존 그대로) + `query_error{code,start,end}`.
  - 화면: 문장이 조건의 정본이고 드롭다운·수준 칩은 문장을 보여 주고 고치는 창입니다(span 단위로 고쳐 사용자 표기 보존). 옛 링크는 들어올 때 문장으로 접고, 뜻이 똑같이 옮겨지지 않는 값은 옛 파라미터로 남깁니다.
  - 알림 규칙의 조회 범위(ADR-025)는 `Rule.categories`(문장 속 `category:` 포함)로 판단합니다.
- **검증:** 케이스 표 하나(`server/tests/querylang_cases.json`: 정상·오류 문장, 고정 이벤트 매칭, 같은 SQL, 옛 링크 접기, 문장 편집)를 Python 파서·실제 SQL·Python 매처·JS 파서·JS 매처가 함께 씁니다. 무작위 300문장으로 SQL ≡ 매처, node 와 python3 교차 퍼징 3,000문장으로 두 파서를 비교합니다. JS 시험은 npm 없이 `node --test`(컨테이너에는 node 가 없어 개발 PC·CI).
- **이유:** 조사할 때 "이 IP 인데 이 계정은 빼고" 같은 조건을 한 줄로 쓰고 공유할 수 있어야 합니다. 서버·실시간(대시보드)·알림이 같은 규칙을 쓰지 않으면 같은 문장이 화면마다 다른 결과를 냅니다.
- **대가:** 제외·`-단어` 는 색인을 쓰지 못해, 제외만 있는 긴 기간 건수·시계열은 본문을 읽어 느립니다(PERFORMANCE.md §2.1, 화면 린트로 안내). 엄격한 문법이라 `Error:` 같은 말은 따옴표가 필요합니다(빠른 고침 단추). 분류처럼 닫힌 어휘를 바꾸면 SYNC 두 곳·케이스 표를 함께 고칩니다(불일치는 시험이 잡음).
- **되돌리기 위험:** 이 기능 이전 버전은 `query` 를 조용히 무시합니다 — 공유 링크·위젯 문장이 '전체'로 넓어지고, 알림 규칙의 `match.query` 는 ConfigError 로 거부되어 이전 규칙을 유지합니다.
- **대안:** 타입을 따지는 jsonb 비교(배포된 규칙의 `"10"` 비교가 바뀜), 와일드카드(btree 색인 못 씀·세 엔진의 glob 일치 위험), 한글 키 별칭, 쉼표·`|` 를 단어 OR 로 쓰기(`1,024` 같은 로그 값과 충돌), 화면 안의 자체 시험 페이지(운영 이미지에 들어감), 최근 검색어 저장(계정·IP 가 브라우저에 남음 — ISMS) — 모두 기각.

## ADR-034 CI: 개발 이미지 안에서 시험, 외부 action 은 커밋 해시 고정
- **상태:** 채택 (2026-10-16, BACKLOG B-15)
- **결정:** GitHub Actions(`.github/workflows/ci.yml`)가 모든 push·PR 에서 돌린다.
  - 서버 시험·린트는 `server/Dockerfile` 의 `dev` 이미지 안에서(PostgreSQL 17 서비스 컨테이너). 시험이 컨테이너 배치(`/app/app`·`/app/web`·`/app/config`)를 전제하고, 운영과 같은 Python·의존성으로 돌기 위해서다.
  - 백업 스크립트는 compose 와 같은 `postgres:17-alpine` 이미지로 `selftest`, 화면 모듈은 npm 없이 `node --test`(교차 퍼징에 python3).
  - 에이전트 설정은 설치 스크립트와 같은 규칙으로 틀을 채워(`tools/ci/render_agent_configs.py`) `fluent-bit --dry-run`. 윈도 설정의 `winevtlog` 은 윈도 빌드에만 있어 윈도 러너에서 폐쇄망 묶음과 같은 4.0.14 zip 을 받아 **저장소의 SHA-256 으로 확인**한 뒤 돌린다.
  - 운영 이미지는 Trivy 로 점검: 고칠 수 있는 CRITICAL 은 실패, HIGH 는 기록만.
  - 외부 action 은 **커밋 해시로 고정**(태그는 옮겨질 수 있다 — 공급망), 토큰 권한은 읽기만. ruff 는 정확한 버전으로 고정 — 새 버전이 규칙을 바꾸면 이유 없이 CI 가 깨진다(실제로 0.16→0.17 에서 `noqa` 판정이 바뀜).
- **이유:** ISMS 2.8.5(소스 변경 관리)·2.10.x(시스템 보안)는 변경이 검증을 거쳤다는 증적을 본다. 사람이 '시험 돌렸다'고 적는 것보다 CI 기록이 증적이 된다. B-01 처럼 두 언어가 같은 규칙을 지켜야 하는 코드는 node 시험이 컨테이너 밖에서만 돌아 CI 가 꼭 필요했다.
- **대가:** 개발 이미지 빌드 시간(수 분), 윈도 러너, action·Trivy 해시 갱신을 사람이 챙겨야 한다.
- **대안:** 러너에 직접 pip 설치 — 경로·버전이 컨테이너와 달라 시험이 어긋나 기각. 사내 GitLab CI — 저장소가 GitHub 라 우선 Actions, 사내로 옮기면 같은 단계를 옮긴다.

## ADR-035 화면 조회에 시간 상한과 동시 자리 (503 + 그 화면에 맞는 안내)
- **상태:** 채택 (2026-10-16)
- **배경:** B-01 벤치(PERFORMANCE.md §2.1)에서 2글자 단어 검색이 30일 29초, 결과 없는 7일 검색이 1분을 넘겼다. 검색에는 시간 제한이 없었고, 브라우저를 닫거나 클라이언트를 끊어도 DB 쿼리는 끝까지 돈다(실측: 끊긴 쿼리가 3분 넘게 남음). 연결 풀 10개를 수집과 나눠 쓰므로 느린 검색이 쌓이면 수집이 풀 대기 30초 뒤 실패(500)한다 — 검토에서 느린 문장 20개로 재현.
- **결정:**
  - **시간 상한:** 화면 조회(`routers/query.py` 라우터의 GET 전부 + POST 로 읽는 규칙 미리보기)는 쿼리마다 `statement_timeout` 을 건다 — `WLM_SEARCH_TIMEOUT_SEC`(기본 30초, 0 = 없음). 의존성이 컨텍스트 변수를 켜고, `db.fetch_all/fetch_one` 이 같은 트랜잭션에서 `set_config('statement_timeout', …, true)`(= `SET LOCAL`)를 먼저 보낸다. 풀에 돌려줄 때 트랜잭션이 끝나 같은 연결을 다음에 쓰는 수집·알림 엔진에는 남지 않는다(시험이 풀 연결마다 확인).
  - **동시 자리:** 상한이 걸린 조회는 한꺼번에 `SEARCH_SLOTS`(6)개 연결까지만 쓴다. 나머지 4개는 수집·알림 엔진·상태 확인 몫으로 늘 남는다. 자리를 기다리는 시간에도 같은 상한을 두고, 넘으면 '조회가 몰려 차례가 오지 않았다'로 안내한다.
  - **쓰기는 제외:** PC 삭제처럼 같은 라우터의 쓰기(DELETE·POST)는 잠금을 기다려서라도 끝내야 하므로 걸지 않는다. 알림 엔진·점검 보고서·수집·보관 작업에도 걸지 않는다 — 놓치면 안 되는 작업이고, 느린 규칙은 미리보기(상한 있음)에서 먼저 드러난다.
  - **안내:** 넘으면 `db.QueryTimeout` → **503** + 그 화면에서 할 수 있는 방법(검색: 기간·조건·짧은 단어는 따옴표 / 수집 PC: 기간 / 미리보기: 조건 좁히기). 관리자의 `pg_cancel_backend` 같은 다른 취소는 시간 초과로 바꾸지 않는다(서버 메시지와 걸린 시간으로 구별).
  - **기록:** 끝나지 않은 검색도 접속기록(`events.search`, `timeout_sec`)에 남긴다. 서버 경고 줄은 경로만 — 전체 주소는 같은 요청의 접근 로그 줄에 있다(검색어·계정·IP 가 컨테이너 로그에도 남는 것은 그대로, docs/ISMS.md).
  - 화면은 이전 검색의 건수·막대를 지우고 안내를 보인다. '더 보기'가 실패하면 받은 결과는 두고 '다시 시도'.
- **이유:** 어떤 조회든 끝나는 시간이 정해져 있어야 운영자가 '멈춘 화면'과 '느린 검색'을 구별하고, 한 사용자의 검색이 수집을 멈추지 못한다. 쿼리 단위(SET LOCAL)라 다른 작업에 새지 않고 연결 문자열·DB 설정을 바꾸지 않는다.
- **대가:** 30초가 넘는 정당한 조회(긴 기간의 원본 필드·짧은 단어, 큰 규모의 30일 집계)는 조건을 좁히거나 상한을 올려야 한다(PERFORMANCE.md §2.2). 조회가 7개 넘게 동시에 오면 차례를 기다린다. 쿼리마다 왕복 한 번(set_config)이 늘어난다(0.1ms 안팎). 클라이언트가 끊겨도 상한까지는 쿼리가 돈다. 자리 대기 + 실행이라 한 요청이 상한의 두 배까지 걸릴 수 있다.
- **대안:** DB 역할·연결 단위 `statement_timeout` — 수집·보관·마이그레이션까지 걸려 기각. 수집 전용 풀 분리 — 연결 수가 늘고 실시간·하트비트 경로까지 나눠야 해 자리 제한으로 대신. 끊긴 요청의 쿼리 취소 — 서버 프레임워크가 연결 끊김을 엔드포인트에 알리지 않아 보류. 2글자 색인(pg_bigm) — DB 이미지를 바꿔야 해 보류. 짧은 단어의 SQL 을 바꿔 색인을 피하기 — 캐시 상태에 따라 오히려 느린 경우가 있어(실험) 기각.

## ADR-036 운영 HTTPS·에이전트 TLS: api 가 직접 TLS 를 끝내고, 평문·TLS 수집을 병행한 뒤 닫는다
- **상태:** 채택 (2026-10-16, BACKLOG B-06)
- **배경:** 화면과 수집이 평문 HTTP 였다(ISMS 2.7.1). BACKLOG 원안은 Caddy compose 프로필 + Nginx 예시였다. 폐쇄망 반입 묶음은 compose 의 이미지를 모으므로 이미지가 늘면 반입·Trivy·심사 대상이 함께 는다. 운영 첫 설치(B-25) 전이다. 설계는 관점이 다른 세 안(폐쇄망 운영·보안·전환)을 심사해 종합했다.
- **결정:**
  1. **api 의 uvicorn 이 TLS 를 끝낸다**(`WLM_TLS=on`). TLS 1.2 이상, TLS 1.2 는 ECDHE+AEAD 만(파이썬 기본은 CBC 를 허용 — 실측), 재협상 끔(`tlsutil.server_context`). 새 이미지·의존성 없음(uvicorn 하한만 0.54 — ssl_context_factory).
  2. **포트를 역할로 나눈다:** 화면 8000(→`WLM_PORT`)은 TLS 만(평문 화면 리스너·리다이렉트 없음), 수집은 평문 8001(→6976)과 TLS 8002(→6977)를 **병행**하다가 모든 PC 가 옮기면 `WLM_INGEST_PLAIN=off` 로 평문 리스너를 띄우지 않는다(연결 거부). syslog 수신기는 게시하지 않는 내부 8003 으로 — 평문을 닫아도 syslog 는 계속.
  3. **에이전트는 서버를 확인한다:** 설치 묶음의 `ca.crt` 로 연쇄를(`tls.verify`), 인증서의 **DNS 이름**으로 이름을(`tls.verify_hostname: on` — Fluent Bit 기본값은 off, `tls.vhost`). Fluent Bit 4.0 은 IP SAN 으로 확인하지 못해(실측) 서버 인증서에 DNS 이름이 꼭 있어야 한다(DNS 등록은 필요 없음). 끄는 선택지는 두지 않는다. 설치 스크립트(Windows `CaSha256`, Linux `TLS_CA_SHA256`)는 CA 지문을 대조하고, PC 에는 인증서만 ASCII PEM 으로 둔다. Windows 는 파일을 쓰기 전에 폴더 소유자·권한을 다시 잡는다(일반 사용자가 폴더를 미리 만든 경우).
  4. **확인할 수 없는 묶음은 만들지 않는다:** TLS 서버는 TLS 묶음만 만든다. 인증서 상태는 에이전트와 같은 OpenSSL 로 **메모리 안에서 실제 핸드셰이크**를 해 보고 판단한다(`tlsutil.agent_handshake` — 연쇄·만료·용도(EKU)·이름 제한·중간 CA·키 짝, 파이썬 3.13 의 STRICT·PARTIAL_CHAIN 은 끔). 다른 검증기로 흉내 내면 만료된 CA·중간 CA 를 루트로 둔 경우를 놓친다(검토에서 재현). 실패하거나 CA 없음·DNS 이름 없음·인증서에 없는 이름이면 409/422. CA 파일은 인증서만 다시 써서 넣는다(개인키가 섞인 사내 PKI 파일 방지).
  5. **인증서:** 자체 CA(ECDSA P-256, 10년, **이름 제한** — 준 DNS·IP 만, IP 를 안 주면 모든 IP 금지, 메일 금지, 용도는 서버 인증만)와 서버 인증서(2년, AKI 포함, 하루 앞당김)를 `app.cli tls-init/tls-renew` 로(DB 없이, 설치가 일회성 컨테이너로). CA 개인키는 api 에 마운트하지 않는 `tls-ca/` 에 — 서버가 뚫려도 가짜 인증서를 못 만들게. 사내 PKI 도 같은 자리(`tls/`). 서버 키는 소유자 uid 10001·0600(이미지의 wlm 그룹 번호는 999 로 고정돼 있지 않아 그룹으로 주지 않는다).
  6. **쿠키 Secure 는 요청 scheme 으로 자동**, `WLM_COOKIE_SECURE=true` 는 강제용(그러면 http 로그인은 안내와 함께 400). HSTS 는 선택(비우면 안 보냄, `0` 이면 `max-age=0` 으로 브라우저의 기억을 지움, includeSubDomains 없음).
  7. **프록시 헤더는 `WLM_TRUSTED_PROXIES` 에 적은 주소만 믿는다.** 값을 uvicorn 에 직접 넘겨 `.env` 의 `FORWARDED_ALLOW_IPS` 한 줄로 신뢰 범위가 바뀌던 경로를 막았다. `*`·/0, uvicorn 이 조용히 무시하는 값(호스트 비트가 있는 대역, IPv4 매핑 주소)은 기동 거부.
  8. **PC 별 전송 방식**(마지막 하트비트가 TLS 리스너·신뢰 프록시의 https 로 왔는지, 평문이면 수집 포트인지 화면 포트인지 — `tls`·`plain`·`web`)을 `agents.last_transport` 에 남겨 수집 PC 화면에 보인다 — 평문을 닫을 근거, TLS 를 켜면 끊길 옛 묶음(화면 포트로 보냄 — 설정 버전으로는 구별되지 않음) 찾기, ISMS 증적.
  9. 기동 전 점검(`tlsutil.preflight`)이 실패하면 아무 리스너도 띄우지 않는다(반쯤 뜬 상태 방지). 상태 확인은 `app.healthcheck`(TLS 면 https). 인증서 만료·이름·CA 문제는 기동 때와 하루 한 번 로그 — 기동 때 내보낸 인증서를 기억해, 파일만 바꾸고 재시작을 빠뜨린 경우도 알린다. 폐쇄망 설치는 켜기 전에 api 계정으로 같은 핸드셰이크를 해 보고, 배포된 CA 가 있는데 CA 키가 없으면 새 CA 를 만들지 않고 멈춘다.
- **이유:** 반입·Trivy 대상이 그대로이고, 접속 IP 가 보존되어(로그인 시도 제한·감사 IP·PC 마지막 IP) 신뢰 프록시 설정이 필수가 아니며, 소켓 포트로 판단하는 수집 포트 제한과 한 프로세스 구조(ADR-006)를 지킨다. 병행 후 닫기는 수백 대의 PC 를 끊김 없이 옮기는 유일한 순서다.
- **대가:** 인증서 교체에 api 재시작(기동 때 한 번 읽음). 화면의 http 북마크는 빈 응답. 장비 → 수신기 syslog(514)는 평문. TLS 핸드셰이크도 한 프로세스가 처리(초당 200회 새 연결에서 문제없음 — PERFORMANCE.md §2.3). 이름 제한 때문에 허용 이름 밖으로 바꾸려면 새 CA 와 전체 재배포. Windows 에이전트의 인증서 저장소·PS 5.1 실기 동작은 B-28 에서 확인.
- **대안:** Caddy compose 프로필(원안) — 이미지·반입·Trivy 가 늘고, 프록시 뒤에서는 접속 IP 를 잃어 신뢰 프록시가 필수, api 게시 포트가 남으면 프록시를 우회하는 평문 경로. 같은 포트에서 평문·TLS 자동 판별 — 이미 읽은 ClientHello 를 되돌릴 수 없음. 6976 을 그 자리에서 TLS 로 바꾸기 — 평문 에이전트가 버퍼만 쌓고 서버 로그에는 아무것도 안 남음. 화면 평문 포트 + 308 — 평문 리스너가 남음(HSTS 로 대신). 평문 수집을 403 으로 거절 — 옛 에이전트가 키를 평문으로 계속 보냄. 평문 수집 기한 자동 차단 — 날짜 하나로 수집이 끊기는 사고 위험. CA 없이 서버 인증서를 직접 신뢰 — 갱신마다 전체 재배포. 모두 기각.

## ADR-037 IIS 열 순서는 DB 에, 추정한 순서는 값 모양으로 확인 · MSSQL 여러 줄은 에이전트가 묶고 서버는 첫 줄로 해석
- **상태:** 채택 (2026-10-19, BACKLOG B-08, ADR-020 의 '한계' 개정). 서버(1단계)와 에이전트 설정 0.4.0(2단계)을 구현했다. 실제 ERRORLOG·IIS 샘플 확인은 B-08 에 남았다.
- **배경:**
  - IIS `#Fields:` 기억이 프로세스 메모리여서, 서버를 다시 시작하면 사용자 지정 열 순서를 기본 순서로 **잘못** 읽었다. 칸 수가 같으면 `src_ip`·`username` 자리가 바뀐 채 저장되었다(재현: `src_ip='lee'`, `username='443'`). `clean_ip` 는 IP 인지 확인하지 않는다.
  - 에이전트 tail 은 db 위치에서 이어 읽어, 에이전트를 다시 시작해도 머리줄을 다시 보내지 않는다. 에이전트가 멈춘 사이 새로 생긴 파일은 끝부터 읽어 머리줄 자체가 오지 않는다(실측).
  - Fluent Bit 4.0.14 의 http 출력은 작업자 2개·재시도라 요청 사이 순서가 보장되지 않는다(실측).
  - ERRORLOG 의 시작 배너·시작 인자·여러 줄 메시지는 줄마다 저장되어, 이어지는 줄에 받은 시각과 단어로 추정한 수준이 붙었다.
  - 설계는 관점이 다른 두 안(서버 중심·에이전트 중심)을 실험(Fluent Bit 4.0.14 컨테이너)으로 심사해 종합했다.
- **결정:**
  1. IIS 열 순서는 표 `iis_layouts(host, file, dir, fields, seen_at)`(마이그레이션 014)에 둔다. 이벤트와 **같은 트랜잭션**에서 upsert 한다. 프로세스 안 캐시(`repository._IIS_FILE`·`_IIS_SITE`)는 정본이 아니며 커밋한 뒤에만 넣는다. 캐시에 없는 파일은 요청마다 한 번의 쿼리로 묻는다.
  2. 줄을 읽을 후보는 이 순서다: 같은 요청의 머리줄 → 그 파일의 저장된 열 순서 → 같은 폴더(`W3SVC<n>`)의 최신 열 순서 → 기본 순서.
     **어느 후보든 칸 수와 값 모양이 맞아야 쓴다.**
     - 그 파일의 순서(같은 요청의 머리줄·저장된 순서)는 서버(IIS)가 만드는 필드만 본다(`iis.plausible`): date·time·sc-status(100–999)·정수 필드·IP(`ipaddress` 로 확인). 요청자가 정하는 값(method·URI·UA·Referer·username)이 무엇이든 해석이 깨지지 않는다 — 해석 실패를 일부러 일으켜 규칙을 피하지 못하게.
     - 추정한 순서(같은 폴더·기본)는 더 엄격하다(`iis.plausible_guess`): IIS 가 늘 쓰는 필드(date·time·s-ip·c-ip·상태·하위 상태·win32·time-taken 등)가 비어 있으면 안 되고, method·URI·HTTP 버전이 요청 모양이어야 하며, 요청자 값 칸(username·UA·Referer·query·Cookie)에 숫자나 IP 만 있으면 안 된다.
       IIS 의 열 순서는 정해져 있어(포함·제외만 고름) 구성이 다르면 칸이 밀리고, 그러면 서버 값(IP·숫자)이 요청자 칸으로도 간다. 검토에서 ①만으로는 요청자가 UA 에 IP 를 넣어 `src_ip` 를 정하고 실제 IP 가 username 에 들어가는 것을 재현했다.
     맞는 것이 없으면 원문으로 저장한다(틀리게 읽지 않는다). 추정한 순서로 읽었으면 `raw.iis._layout` = `site`|`default`.
  3. 머리줄은 필드 이름(인쇄 가능·공백 없음·256자 이하 — 사용자 지정 필드의 한글 이름도, 100개 이하)과 PC·파일 경로(UTF-8 1024바이트, NUL 없음)를 확인한 뒤에만 배운다. 저장할 수 없는 값 때문에 요청 전체(다른 이벤트까지)가 거절되지 않게.
  4. 정리: 35일이 지난 열 순서는 지우되 폴더마다 최신 1개는 남긴다(월 단위·나누지 않는 파일은 머리줄이 처음 한 번뿐). 로그가 아니라 해석용 문맥이라 감사로그는 남기지 않는다.
  5. MSSQL 정규화기는 레코드의 **첫 줄**로 시각·프로세스·오류 번호를 읽고, 나머지 줄은 message 에 붙인다(`raw.mssql.lines` = 줄 수). 줄마다 온 레코드(에이전트 0.3.0 이하)와 묶인 레코드를 같은 방식으로 센다.
     에이전트 0.4.0 은 `multiline.parser`(시각으로 시작하는 줄 = 새 레코드)로 묶는다. 그 tail 은 `storage.type: filesystem` 이어야 한다(메모리면 멈출 때 묶던 레코드를 잃는다 — 실측). — 2단계.
  6. `Error:` 머리줄 짝(`_pending`)은 메모리에 그대로 두되 키에 파일을 더한다(한 PC 의 여러 인스턴스). DB 로 옮기는 것은 B-20.
- **이유:** 서버만 올리면 모든 에이전트 버전의 IIS 재시작 문제가 풀린다. 원본(raw)은 늘지 않는다. 추정에 모양 검사를 더해 '맞게 읽거나 원문으로 남기거나' 둘 중 하나가 되게 했다. multiline 은 원본을 바꾸지 않는다 — 에이전트가 보낸 레코드가 그대로 raw 다.
- **대가:**
  - 첫 설치 당일, 그리고 에이전트가 멈춘 사이 새로 생긴 파일은 머리줄이 오지 않는다(tail 이 끝부터 읽음). 같은 폴더의 열 순서가 있으면 그것으로 읽는다. 없으면 사용자 지정 열 순서 사이트는 다음 파일(00:00 UTC)까지 원문으로 남는다. → B-32.
  - 정수 열끼리만 순서가 바뀐 경우(sc-bytes↔time-taken)는 모양으로 가리지 못한다(보안 판단에 쓰는 필드는 아님).
  - 추정하는 동안(그 파일의 머리줄을 아직 못 받음) 요청자는 UA 등에 IP·숫자를 넣어 자기 줄을 원문으로 남길 수 있다(상태 코드 규칙을 피함). 틀린 IP 로 남는 것보다 낫다고 보았다. 숫자뿐인 사용자 이름·query 도 추정 동안은 원문이 된다.
  - 값 모양으로 가릴 수 없는 구성이 남는다(2차 검토, 기본 순서에서 한 칸 바뀐 구성 전수 탐색): 숫자 필드 하나(time-taken·win32·하위 상태)를 빼고 cs(Cookie) 를 더한 사이트는 추정하는 동안 요청자가 Referer 로 **자기 줄의 상태 코드**를 정할 수 있고, c-ip 를 기록하지 않는 사이트는 UA 의 IP 가 src_ip 가 될 수 있다. c-ip·sc-status 를 모두 기록하는 구성에서 다른 사람의 IP·사용자로 잘못 읽히는 경우는 찾지 못했다.
  - 업그레이드 직후에도 머리줄이 없다(옛 메모리 기억은 저장된 적이 없다): 사용자 지정 열 순서 사이트는 다음 파일(하루 단위면 00:00 UTC = 09:00 KST)까지 원문으로 남는다. 파일을 나누지 않는 사이트는 머리줄이 다시 올 때까지.
  - 한 파일 안에서 열 구성이 바뀐 뒤 옛 머리줄이 든 청크가 재시도로 늦게 오면 최신 열 순서를 덮을 수 있다(같은 파일의 머리줄은 보통 같아 드묾 — 모양 검사가 틀린 해석은 막는다).
  - 업그레이드 직후에는 표가 비어 있다(옛 메모리 기억은 저장된 적이 없다). 기본 열 순서 사이트는 `_layout: default` 로 바로 읽히고, 사용자 지정 사이트는 다음 새 파일까지 원문으로 남는다.
  - 0.4.0 에서는 `Error:` 머리줄과 본문이 다른 요청으로 갈리는 일이 잦다(multiline 이 본문을 다음 시각 줄이나 2초까지 붙잡는다 — 실측 9쌍 중 3쌍).
    짝 맞추기는 메모리라, 그 사이 서버가 다시 시작되거나 장애 뒤 재전송 순서가 바뀌면 본문에 번호가 붙지 않는다.
    순서가 뒤집혀 머리줄이 본문보다 늦게 오면, 그 머리줄이 같은 시각(1/100초)·프로세스의 다음 줄에 붙을 수 있다(드묾 — 같은 시각 줄들이 요청 경계에 걸쳐야 함).
    로그인 실패(18456)는 본문 문장으로 세므로 영향이 없고, 9002·823·824 같은 중요한 오류는 응용 프로그램 이벤트 로그에도 남아 규칙이 그쪽으로 걸린다. 짝을 DB 로 옮기는 것은 B-20.
  - MSSQL 효과는 에이전트를 다시 설치한 PC 부터. 0.4.0 에이전트 + 옛 서버는 묶인 레코드를 잘못 읽으므로(시각=받은 시각, 오류 번호 없음 — 실측) **서버를 먼저** 올린다.
  - 캐시는 워커 1개 전제다(ADR-006). 여러 워커가 되면 TTL 이 필요하다(B-20).
- **대안:**
  - 에이전트 Lua 가 레코드마다 `#Fields:` 를 붙이기 — 기각. Lua 오류는 dry-run 을 통과하고 실제 기동에서 엔진 전체(Windows 이벤트 포함)를 멈춘다. 기억이 없을 때마다 IIS 파일 전체를 엔진 스레드에서 다시 읽는다. IIS raw 가 +25~36% 영구히 커진다. 모든 IIS PC 를 다시 설치해야 효과가 난다.
  - 서버가 이어지는 줄을 붙잡았다가 합치기 — 원본 보존을 어긴다. 200 을 돌려준 뒤 유실될 수 있고, 요청 사이 순서도 믿을 수 없다.
  - 요청 사이 `Error:` 짝을 DB 로 찾기 — B-20.
  - 에이전트에서 `Error:` 머리줄과 본문까지 합치기 — spid·시각을 비교할 수 없어 끼어든 줄을 잘못 합친다. (짝이 요청 사이로 갈리는 문제를 풀 수 있어, 실제 ERRORLOG 에서 끼어드는 줄이 없는지 확인되면 다시 본다 — B-08)

## ADR-038 Windows EventData 이름은 서버가 붙이고, `f.EventData.<이름>` 은 별칭으로 본다
- **상태:** 채택 (2026-10-19, ADR-019 개정). 벤치마킹 조사(Windows 탐지 묶음)에서 드러난 결함을 고침.
- **배경:**
  - 에이전트는 Fluent Bit 4.0 이라 `event_data_as_map`(5.1.0, 2026-08 부터)이 없어 857359e 에서 빼고 `string_inserts` 만 보낸다.
    그런데 문서·UI 예시·기본 규칙 1000007(원격 데스크톱 무차별 대입)·1000009(관리자 그룹 추가)·보안 대시보드 위젯이
    `f.EventData.*` 를 써서 **실제 PC 에서는 맞을 수 없었다**. 시험·시뮬레이터가 EventData 맵을 넣어 보내 아무도 몰랐다.
  - 윈도 CI 러너에서 실제 이벤트(4624·4625·4688·4697·4720·4726·4732·4733·4738·7045·4104)를 일으켜 에이전트 설정으로 받아 보니:
    EventData 키가 없고, StringInserts 는 매니페스트 템플릿 순서이며, LogonType 같은 정수는 숫자로 온다.
    4624 v3 는 RemoteCredentialGuard 를 **중간에** 끼워 '새 필드는 뒤에 붙는다'가 늘 맞지는 않았다.
- **결정:**
  1. 서버가 `(공급자, 이벤트 ID[, 버전])` 템플릿(`normalizers/win_templates.py`)으로 StringInserts 에 이름을 붙여
     `raw.winevtlog.EventData` 에 덧붙인다(원본은 그대로 — AGENTS.md 원본 보존). 에이전트가 EventData 맵을 보내면 붙이지 않는다.
     배열보다 긴 이름은 버린다(옛 버전). 모르는 이벤트는 위치(`f.StringInserts.N`)로만 볼 수 있다.
  2. 검색·규칙·대시보드의 `f.EventData.<이름>` 은 **별칭**이다: 에이전트가 보낸 값이 먼저, 없으면(없음·JSON null) 서버가 붙인 값.
     SQL `COALESCE(raw #>> '{EventData,X}', raw #>> '{winevtlog,EventData,X}')`, Python `querylang.raw_field`,
     JS `rawField` 가 같은 뜻이다(케이스 표 querylang_cases.json, SYNC `raw_alias`). 별칭이 아닌 경로의 SQL 은 그대로다.
  3. 화면에서 값을 눌러 검색하면 `f.EventData.<이름>` 으로 만든다(`aliasPath`) — 이름을 보내는 에이전트의 PC 도 같이 맞는다.
  4. 공통 필드 username 은 이름으로 고른다. 그룹 구성원 변경(4728·4732·4756 등)은 TargetUserName 이 그룹 이름이라 바꾼 사람(SubjectUserName).
  5. 시험·시뮬레이터는 실제 에이전트 모양을 쓴다: `tests/fixtures/winevtlog/agent-fb4.0.14.jsonl`(윈도 CI 실측),
     `tools/simulate.py` 의 기본값은 StringInserts 만(`--event-data` 로 이름을 보내는 에이전트 흉내).
     윈도 CI(`tools/ci/capture_winlog.ps1`)가 매번 실제 이벤트를 받아 고정 자료와 모양(배열 길이·값의 형)을 비교한다.
- **이유:** 이미 설치된 사이트의 `alerts.yaml`·대시보드·사람이 쓴 검색이 고치지 않고 동작한다. Sigma 등 이름 기반 규칙을 들여올 바탕이 된다.
  위치 번호로 규칙을 고치는 안(`f.StringInserts.10`)은 버전마다 위치가 바뀌고(4624 v3) 사람이 읽을 수 없어 기각.
- **대가:** 템플릿이 있는 Windows 이벤트의 원본이 커진다 — 저장 크기(압축 포함) +6~39%(개발 DB 실측, 메시지가 길수록 작음).
  에이전트를 Fluent Bit 5.1(`event_data_as_map`)로 올리고 `string_inserts` 를 끄면 중복이 사라진다(로드맵). 템플릿은 손으로 늘린다
  (윈도 CI 의 실측 레코드로 길이를 확인). 같은 이름이 두 경로에 있어 필드 탐색에는 `winevtlog.EventData.*` 로 보인다(설명은 같음).
- **대안:** 조회할 때 이벤트 ID 별 위치로 바꾸는 SQL(CASE) — 저장은 늘지 않지만 같은 표를 SQL·Python·JS 세 곳에 두어야 하고
  상세·필드 탐색에 이름이 보이지 않아 기각. 에이전트를 지금 5.1 로 올리기 — 이미 설치된 4.0 PC 는 그대로 남아 서버 쪽이 어차피 필요.

## ADR-039 에이전트 하트비트는 전용 출력으로 보내고 2번 재시도 후 버린다 (에이전트 메모리)
- **상태:** 채택 (2026-10-29, ADR-027 의 에이전트 부분 보강). 에이전트 설정 Windows 0.4.1 · Linux 0.2.1.
- **배경:** 에이전트를 설치한 PC 에서 메모리를 많이 쓴다는 보고. Fluent Bit 4.0.14 소스로 확인한 원인:
  - 하트비트(dummy) 입력은 메모리 저장인데 `mem_buf_limit` 이 없어 상한이 없다. `storage.max_chunks_up` 은 filesystem 입력에만 걸린다.
  - 하트비트마다 새 조각이 생기고, 메모리 조각은 내용(약 100B)과 상관없이 **256KB 를 미리 잡는다**(`FLB_INPUT_CHUNK_SIZE`).
  - 하트비트가 로그와 같은 출력(`retry_limit: no_limits`)으로 가서, 서버에 못 보내는 동안(서버 중단·포트 막힘·키 틀림·TLS 오류)
    조각이 버려지지 않고 쌓인다. 30초마다 1개 → **장애 하루에 약 720MB**, 작업 수 상한(16384)까지 약 4GB. Windows 는 힙이 바로 잡는다.
  - 오래된 하트비트는 쓸모가 없다: 서버는 하트비트를 **받은 시각**으로 `last_heartbeat_at` 을 적는다(repository.py).
- **결정:**
  1. 하트비트 전용 http 출력(`match: heartbeat`, `retry_limit: 2`). 로그 출력은 `match_regex: '^(?!heartbeat$).*'` —
     허용 목록이 아니라 제외 정규식이라, 새 입력 tag 를 추가해도 버리지 않는 로그 출력으로 간다.
  2. 하트비트 입력에 `storage.type: memory` + `mem_buf_limit: 64K`(안전장치. 내용 바이트를 세므로 이것만으로는 못 막는다).
  3. `storage.max_chunks_up` 16 → 8, `storage.backlog.mem_limit` 16M → 8M, 출력 `workers: 1`(기본 2). 디스크에 더 남을 뿐 버리지 않는다.
  4. 두 출력 모두 TLS 블록을 둔다(설치 스크립트가 모든 `@@TLS` 블록을 켠다). `render_agent_configs.py` 가 http 출력 **전부**의 TLS,
     그리고 '재시도 제한 출력은 heartbeat 만, 로그 출력은 heartbeat 를 빼고 모든 로그 tag' 를 정적으로 검사한다.
  5. 윈도 CI(`tools/ci/agent_memory.py`)가 실제 Fluent Bit 로 서버 없이 2분(하트비트 1초) → 받는 쪽을 띄워 본다:
     옛 설정(0.4.0, `tools/ci/fixtures/windows-agent-0.4.0.yaml`) 대비 Private Bytes 증가가 절반 이하, 장애 중에 쓴 로그는 도착,
     장애 중 하트비트는 대부분 버려짐.
  6. PC 에서 잴 도구 `agent/windows/check-memory.ps1`(설치 묶음에 포함): Private Bytes·핸들·버퍼 크기를 CSV 로 남기고 판단을 출력.
- **기각:**
  - `storage.pause_on_chunks_overlimit: on` — 장애 중 재시도 조각이 상한을 채워 winevtlog 가 장애 내내 멈추고 디스크 버퍼에 쓰지 않는다.
    Security 로그(클라이언트 기본 20MB, 덮어쓰기)가 돌면 영구 유실. 원본 보존 원칙에 어긋난다.
  - 로그 출력의 `retry_limit` 을 유한값으로 — 4.0 에는 DLQ 가 없어 버려진다.
  - `read_limit_per_cycle` 축소·`flush` 늘리기 — 메모리를 줄이지 못한다(조각은 읽은 양과 상관없이 2MB 단위, flush 를 늘리면 조각이 더 오래 메모리에 남음).
  - Fluent Bit 4.2.8/5.1 로 올리기(winevtlog 렌더 실패 경로 누수·이중 해제 수정) — 렌더 실패가 드물고(로그에 'EvtRender failed') 실제 원인으로
    확인되지 않았다. 레코드 모양·서버 수신기 계열이 바뀌는 큰 변경이라 측정 결과를 보고 결정한다(BACKLOG B-33).
- **대가:** 서버가 돌아온 직후 PC 가 '온라인'이 되기까지 다음 하트비트(최대 30초)를 기다린다. 출력이 둘이라 30초마다 HTTP 요청이 하나 는다(작음).
  이미 설치된 PC 는 다시 설치해야 바뀐다(설치 묶음을 다시 받아 `install.cmd` — 기존 위치 기록 db 는 그대로라 유실·중복 없음).

## ADR-040 기록 종류별 보관기간, 보관 파일에 공통 필드 (형식 v2)
- **상태:** 채택 (2026-10-29, ADR-016 보완). 벤치마킹 조사(국내 법령·상용 제품 묶음)에서 드러난 두 결함을 고침.
- **배경:**
  - `WLM_RETENTION_DAYS` 하나로 로그 보관 파일·알림 이력·감사로그·점검 보고서를 같은 날 지웠다. 이 시스템의 권한 부여·변경·말소 기록
    (`user.*`·`user_group.*`)이 1년 만에 사라지는데, 개인정보의 안전성 확보조치 기준 제5조는 3년 보관을 요구한다.
  - 보관 파일(`archive.COLUMNS`)에 마이그레이션 007 의 `category`·`username`·`src_ip` 가 빠져 있었다. 보관했다가 복원한 달에서는
    `user:`·`ip:`·분류 검색이 0건이 되고(조사자가 '활동 없음'으로 오판), 분류로 범위를 정한 사용자에게는 보이지 않았다.
- **결정:**
  1. 보관기간을 기록 종류별로 나눈다: 로그 `WLM_RETENTION_DAYS`(그대로), 알림 `WLM_ALERT_RETENTION_DAYS`(비우면 로그와 같음),
     감사로그 `WLM_AUDIT_RETENTION_DAYS`(기본 1095), 점검 보고서 `WLM_REPORT_RETENTION_DAYS`(기본 1095).
     감사로그는 접두어별로 나누지 않고 전체를 3년 둔다 — 행이 작아 부담이 없고, 어떤 동작이 '권한 변경'인지 가르다 틀리면 되돌릴 수 없다.
  2. 법정 최소(접속기록 365, 권한 기록 1095)보다 짧으면 기동 로그 경고·로그 보관 화면 빨간 줄·점검 보고서 '점검 필요'.
     민감정보 처리 시스템의 접속기록 2년(제8조)은 어떤 로그가 해당하는지 사이트가 판단하므로 안내만 한다(기본값은 바꾸지 않음).
  3. 보관 파일 형식 v2 는 공통 필드를 넣는다. v1 을 복원하면 원본(+ 서버가 덧붙인 `raw.<소스>`)에서 다시 구한다
     — `normalizers.derive_common`. 정규화기를 다시 돌리지 않는 것은 IIS 열 순서(요청 문맥)·MSSQL 짝(메모리) 없이도
     저장 당시와 같은 값을 얻기 위해서다(모든 소스에 대해 '정규화 값 = 다시 구한 값' 왕복 시험). 복원 감사로그에 다시 구한 행 수.
  4. `events` 의 열과 `archive.COLUMNS` 가 같은지 시험이 본다 — 열을 더하면 보관 파일에도.
- **이유:** 둘 다 '된다고 말하는 것'이 틀린 부분이고, 첫 운영 설치(B-25) 전에 고치면 v1 보관 파일이나 1년 만의 감사로그 파기가 운영에
  한 번도 생기지 않는다. 지운 감사로그는 되돌릴 수 없다.
- **보완 (벤치마킹 검토):**
  - 사이트 표식 `WLM_SENSITIVE_ACCESS_LOG=on`(기본 off) — 진료정보 처리 시스템의 접속기록을 받는 설치면 로그 보관 경고 기준이
    730일이 된다. 기본값(365)은 그대로 두고 경고만 바꾼다: 어떤 설치가 해당하는지는 사이트가 판단하는데, 안내 문구만으로는
    1년으로 둔 채 넘어가도 아무도 알려 주지 않았다(경고 3곳 — 기동 로그·화면·점검 보고서 — 이 같은 함수 `retention_warnings`).
  - v1 보관 파일을 복원할 때 ADR-038 이전의 Windows 이벤트에는 `win_templates` 로 `raw.winevtlog.EventData` 이름을 덧붙인다.
    원본 키는 건드리지 않는다(원본 보존). 이름이 없으면 복원한 달에서 `f.EventData.LogonType:10` 같은 기본 규칙·대시보드 조건이 0건이었다.
- **대가:** 감사로그·보고서가 3년 쌓인다(행이 작아 수십 MB 수준). 업그레이드하면 기본값이 3년으로 늘어나므로, 1년보다 오래된 감사로그가
  이미 지워진 사이트는 그만큼 남지 않는다(되돌릴 수 없음).
- **대안:** 감사로그를 동작 접두어별로 다른 기간 — 분류 실수의 대가가 커서 기각. 기본 로그 보관을 730 으로 — 접속기록 해당 여부는 사이트
  판단이고 저장 공간이 두 배라 안내로 대신.

## ADR-041 알림 규칙의 서로 다른 값 수 (`distinct`)
- **상태:** 채택 (2026-10-29). 벤치마킹 조사(Elastic threshold cardinality, Sigma value_count, Wazuh different_field, DeepBlueCLI)의 공통 결론.
- **배경:** 규칙은 건수(`count(*) GROUP BY` 키 하나)만 셌다. 한 IP 가 계정 30개에 1~2번씩 시도하는 패스워드 스프레이는 IP 당 20건 기준에
  걸리지 않고, 기준을 낮추면 공용 PC·교대 근무의 오타가 오탐이 된다. '한 계정이 짧은 시간에 서버 여러 대에 원격 로그온'은 표현할 수 없었다.
- **결정:**
  1. 규칙에 `distinct: { field, min }` — `group_by` 묶음마다 `count(DISTINCT field) >= min` 일 때만(건수 기준 `threshold` 와 함께).
     `field` 는 `group_by` 와 같은 키(`user`·`host`·`ip`…)나 `f.<경로>`(EventData 별칭 포함, ADR-038), `min` ≥ 2.
  2. **값이 없는(NULL) 이벤트는 서로 다른 값으로 세지 않는다**(PostgreSQL `count(DISTINCT)` 그대로) — 사용자를 알 수 없는 로그온 실패
     10건은 '서로 다른 계정 10개'가 아니다. 건수(`threshold`)에는 들어간다.
  3. `window` ≤ 1d — 엔진이 30초마다 다시 세므로 긴 구간의 `count(DISTINCT)` 를 막는다. 묶음 순서는 서로 다른 수가 많은 것부터.
  3-1. (벤치마킹 검토 반영) **묶음 값(`group_by`)이 없는 이벤트는 알림 후보·미리보기에서 뺀다** — 건수 규칙도 마찬가지.
     IP 없는 대화형·잠금 해제 로그온 실패가 모든 PC 에서 '빈 출발지' 하나로 합쳐져, 출시한 1000006(무차별 대입, IP 기준)이
     출발지·표본 없이 울렸고(개발 DB 의 후보 1위가 이 빈 묶음 3,610건), distinct 를 더하면 병원 전체의 오타가 '서로 다른 계정 n개'의
     패스워드 스프레이가 된다. `group_by: none` 은 그대로 전체를 합산한다.
  4. 알림 본문·저장된 내용에 서로 다른 수와 앞의 값 10개(`array_agg(DISTINCT … ORDER BY …)`). 건수 규칙의 본문은 예전과 같다(웹훅 json 포함).
  5. 기본 규칙 3개: 패스워드 스프레이(4625·4771, IP 마다 계정 10), 없는 계정으로 로그온 시도(SubStatus 0xc0000064, IP 마다 계정 4),
     한 계정이 여러 서버에 원격 데스크톱(4624 LogonType 10, 계정마다 PC 3, 30분). 실제 에이전트 모양 레코드로 맞는 경우·안 맞는 경우·
     경계(9/10)·NULL 을 통합 시험한다.
- **이유:** SQL 한 줄 확장으로 가장 큰 오탐원(건수 규칙)을 줄이고, 대량 출력·정보주체 수·Kerberoasting·Sigma value_count 의 바탕이 된다.
- **대가:** 서로 다른 값 수는 건수보다 비싸다(구간 상한으로 막음). 서비스 계정·관리 PC 는 예외 기능(로드맵) 전까지 검색 문장의 `-user:` 로 뺀다.
  여러 키로 묶기(`group_by` 목록)는 다음 단계.
- **대안:** Wazuh 식 same/different_field(직전 이벤트와 비교 — 진짜 서로 다른 수가 아님), 엔진 메모리에 집합 유지(워커 1개·재시작 때 잃음) — 기각.

## ADR-042 이 시스템의 접속기록: 정보주체 기록, 개인정보 통계 조회, 실패하면 거부(fail-closed), 내려받기 사유
- **상태:** 채택 (2026-10-29). 벤치마킹 조사(국내 접속기록 관리 제품·안전성 확보조치 기준)와 적대적 검토가 범위를 줄여 정함.
- **배경:** 이 서버는 병원 전체의 로그온·접속 기록을 모은다 — 그 자체가 개인정보처리시스템이다. 검색 조건(`events.search`)과 상세 조회(`events.view`)는
  남겼지만, 상세 기록에는 PC·이벤트 ID 만 있어 '누구의 기록을 봤는지'가 없었다. 사용자·IP 상위 값 목록(`/api/stats/top`)은 개인정보가 보이는데
  기록되지 않았다. `db.audit` 는 실패해도 본 작업을 막지 않아, 기록 없이 열람될 수 있었다. CSV 내려받기에는 사유가 없었다.
- **결정:**
  1. `events.view` 에 이벤트의 `username`·`src_ip`·`category`(정보주체)를 함께 남긴다.
  2. 상위 값 조회 중 사람·출발지가 보이는 것(`user`·`ip`, 무엇이든 될 수 있는 원본 필드 `f.`)을 `events.stats` 로 남긴다.
     대시보드 위젯이 같은 조건으로 몇 분마다 다시 부르므로 같은 사람·같은 조건은 10분에 한 번(기록에 성공한 뒤에만 셈).
  3. 검색·상세·개인정보 상위 값·CSV 내려받기는 `db.audit(required=True)` — 기록하지 못하면 `AuditError` → **503**, 결과를 내주지 않는다.
     설정 변경 등 다른 기록은 지금처럼 실패해도 본 작업을 막지 않는다(로그인 불가 같은 연쇄 장애를 피함).
  4. 감사로그·알림 이력 CSV 는 내려받는 사유(2~200자)를 받아 기록에 남긴다(없으면 400). 화면은 사유 창 → 받아서 저장(주소로 이동하지 않아
     거절 사유를 화면에서 보임).
- **이유:** 개인정보처리시스템 접속기록은 '누가·언제·어디서·무엇을(정보주체)·어떤 업무로' 가 핵심이다. 기록을 못 남겨도 열람되면 기록의 의미가 없다.
  법 조항 번호(2025 개정 고시의 출력·복사 조항 등)는 원문으로 확인한 뒤 ISMS.md 에 적는다 — 이 결정은 조항과 무관하게 맞는 방향이다.
- **대가:** DB 가 잠깐 불안정하면 검색도 503 이 된다(어차피 같은 DB). 감사로그가 늘어난다(통계는 10분 묶음으로 줄임). 사유는 사용자가 적는 대로라
  내용을 강제하지 못한다(점검 때 사유를 함께 본다).
- **대안:** 모든 통계 조회 기록 — 대시보드가 기록을 쏟아내 기각. 사유 없이 행 수만 — 출력·복사 통제의 '왜'가 빠져 기각.
- **보완 (2026-11-01, B-38):** 남은 개인정보 조회도 같은 방식(`app/accesslog.record` — 같은 사람·행위·조건은 10분에 한 번, 기록 실패면 503)으로 —
  실시간 스트림 열기(`events.live`), 사용자·IP·원본 필드로 나눈 시계열(`events.stats`), 점검 보고서 열람·인쇄(`report.view`·`report.print`,
  화면의 요약과 iframe 은 한 번의 열람), 감사로그 목록(`audit.list` — 직원 계정·IP). 인쇄용으로 연 보고서에는 맨 위·아래에 출력자·시각·IP 를 찍는다
  (출력물이 누구 것인지 — 출력·복사 안전조치). 점검 보고서에 '개인정보 내려받기' 절: 기간의 내려받기 수와 사유가 뜻이 없을 만큼 짧은 것(`csvexport.weak_reason`,
  공백 뺀 4글자 미만·한 글자 반복·글자 없음 — '월간 점검'은 통과)을 표와 '점검 필요'로.


## ADR-043 알림 설정 판본과 '탐지 약화' 알림 (감시자 감시)
- **상태:** 채택 (2026-10-29). 벤치마킹 검토 NEW-M2.
- **배경:** `config/alerts.yaml` 을 서버에서 직접 고치면 엔진이 mtime 을 보고 로그 한 줄만 남긴 채 바로 적용했다 — 감사로그·해시·차이가
  없었다. 화면에서 규칙을 끄거나 기준을 올리면 감사로그에는 남지만, 그 규칙의 알림을 받던 사람은 알 수 없었다(알림이 오지 않을 뿐).
  '모든 규칙' 무음도 마찬가지다. 파일이 깨진 채로 서버를 다시 시작하면 규칙 0개로 돌았다(화면에 오류 한 줄).
- **결정:**
  1. 적용한 설정을 판본 표 `alert_config_versions`(마이그레이션 015)에 남긴다 — 방법(`ui` 화면 · `file` 실행 중 파일 수정 ·
     `startup` 꺼져 있는 동안의 수정), 누가(화면이면 사용자, 파일이면 `system`), 내용·해시, 직전 판본과의 차이, 약해졌는지.
     감사로그처럼 추가만 하고(트리거), 보관기간 정리는 감사로그와 같이 하되 마지막 판본은 남긴다. 감사로그에도 `alerts.config.apply`.
  2. 서버가 시작되면 DB 의 마지막 판본을 기준으로 삼는다 — 꺼져 있는 동안 고친 것도 `startup` 판본으로 드러난다. 처음 설치면 기준 판본만.
  3. 탐지를 약하게 하는 변경(규칙 삭제·끔, 건수 기준↑, 집계 기간↓, 심각도↓, 받는 곳 뺌, 조건·묶음 기준 바꿈, 서로 다른 값 조건 추가·↑,
     재알림 간격↑, 끊김 판정↑, 평가 주기↑ — 확신할 수 없는 변경은 약해진 것으로 본다)이면 내장 규칙 **'알림 설정 변경'** 으로 알린다.
     받는 곳은 **바뀌기 전** 설정에서 그 규칙들의 받는 곳 — 바꾼 사람이 받는 곳까지 지워도 받던 사람이 안다. 심각도는 걸린 규칙 중 가장 높은 것.
     꺼져 있던 규칙은 무엇을 바꿔도 약화가 아니고, 받는 곳·심각도에도 넣지 않는다.
     - 다시 켜거나 다시 추가한 규칙은 **마지막으로 켜져 있던 판본**과 비교한다 — 끄고(알림) → 꺼진 채 고치고 → 켜면 바로 앞 판본은
       꺼진 모양이라 약화가 보이지 않았다(검토에서 재현).
     - 무음이 걸린 이름으로 바꾸거나 추가하는 것도 약화(무음·재알림 간격은 이름이 열쇠). sid 가 새로 붙은 같은 이름은 같은 규칙(삭제+추가 아님).
       PC 목록은 집합으로 비교(순서·추가는 약화 아님). 이전 판본을 읽을 수 없으면 새 판본의 켜진 규칙들의 받는 곳으로.
  4. 넓은 무음(모든 규칙·모든 대상, 또는 지금부터 24시간 넘게 덮음)도 같은 알림. 길이는 같거나 더 넓은 범위의 무음과 이어 붙인 구간으로
     잰다 — 24시간짜리를 이어 붙이면 한 달을 막을 수 있었다. 이 알림은 무음으로 막지 않는다 — 무음을 건 뒤 규칙을 끄면 아무도 모른다.
  5. 시작할 때 파일이 깨졌거나 **없으면** 마지막 판본으로 감시를 계속하고(화면 오류에 판본 번호), 깨진 파일은 내용마다 한 번
     `alerts.config.invalid` + 알림(UTF-8 이 아닌 파일·검증이 예상하지 못한 모양도 — 예외가 새면 오류도 기록도 없이 옛 설정으로 돌았다).
     파일이 깨졌거나 없는 동안에는 규칙 하나만 고치는 저장을 409 로 막는다(빈 틀에 규칙 하나를 더해 쓰면 나머지가 사라진다) — '고급 편집'의
     전체 저장으로 고친다.
  6. 점검 보고서 '알림 처리'에 기간 안의 설정 변경·넓은 무음, '점검 필요'에 약해진 변경·화면을 거치지 않은 변경·넓은 무음·설정 파일 오류.
  7. 화면 저장은 쓰기 전에 아직 기록하지 않은 파일 직접 수정부터 `file` 판본으로 남긴다 — 서버에서 고친 것이 화면 사용자 이름으로 섞이지 않게.
     그것을 남기지 못하면 저장을 503 으로 거절한다. 판본 비교·기록은 하나씩(잠금), 화면이 규칙 목록을 읽을 때도 바로 기록한다.
     파일 변경은 수정 시각만이 아니라 (mtime, ctime, 크기, inode)로 알아챈다 — `touch -r` 로 시각을 되돌린 수정도 보인다.
     판본은 남겼는데 감사로그·알림이 실패하면 다음 주기에 다시 한다(판본을 두 번 남기지 않음).
- **이유:** 1~2명이 운영하는 병원에서 '탐지가 꺼진 줄 모르는 것'이 가장 비싼 실패다. 판본 표는 변경 관리(ISMS 2.9.1)·관리자 행위 점검(2.9.5)의
  증적이고, 깨진 파일 대비도 같은 표로 해결된다.
- **대가:** 정상적인 조정(오탐 줄이려 기준 올림)도 알림이 간다 — 의도된 것(누가 왜 바꿨는지 받던 사람이 알아야 함). 판본마다 파일 전체(수십 KB)를 저장한다.
  수신 그룹의 구성원·채널 설정(환경설정 화면)을 바꾸는 것은 아직 판본·약화 알림 대상이 아니다(감사로그에만, 후속 — 바꾼 사람과 무관한
  받는 곳 `fallback_notify` 는 B-34). 약화 알림을 보내는 동안 화면 저장 요청이 기다린다(받는 곳마다 최대 30초, 전송 분리 B-34 에서 해소).
- **2단계 (2026-10-30, B-36):** 받는 곳 쪽의 약화와 관리 작업도 내장 '관리 작업 알림'(무음 불가, `alerts/adminwatch.py`)으로 알린다.
  - 받는 곳 약화: 수신자·수신 그룹·외부 연동·메일 서버 저장 앞뒤로 받는 곳을 비교해, 규칙·대체 경로가 쓰는 곳에서 받는 사람이 빠짐·꺼짐·지워짐·
    최소 수준 올림·보내는 곳 바뀜이면. 받는 곳 = 대체 경로 + 켜진 규칙의 받는 곳 − 이번에 약해진 곳(그리로는 안 간다).
  - 관리 권한 부여: 관리자 계정 생성·관리자로 바꿈, 사용자 그룹에 관리 권한(`alerts.manage`·`settings.manage`·`audit.view`·`agents.deploy`)을
    주거나 그런 그룹에 사람을 넣음. 보관 파일 복원(지난 로그를 다시 검색할 수 있게 됨).
  - 점검 보고서 '관리 작업 요약'(권한·계정, 알림 규칙·무음, 알림 받는 곳, 보관·복원, 내려받기 — 0건도 보인다) + 바로 알린 관리 작업 수.
- **대안:** 감사 행을 이벤트(`source=wlm`)로 넣어 일반 규칙으로 알림 — 그 규칙 자체를 끄면 끝이라 기각(내장 알림은 파일로 끌 수 없음).
  파일 해시 체인·서명 — 서버 셸 권한자는 DB 도 고칠 수 있어 효과에 비해 무겁다(외부 복제 B-17 로).

## ADR-044 수집 견고성: 문제 레코드 격리, 수집 거절 장부
- **상태:** 채택 (2026-10-29). 벤치마킹 검토 NEW-M1 나머지(BACKLOG B-40).
- **배경:** NUL 은 aeb38bf 에서 막았지만, 같은 부류가 남아 있었다. 정규화기 예외 하나, INTEGER 범위를 넘는 EventID 하나, 짝 없는
  서로게이트(`\ud800`) 하나, 값에 글자 그대로 든 `\u0000`(옛 `_json` 이 NUL 로 착각해 지워 JSON 이 깨짐) 하나가 요청 전체를 500 으로
  만들었다(모두 재현). 에이전트는 같은 청크를 끝없이 다시 보내고 Fluent Bit 4.0 에는 DLQ 가 없어(ADR-039) 그 PC(수집기면 모든 장비)의
  로그가 멈춘다. 서버가 거절한 요청(옛 API 키 등)은 어디에도 남지 않아 그 PC 는 그냥 '오프라인'으로만 보였다.
- **결정:**
  1. 정규화는 레코드 단위로 가둔다(`normalize_safely`): 실패한 레코드는 일반 로그로 저장하고 `raw._ingest.error` 를 덧붙인다.
  2. **알려진 값 오류는 미리 막는다:** 칸 범위를 넘는 EventID·수준은 비우고(원본은 raw 에), JSON 의 NaN·Infinity 는 글자로, 짝 없는
     서로게이트는 U+FFFD 로(본문에 그 이스케이프가 있을 때만, 재귀 없이 훑음 — 깊은 JSON 에서 RecursionError), `_json` 은 홀수 개 역슬래시
     뒤의 `\u0000` 만 지운다. UTC 로 옮기면 범위를 벗어나는 시각(0001-01-01+09:00)은 다음 키·수신 시각으로.
  3. **모르는 값 오류는 격리한다:** 저장이 값 오류(`DataError`·`ProgramLimitExceeded`·`UnicodeError`)로 실패하면 **한 트랜잭션 안에서** 하트비트·
     IIS 머리줄을 쓰고, 이벤트를 반씩 나눠 저장점(savepoint)마다 저장하며 실패하는 레코드만 `ingest_quarantine`(마이그레이션 016)에 원본
     JSON(ASCII 이스케이프, 64KB, 정보주체 열 포함)으로 격리한 뒤 한 번에 커밋한다. 응답은 200 + `quarantined`. 중간에 연결·풀 오류로
     500 이 되면 모두 되돌린다 — 반쯤 커밋한 뒤 500 이면 에이전트가 청크째 다시 보내 앞부분이 두 번 저장됐다(검토에서 재현).
     실패한 시도가 요청당 256번을 넘으면 400 으로 거절한다 — 키를 가진 쪽이 값 오류 레코드만 보내 레코드 수에 비례해 DB 를 두드릴 수 없게.
  4. 수집 거절 장부 `ingest_rejections`: (보낸 IP, 상태, 사유, **정시**)마다 횟수·처음·마지막. 시간으로 나눠야 보고서가 그 기간의 거절을 센다
     (누적 한 줄이면 계속 거절되는 PC 가 보고서에서 빠졌다 — 검토에서 재현). 인증 전 요청이라 요청마다 DB 에 쓰지 않고 메모리에 모아
     30초마다(종료 때도) 쓴다. 서로 다른 줄은 2,000개까지, 넘치면 '그 밖의 IP' 한 줄로(DB 가 멈춰 되돌릴 때도). API 키는 바이트로 비교한다
     (ASCII 아닌 글자가 섞인 키가 500 '서버 오류'가 됐다). 보내는 도중 끊긴 요청은 499(보고서 '점검 필요'에는 넣지 않음).
  5. 수집 PC 화면(관리자)에 거절·격리 목록, 원본 열람은 관리자만 + 접속기록(실패하면 거부, ADR-042). 점검 보고서 '점검 필요'.
     격리 레코드·거절 장부는 로그 보관기간으로 정리.
- **이유:** '하나가 전체를 막는' 실패는 조용하고(서버는 500 로그 한 줄, PC 는 버퍼가 찰 때까지 재시도) 범위가 크다. 격리는 원본을 버리지 않으면서
  나머지를 살린다. 401 장부는 키 교체(ADR-036 운영 절차)의 마지막 확인 수단이다.
- **대가:** 반씩 나누는 동안 저장 시도가 여러 번(문제 k건이면 약 2k·log n, 요청당 상한 256). 격리된 레코드는 규칙·검색에 걸리지 않는다 —
  그래서 화면·보고서에 드러낸다. 나누는 동안 연결 하나를 쥔다.
- **대안:** 레코드마다 따로 저장(평소에도 수백 배 트랜잭션) — 기각. 실패한 요청 전체를 격리(나머지 로그까지 검색에서 빠짐) — 기각.
  요청 본문 해시로 중복 제거 — 다음 단계(B-40 P2).


## ADR-045 알림 엔진 자체 감시와 전송 분리
- **상태:** 채택 (2026-10-29). 벤치마킹 NEW-5·NEW-15(BACKLOG B-34 1단계). 설계는 두 안을 심사해 합쳤다(감시 스레드·시스템 알림은 2단계).
- **배경:**
  - 엔진이 평가 주기 안에서 알림을 보냈다(`fire` → 받는 곳마다 최대 30초). 메일 서버 하나가 멈추면 그동안 규칙 평가가 늦어졌고,
    실패분 재시도도 같은 주기에서 했다.
  - 보내는 중에 서버가 멈추면(배포·OOM) 그 행은 `pending` 으로 영영 남았다 — 아무 코드도 `pending` 을 다시 보내지 않았다.
  - 규칙 쿼리에는 시간 상한이 없었다(ADR-035 는 화면 조회만). 무거운 규칙 하나가 평가 전체를 멈출 수 있었다.
  - 알림 화면의 상태 띠는 설정 오류·마지막 오류가 비어 있으면 늘 초록이었다. 평가가 몇 시간째 멈춰도, 메일이 하루 종일 실패해도.
  - 기준을 넘은 묶음은 100개에서 조용히 잘렸다.
- **결정:**
  1. `alert_deliveries` 가 전송 대기열이다(마이그레이션 017: `next_attempt_at`·`claimed_at`). 엔진의 `fire()` 는 행을 넣고 전송기를 깨울
     뿐 네트워크를 쓰지 않는다. 전송기(`alerts/dispatcher.py`, advisory lock 727_004)가 보낼 차례인 행을 하나씩 잡아(`claimed_at`) 보낸다.
     받는 곳마다 한 줄(lane), 한꺼번에 4곳까지, 같은 곳으로는 한 번에 하나. 보내는 동안 DB 연결을 쥐지 않는다. 심각한 것부터.
  2. 재시도 간격은 1·5·15·60분, 다섯 번째 실패면 `gave_up` (ADR-011 그대로). 받는 곳 자체가 안 될 때(시간 초과·연결 실패·5xx·429)는 그 곳의
     다른 대기 행을 한 번에 실패로 넘긴다 — 같은 곳에 30초씩 줄줄이 기다리지 않게. 다른 받는 곳과 평가는 영향을 받지 않는다.
  3. 서버가 보내는 도중 멈춘 행은 다음에 잠금을 잡을 때 풀어(한 번 시도로 셈) 다시 보낸다 — 같은 알림을 두 번 받을 수 있다(at-least-once).
     하루가 지난 대기 행은 보내지 않는다(`gave_up`, '하루가 지나'). 결과는 `claimed_at` 이 그대로일 때만 쓴다(늦게 온 결과는 버림).
  4. 테스트 발송은 대기열을 거치지 않고, 성공하면 그 곳의 실패분을 바로 보낼 차례로 돌린다(고친 뒤 한 시간 기다리지 않게).
  5. 규칙 쿼리에 시간 상한 `WLM_ALERT_RULE_TIMEOUT_SEC`(기본 20초). 화면 조회 자리(SEARCH_SLOTS)는 쓰지 않는다(`db.background_time_limit`).
     넘기거나 실패하면 그 규칙만 '시간 초과·오류'로 남기고 다음 규칙으로. 표본 조회가 넘치면 표본 없이 알린다.
  6. 규칙마다 마지막 평가(`RuleRun`: 시각·걸린 시간·후보 수·잘림·오류·연속 오류·평가 공백)를 메모리에 둔다(워커 1개, ADR-006).
     기준을 넘은 묶음이 100개를 넘으면 '일부만'. 앞 평가가 본 구간과 이번 구간 사이에 틈이 있으면 '평가 공백'.
     다음 주기는 시작 시각 기준(오래 걸린 주기 뒤에 주기 하나를 통째로 더 쉬지 않게).
  7. 상태 판단은 한 곳(`alerts/health.py`, 순수 함수): 평가 멈춤(나아간 시각이 max(3×주기, 2×상한+30초, 120초)보다 오래됨)·느림,
     전송 멈춤·꺼짐, 밀림(보낼 차례가 5분 넘음), 받는 곳 실패 중, 규칙이 쓰는 모든 받는 곳 15분 넘게 실패, 24시간 안 재시도 중단, 규칙 오류·
     시간 초과·일부만·느림·평가 공백. 알림 화면 상태 띠·규칙 '평가' 칸·알림 대상 줄, 로그인 없는 `GET /healthz/alerts`(수·코드만,
     down 이면 503, `?strict=1` 이면 warn 도 503, 수집 포트에서는 404), 점검 보고서 '점검 필요'가 같이 쓴다.
- **이유:** '알림이 안 오는 것'은 조용하다. 받는 쪽은 아무 일도 없다고 믿는다. 평가와 전송을 나눠 서로 막지 않게 하고, 멈춤을 사람이
  보는 세 곳(화면·외부 감시·아침 보고서)에 드러낸다. 아침 점검 보고서가 오지 않는 것도 신호다(보고서는 자기 경로로 보낸다).
- **대가:** 배포·재시작 때 보내던 알림이 두 번 갈 수 있다(문서화). 규칙 상태는 메모리라 다시 시작하면 한 주기 동안 '평가 전'.
  `pending` 은 이제 '전송 대기'(곧 보냄)다.
- **대안:** 전송 상태 'sending' 추가·임대 시각·순번(설계 A) — 상태 값이 늘고 되돌리기가 어려워 기각(`claimed_at` 하나로 충분).
  규칙 상태 표 — 화면·보고서에는 메모리로 충분하고, 오래 남길 것(멈춤·공백)은 2단계에서 감사로그로.
  규칙별 시간 상한을 alerts.yaml 에 — 서버 보호는 서버 관리자의 설정이라 환경변수로(`WLM_SEARCH_TIMEOUT_SEC` 와 같게).
- **보완 (적대적 검토, 2026-10-30):**
  - 받는 곳 장애로 **미룬 행은 시도로 세지 않는다** — 받는 곳이 알림 하나의 본문만 500 으로 거절하면, 보지도 않은 다른 알림까지 같은 일정으로
    다섯 번 만에 버려졌다(재현). 잡는 순서는 덜 실패한 것부터(그다음 심각도). SMTP 의 본문·받는 사람 거절(554 등)은 그 메일만의 문제.
  - 잡은 뒤 결과를 쓰다 실패하면 풀어 두고, 10분 넘게 잡힌 행은 정리 때 푼다(줄이 죽어도 '보내는 중'으로 남지 않게). 오류 문구의 NUL 은 지운다
    (받는 쪽 응답의 NUL 하나로 결과를 못 써 같은 행을 끝없이 다시 잡았다).
  - 동시 자리는 한 건 보낼 때마다 잡고 놓는다(대기열이 긴 받는 곳 넷이 다섯째를 몇 분씩 막지 않게). 만들 수 없는 받는 곳(지워짐·꺼짐·복호화
    실패)도 '실패 중'으로 — 모든 받는 곳이 이러면 '알림 멈춤'.
  - 기준을 넘은 묶음 중 재알림 간격에 든 것은 SQL 에서 미리 뺀다(엔진의 판단과 같은 조건, 해결된 알림·끝난 무음은 남김) — 빼지 않으면 늘 앞서는
    100개가 자리를 차지해 101번째부터는 영영 알리지 못했다.
  - 상태: 주기 전체가 실패하면(설정 파일을 못 읽음·DB 연결 거부) '평가 실패'(나쁨) — 나아간 시각은 잠금을 잡은 뒤부터 찍는다. 꺼졌다 켜진 규칙은
    평가 공백으로 치지 않고, 공백은 쿼리를 낸 시각부터 잰다. 주기를 줄인 직후에는 실제로 쉬는 옛 주기로 '멈춤'을 판단한다.
- **2단계 (2026-10-30):** 감시 작업(`alerts/watchdog.py`, 30초마다):
  - 평가가 멈추면 감사로그 `alerts.health.engine_stall`, 평가 작업 다시 시작(10분에 한 번까지, `engine_restart`), 내장 알림 '알림 엔진 멈춤'(심각).
    다시 나아가면 `engine_resume`(멈춘 시간·평가 공백이 생긴 규칙).
  - 전송기가 멈추면 다시 시작(`dispatcher_restart`) — 알림은 보내지 않는다(그것을 보낼 길이 멈춘 것).
  - 받는 곳이 15분 넘게 실패하면 '알림 전송 실패'를 **그 곳을 뺀** 받는 곳으로(`target_down`·`target_recovered`). 규칙이 세 번 잇달아 실패하면
    '알림 규칙 동작 안 함'(`rule_error`·`rule_recovered`). 평가 공백은 `rule_gap`.
  - 받는 곳 = `settings.fallback_notify`(alerts.yaml), 비우면 점검 보고서 받는 곳. 어디에도 없으면 상태에 '받을 곳 없음'(확인 필요).
    `fallback_notify` 에서 받는 곳을 빼는 것도 탐지 약화(ADR-043). 같은 문제는 한 시간에 한 번(해결하면 바로 다시).
  - 이 알림들은 무음으로 막을 수 있다(메일 서버 점검처럼 예정된 일) — 설정 변경 알림은 여전히 막을 수 없다. 조회 범위가 있는 사용자에게는 보이지 않는다.
  - 남은 것: 주간 시험 전송, Oracle 생존 신호 행.

- **보완 (2026-10-31, BACKLOG B-34 남은 것) — 정기 시험 전송과 Oracle 생존 신호:**
  - 매주 정해진 요일·시각(`WLM_ALERT_TEST_WEEKDAY`·`TIME`, 기본 월 09:00) 뒤 첫 감시 때 쓰는 받는 곳(켜진 규칙 + 대체 경로)마다 시험 알림 한 건.
    '그 시각 뒤로 시험한 적 없음'으로 판단해 서버가 그때 꺼져 있었어도 다음 감시 때 한다. 화면의 테스트 발송·연동 시험도 시험으로 친다(감사로그가 정본 —
    다시 시작해도 같은 주에 두 번 보내지 않는다). Oracle 은 dry_run(실행 후 되돌림) — 매주 사내 알림 표에 시험 행이 쌓이지 않게.
  - 실패하면 그 곳을 '보내지 못하는 중'으로 둔다 → 기존 감시가 15분 뒤 '알림 전송 실패'를 다른 곳으로 보낸다(새 내장 알림을 만들지 않음). 다시 시작해
    메모리 상태가 사라져도 마지막 시험이 실패한 곳은 감사로그로 `test_failed` 가 남는다(그 뒤 성공한 시험이 있으면 사라짐).
  - 메일 그룹은 실제로 메일을 보낸다 — SMTP 연결만 확인하면 비밀번호 만료·수신 거부를 놓친다. 받는 사람에게 매주 한 통이 늘지만 '알림 경로가 살아 있음'의
    증거다(Prometheus Watchdog 와 같은 생각). 싫으면 0 으로 끈다.
  - Oracle 생존 신호: 연동마다 선택 SQL, 1분마다(감시와 따로 도는 작업 — 30초 상한). 바인드는 `:at :status :version :problems` 만(알림 바인드와 섞지 않게
    저장 전에 거부). 서버 밖의 감시가 서버 전체의 정지를 잡는 유일한 길이다(병원에는 NMS 가 없는 경우가 많다). 실패·회복은 바뀔 때만 감사로그.
  - **적대적 검토 반영:** 되돌리는 시험의 키 중복(ORA-00001, 시험 알림 번호 0 이 이미 있는 표)을 성공으로, Oracle '연결 시험'은 시험으로 세지 않고
    SQL 시험 실행은 셈, 실패하면 1분 뒤 한 번 더, 시험 실패 뒤 실제 알림이 나가면 경고를 지움, Oracle 호출을 전용 스레드 풀로·생존 신호는 하나씩
    (asyncio 시간 초과는 스레드를 멈추지 못해 응답 없는 Oracle 에 1분마다 스레드가 쌓였고 기본 풀이 차면 로그인까지 막혔다 — 재현).
  - **대가:** 정기 시험은 감시 작업(=전송기가 켜진 프로세스)에서만 돈다. 여러 대면 각자 한다(같은 주에 감사로그를 보고 건너뛰지만 동시에 돌면 두 번 갈 수 있음).

## ADR-046 수집 완전성 1단계: 늘 오던 채널이 끊긴 것
- **상태:** 채택 (2026-10-30). 벤치마킹 NEW-6 ①(BACKLOG B-37 1단계).
- **배경:** 규칙 팩은 감사 정책(4625·4732·4698·4697·4104 등)이 켜져 있다고 가정한다. GPO 변경·부분 적용으로 한 PC 의 Security 수집만 끊겨도
  하트비트·System 로그는 계속 와서 '연락 끊김'(agent_silent)은 조용했고, 점검 보고서는 전체 0건·절반 이하만 봤다.
  '규칙은 켜져 있는데 데이터가 없는' 상태가 병원 PC 수백 대에서 가장 흔하고 조용한 실패다.
- **결정:**
  1. 수집 트랜잭션에서 (PC, 소스, 채널)마다 날짜(UTC)별 건수·처음·마지막 수신을 `agent_streams`(마이그레이션 018)에 더한다. 문장 하나(`unnest`)로 —
     줄마다 upsert 하면 PC 가 많은 묶음에서 수집이 13% 느려졌다(PERFORMANCE.md §2.5, 문장 하나로는 차이 없음). 35일 뒤 지운다.
  2. 끊김 = 지난 7일(오늘 제외) 중 5일 이상 온 채널이, PC 는 6시간 안에 다른 것을 보냈는데 max(6시간, 평소 간격 × 10)(3일 한도)보다 오래 조용함.
     평소 간격 = 그 기간의 날 수 / 건수. 하루 몇 건인 채널은 밤새 조용해도 끊김이 아니다. PC 자체가 끊긴 것은 빼서 '연락 끊김'과 겹치지 않게.
  3. 수집 PC 화면(조회 범위 반영)과 점검 보고서 '점검 필요'·수집 PC 절에 보인다.
- **이유:** 채널 단위의 '평소'가 있어야 끊김을 말할 수 있다. 이벤트 ID 단위는 줄이 수십 배라 규칙별 데이터 유무(2단계)에서 필요한 것만 본다.
- **대가:** 하루에 (PC, 소스, 채널)마다 한 줄. 5일 미만 쌓인 새 설치에서는 판단하지 않는다. 날짜는 UTC 라 표시 시간대 하루와 9시간 어긋난다(판단에는 영향 작음).
- **2단계 (2026-10-31) — 규칙별 데이터 유무와 채널 끊김 알림:**
  - **이벤트 ID 집계 `agent_events`(020):** (PC, 소스, 채널, 이벤트 ID)마다 한 줄(처음·마지막 수신), Windows 이벤트만. 수집 트랜잭션에서 문장 하나(unnest),
    마지막 수신은 한 시간에 한 번만 고친다(`WHERE last_at < EXCLUDED.last_at - 1 hour`) — 거의 모든 묶음이 쓰기 없이 지나간다. 문장 비용은 agent_streams 와
    같다(PERFORMANCE.md §2.6). 날짜별로 두지 않은 것은 '이 PC 가 이 이벤트를 보낸 적이 있나'만 필요해서다(줄 수 = PC × 이벤트 ID 종류). 90일 보이지 않으면 지운다.
  - **규칙이 필요로 하는 데이터는 조건에서 꺼낸다** (`alerts/coverage.py`, 따로 `requires` 키를 두지 않음 — 조건과 어긋날 수 있다): 소스·채널·이벤트 ID.
    수준·분류·메시지만 보는 규칙은 판단하지 않는다(모든 로그가 후보). 대상 PC = 7일 안에 살아 있고 그 소스를 보낸 PC(규칙의 PC 조건 반영).
    채널은 7일, 이벤트 ID 는 30일. **채널을 보내지 않는 PC 만 '빠짐'으로 경고**한다 — 같은 소스는 보내므로 수집 설정·감사 정책 문제일 가능성이 크다.
    이벤트 ID 는 드물 수 있어(계정 생성 등) 숫자만 보인다. 규칙 표 배지·툴팁(빠진 PC), 점검 보고서 '점검 필요'(채널마다 묶어). 10분 캐시.
    빠진 PC 이름이 있어 조회 범위가 있는 사용자에게는 보이지 않는다.
  - **규칙 종류 `stream_silent`:** 판단은 수집 PC 화면·보고서와 같은 `silent_streams`(규칙마다 기간을 두지 않음 — 화면과 알림이 다른 말을 하지 않게).
    `hosts`·`channels`(비우면 전부), 대상 이름 'PC · 채널'(조회 범위는 PC 부분으로 — `visibility.alert_host`), 끊긴 동안 한 번, 다시 들어오면 자동 해결이
    기본(payload 의 `stream` 으로 그 채널을 다시 본다). 기본 팩에 서버만 보는 '늘 오던 로그 끊김'. 좁히는 변경(PC·채널 빼기)은 탐지 약화.
  - **적대적 검토 반영:** 규칙과 같은 맞춤(PC·채널 정확히, * 는 글자 — 대소문자를 무시하면 'channel: security' 처럼 영영 맞지 않는 규칙이 '데이터 있음'),
    채널을 정하지 않은 규칙은 그 이벤트 ID 가 실제로 오는 채널로(기본 팩은 이벤트 ID 만 정해 경고가 한 번도 나지 않았다), 이벤트 ID 는 모든 소스(SQL Server·IIS)와
    소스 추정(그 ID 가 오는 소스), 채널이 조용한 시간은 PC 가 켜져 있던 동안만(`agents.up_since` — 주말에 꺼진 PC 를 월요일에 '끊김'으로), PC 점검 무음
    ('모든 규칙 · DB-01')이 'DB-01 · 채널' 에도, 채널 이름은 Windows 밖에서는 '소스/채널'(journald·syslog 같은 이름 충돌), 한 시간 안에 고친 줄은 아예 고르지
    않음(ON CONFLICT … WHERE 거짓이어도 잠그고 WAL 을 남김), 보고서 수는 빠진 PC 의 합집합.
  - **남은 것:** 정기 점검 창(B-42)에서 판단 미루기, EventRecordID 누락(B-56).
- **대안:** 하트비트에 채널별 마지막 레코드 시각을 싣기 — 에이전트 재배포가 필요하고 Fluent Bit 이 그 값을 내지 않는다. events 를 매번 집계 — 7일 × PC 수 집계가 무거워 기각.

## ADR-047 백업·보관 파일의 외부 저장소 복제
- **상태:** 채택 (2026-10-30). BACKLOG B-17(벤치마킹으로 P1).
- **배경:** `archive/`(로그 보관 파일)와 `backups/`(DB 백업)가 같은 서버 디스크에만 있었다. 로그 서버는 병원 PC 와 같은 망에 있어 랜섬웨어에 함께
  암호화되면 사고 증거와 복구 수단이 함께 사라진다. 고시 제8조③(접속기록 위·변조·분실 방지)·ISMS 2.9.3·2.9.4.
- **결정:**
  1. 새 이미지(rclone) 없이 `backup` 서비스(postgres:17-alpine, busybox sh)가 매일 백업 뒤 호스트에 마운트한 폴더(`WLM_REPLICA_DIR` → `/replica`)로
     복제한다. 폐쇄망 병원의 외부 저장소는 대개 SMB·NFS 로 붙는 NAS 다 — 폴더 복사면 충분하고 반입할 이미지가 늘지 않는다.
  2. **새 파일만** 복사하고 SHA-256 으로 확인한 뒤 이름을 바꾼다. 이미 있는 파일은 **덮어쓰지 않는다** — 보관 파일·백업은 이름이 바뀌지 않으므로,
     원본이 암호화·변조돼도 복제본은 처음 것 그대로다(크기가 다르면 센다).
  3. 지우는 것은 보관기간이 지난 보관 파일(달 끝 + `WLM_RETENTION_DAYS`, api 와 같은 판단)과 `WLM_REPLICA_BACKUP_DAYS` 가 지난 매일 백업뿐이다.
     원본이 만료 전에 사라졌으면 복제본은 지우지 않고 센다(사고일 수 있다). 객체 잠금(WORM)으로 지우지 못하면 남긴 채 센다.
  4. 결과는 감사로그 `backup.replicate`(새로·실패·크기 다름·만료 삭제·원본 없음·복제본 수). api 는 `WLM_REPLICA=on` 이면 기록 없음·36시간 밀림·실패·
     원본 없음을 로그 보관 화면과 점검 보고서 '점검 필요'(백업 문제)로 알린다.
- **이유:** 덮어쓰지 않기와 만료로만 지우기가 랜섬웨어에 대한 핵심이다(동기화 도구의 sync 는 원본의 암호화·삭제를 그대로 복제한다).
- **대가:** 복제 폴더를 서버가 쓸 수 있으므로 서버를 장악한 공격자는 복제본도 지울 수 있다 — NAS 의 스냅숏·객체 잠금을 켜도록 안내한다(AIRGAP.md §11).
  S3 등 객체 저장소 직접 연결은 없다(필요하면 NAS 게이트웨이나 rclone mount 로).
- **대안:** rclone 서비스 추가(MIT) — 폐쇄망에 이미지가 하나 더 늘고 대부분의 병원 NAS 에는 폴더 복사로 충분해 미룸. rsync --delete — 원본 삭제·암호화를 복제해 기각.
- **함정(시험에서 잡음):** busybox `date` 는 `-d '+1 month'`·`'-3 years'` 를 모른다 — 처음 구현은 만료 판단이 늘 '아님'이었고 자체 시험도 이름이 빈 파일로 우연히 통과했다.

## ADR-048 EMR 접속기록(의료법 제23조④) — 0단계 조사 결과와 보류한 결정
- **상태:** 조사 완료, 수집 범위 결정은 **보류**(병원 답변 대기) (2026-10-30). BACKLOG B-39.
- **배경:** 'EMR 단순 열람도 접속기록을 별도 보관, 2026-12-10 시행' 이라는 보도(2차 출처)를 1차 출처로 확인하고, 이 시스템이 맡을 몫을 정하려 했다.
- **확인한 것 (1차 출처, 2026-10-30 기준):**
  - **법률은 확정:** 의료법 제23조④ 이 '기재·추가기재·수정을 하거나 전자의무기록을 **열람한** 경우' 접속기록을 별도 보관하도록 바뀌었다
    (법률 제21776호, 2026-06-09 공포, **2026-12-10 시행**). 위반은 제90조 500만원 이하 벌금(벌칙 수준은 그대로, 범위만 넓어짐).
    규모 차등·유예 없음 — 모든 의료인·의료기관 개설자. (https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=286719&efYd=20261210)
  - **시행규칙은 입법예고만:** 보건복지부공고 제2026-696호(2026-09-09~10-19), 안 제16조②: 접속기록을 '제16조①2호의 **전자의무기록 이력관리 장비**'에 별도 보관,
    시행 2026-12-10, 시행 뒤의 행위부터. 공포는 아직 없음(현행 제16조② 는 추가기재·수정만). 규제영향분석서: '별도 장비유형을 새로 지정하지 않고' 기존 시스템 기능 활용. (https://opinion.lawmaking.go.kr/gcom/ogLmPp/88448, https://www.law.go.kr/LSW/lsInfoP.do?lsiSeq=286963)
  - **항목·보관기간은 미정:** 법률·시행규칙안 모두 기록 항목을 정하지 않는다. 고시(전자의무기록 시설·장비 기준) 개정안이 보관기간을 '진료기록 보존기간과 같게'(최대 10년)
    한다는 내용은 한 조사자가 공고문 요약으로만 읽었고 교차 확인에서 다시 열지 못했다 — **2차 수준으로 둔다**. 현행 고시(제2023-245호)에는 접속기록 보관기간이 없다. (https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000232676)
  - '열람'의 범위(일부 화면·자동 새로고침·시스템 적재·인터페이스)는 어느 원문에도 정의가 없다.
- **판단:**
  1. 의무를 지는 장치는 **EMR 의 이력관리 장비**다 — 이 로그 서버가 아니다. EMR 업체(인증기준 F008 이 이미 접속기록 생성을 요구한다고 규제영향분석서가 인용 — 원문 미확인)와
     기존 접속기록 솔루션이 1차 담당이다. 이 시스템이 EMR 열람 기록의 '법정 보관 장비'가 되려면 고시 항목·보관기간·위변조 요건이 확정돼야 하고, 지금 만들면 다시 만들 가능성이 크다.
  2. 그래서 B-76(EMR 접속기록 수집·소명)은 **P3 그대로**, B-70(보관 등급)은 10년을 넣지 않는다. B-60(PACS ATNA)은 표준 형식이라 법령과 무관하게 P2 그대로.
  3. 이 시스템이 할 수 있는 몫은 병원 답변에 따라: (a) EMR·접속기록 장비의 syslog·상태만 받아 '기록이 끊겼다'를 알림(B-37 의 채널 감시를 그대로 씀),
     (b) 병원이 교차 분석(퇴근 뒤 열람·대량 열람)을 원하면 B-76 을 올린다.
- **이 시스템 자체(개인정보처리시스템)에 대한 고시 확인 — 코드 변경 없음:**
  - 현행은 개인정보보호위원회고시 제2026-9호. 제2025-9호의 유예 조항(제4조①12·13호, 제5조①⑥, 제6조②, 제8조①②)은 **2026-10-31** 부터 적용(부칙 '발령한 날의 1년 후'에서 계산). (https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000281400&chrClsCd=010201)
  - 제2조제3호 접속기록 항목은 '**식별자**, 접속일시, 접속지 정보, 처리한 정보주체 정보, 수행업무'(조사 때의 '계정'은 2021 판본 문구) — `audit_log` 의
    actor·at·actor_ip·detail(정보주체: 사용자·IP·분류, ADR-042)·action+target 과 맞는다.
  - 제8조① 보관 대상이 '접속한 자(정보주체 제외)' 전체로 넓어짐 — `audit_log` 는 이미 모든 계정(외부 업체 계정 포함)을 남긴다. 1년/2년(5만명 이상·고유식별·민감정보)은 2021 판본부터 같음(ADR-040 그대로).
  - 제8조② '월 1회 이상 점검'과 '다운로드 사유 반드시 확인'이 빠지고 '점검 주기·방법·사후조치절차를 내부 관리계획으로' 정한다. 점검 주기는 사이트가 고르게(B-72, 기본 월 1회 유지).
    CSV 사유(ADR-042)는 법정 문구는 빠졌지만 사후조치 절차로 쓰도록 그대로 둔다 — 내부 관리계획에 적도록 ISMS.md 에 안내.
  - 제5조③ 권한 기록 3년, 제8조③ 위·변조 방지 '조치'(방법은 정하지 않음) — ADR-040·ADR-047, B-71.
  - 공공시스템 특례(제16조 인사정보 연계, 제17조 자동 분석·소명)는 보호위원회가 **지정한** 공공시스템에만 — 병원의 지정 여부는 병원에 묻는다.
- **병원에 물을 것:** EMR 업체가 열람 기록을 남기는지(항목·보관 위치·기간·내보내기 형식), 별도 접속기록 솔루션 유무, PACS 의 ATNA 지원(B-60), 공공시스템 지정 여부,
  내부 관리계획의 접속기록 점검 주기, 이 시스템에 EMR 접속기록 교차 분석을 원하는지.
- **다시 볼 때:** 2026-12-10 전후 law.go.kr 에서 시행규칙·고시 공포를 확인한다. 고시 개정안 원문(.hwpx)은 내려받기라 아직 읽지 않았다.
  공포본이 항목·보관기간·위변조 방법을 정하면 이 ADR 을 갱신하고 B-76·B-70 의 우선순위를 다시 정한다.
- **대안:** 지금 EMR 표 수집·5항목 스키마를 만들기 — 항목·기간 미확정, 업체마다 표가 달라 기각(보류).

## ADR-049 관리자 2단계 인증 (TOTP)
- **상태:** 채택 (2026-10-31). BACKLOG B-74 — 운영(병원) 첫 설치 전에.
- **배경:** 이 서버는 병원 전체의 보안 로그·감사 증적을 쥔 자산인데 비밀번호 하나로 열렸다. 사내 SSO 연동(B-12)만으로는 MFA 가 생기지 않고,
  폐쇄망에는 SMS·푸시가 없다. 고시 제6조②(외부 접속 시 안전한 인증수단)는 2026-10-31부터 대상이 넓어졌다(ADR-048).
- **결정:**
  1. **RFC 6238 TOTP**(HMAC-SHA1, 30초, 6자리) — 표준 라이브러리 `hmac`·`hashlib`, 새 의존성 없음. 인증 앱은 오프라인으로 돌아 폐쇄망에 맞다.
     QR 대신 키 직접 입력(그룹 지은 base32)과 otpauth 주소 — QR 인코더를 직접 짜거나 들여오지 않는다.
  2. **두 단계 세션:** 비밀번호가 맞으면 코드를 기다리는 세션(`sessions.mfa_ok=false`, 5분)만 준다. 이 세션은 내 정보·로그아웃·코드 확인만 —
     비밀번호 변경·2단계 등록도 막는다(비밀번호만 아는 사람이 등록을 바꾸지 못하게). 코드가 맞으면 **새 토큰**의 정식 세션.
  3. **재사용 방지:** 마지막으로 받은 시간 칸(`mfa_last_step`)보다 큰 칸만, 조건부 UPDATE 로 한 번만(동시에 두 번 보내도 한쪽만). 앞뒤 한 칸(±30초) 허용.
  4. **잠금 정책 공유:** 코드 실패도 `failed_count` 에 세고 같은 기준(5회·10분)으로 잠근다. **비밀번호 단계에서는 실패 수를 지우지 않는다** —
     비밀번호를 아는 사람이 다시 로그인할 때마다 지워지면 코드를 끝없이 맞혀 볼 수 있다. IP 단위 제한(10분 30회)도 함께.
  5. **비밀값은 `app/secrets.py` 로 암호화**(WLM_SECRET_KEY), **복구 코드 10개는 서버 키로 HMAC 한 값만**(52비트 — 느린 해시가 필요 없고 DB 만 새면 못 되찾음),
     한 번씩, 등록·새로 받기 때 한 번만 보여 준다.
  6. **필수 범위 `WLM_MFA_REQUIRED`:** privileged(기본: 관리자와 관리 권한 — 알림 규칙·환경설정·감사로그·에이전트 배포 — 그룹 구성원) / all / off.
     필수인데 등록하지 않았으면 비밀번호 변경 다음에 등록 화면(그 전에는 다른 API 403 `mfa_setup_required`). WLM_SECRET_KEY 가 없으면 강제하지 않는다(기동 로그 경고).
  7. **분실:** 관리자의 '2단계 초기화'(세션 끊김, 다른 받는 곳에 관리 작업 알림 — 인증이 약해지는 작업), 비상은 서버 셸의
     `python -m app.cli reset-mfa <아이디> --reason …`(actor=cli). 필수인 사람은 스스로 끌 수 없다. 등록하면 다른 세션은 끊는다(2단계 없이 열린 세션이 남지 않게).
  8. 감사로그 `auth.login_password_ok`(코드 대기)·`auth.login`(detail.mfa = totp·recovery)·`auth.mfa.*`.
- **적대적 검토 반영 (보안):**
  - **동시 요청으로 잠금 피하기(높음, 재현):** 확인한 뒤에 실패를 세고 절댓값으로 써서, 코드 2,000개를 동시에 보내면 모두 잠금·IP 제한을 지나 확인됐다.
    → 시도를 **확인 전에 원자적으로 센다**(`_reserve_attempt`: 잠기지 않은 행만 `failed_count+1`, 기준에 닿으면 같은 문장에서 잠금). 행 잠금으로 줄을 서므로
    잠금 기간마다 기준 수까지만 확인된다. 비밀번호 단계도 같은 방식. IP 제한도 확인 전에 센다(워커 1개라 await 없이 원자적).
  - 복구 코드 새로 받기·끄기의 코드 확인에 제한이 없었다 → 같은 잠금, 기준에 닿으면 그 사람의 모든 세션을 끊는다(가로챈 세션으로 맞혀 보기).
  - 틀린 코드가 401 이라 화면이 '세션 만료'로 로그인 화면에 튕겼다 → 400, 401 은 코드 대기 만료만.
  - 휴대폰 분실 안내가 막다른 길이었다 → **스스로 다시 등록**(`/api/auth/mfa/reenroll`, 지금 코드나 남은 복구 코드 하나로).
  - 코드 대기 세션에 마지막 로그인 IP·권한·범위를 주던 것 → 이름만. 전각 숫자 500, 키가 없으면 비밀번호만으로 들어가던 것(닫힌 쪽으로 503),
    키가 바뀌면 알 수 없는 500 → 안내 문구, 등록·복구 코드 동시 요청(한 트랜잭션·행 잠금), 끌 수 없음의 이유 코드가 코드 대기와 겹치던 것.
  - 비밀번호까지 맞고 코드를 넣지 않은 로그인도 시도 하나로 남는다(비밀번호를 아는 사람이 다시 로그인해 횟수를 지우지 못하게) — 그런 로그인을 5번 버려도 잠긴다.
- **대가:** 휴대폰 시계가 30초 넘게 어긋나면 코드가 맞지 않는다(안내 문구). 관리자 모두가 앱을 잃으면 서버 셸이 필요하다.
  **WLM_SECRET_KEY 를 바꾸면 등록한 사람은 모두 `reset-mfa` 로 다시 등록해야 한다**(비밀값·복구 코드가 그 키에 묶임). 여러 대면 세션·실패 수는 DB 라
  같이 보지만 IP 제한은 프로세스 메모리.
- **대안:** WebAuthn(보안키) — 브라우저·장치 지원과 등록 절차가 병원 PC 에 무겁고 http 설치에서는 쓸 수 없어 나중에. 메일 OTP — 메일이 멈추면 아무도 못 들어오고
  메일 계정이 곧 두 번째 요소가 되어 기각. pyotp(MIT) — 50줄이면 되는 계산이라 의존성을 늘리지 않음.

## ADR-050 감사로그 위·변조 증명: 해시 체인과 DB 밖 앵커
- **상태:** 채택 (2026-10-31). BACKLOG B-71 1단계(감사로그). 이벤트 다이제스트는 2단계.
- **배경:** `audit_log`·`alert_notes`·`reports` 는 트리거로 수정·삭제를 막지만 DB 슈퍼유저(이 배포의 `wlm` 역할이 슈퍼유저다)는 트리거를 끄고 고칠 수 있고
  그 흔적도 같은 DB 에만 남는다. '위·변조되지 않았음을 어떻게 증명하나'는 ISMS 2.9.4 심사의 단골 질문이고 고시 제8조③(접속기록 위·변조 방지 조치)의 근거다.
  ADR-042(기록 못 하면 거부)는 기록이 있다는 것을, 이것은 고쳐지지 않았다는 것을 보인다.
- **위협 모델:** DB 안에서는 슈퍼유저가 무엇이든 할 수 있다. 강한 보장은 **DB 밖 앵커**에 대해서만이다 — 서버 밖에 남은 앵커(외부 저장소 복제·WORM,
  점검 보고서 메일)가 덮는 범위를 고치면 검증이 실패한다. 마지막으로 밖에 나간 앵커 뒤를 통째로 다시 쓰는 것, 이 서버의 앵커 파일을 지우는 것은 막지 못한다.
- **결정:**
  1. **해시 체인 (마이그레이션 022):** BEFORE INSERT 트리거가 행마다 `row_hash = SHA-256(앞 행 해시 + 이 행)` 을 남긴다(PostgreSQL 내장 `sha256()`,
     새 의존성 없음). 한 줄짜리 머리 `audit_chain` 을 `FOR UPDATE` 로 잠가 INSERT 가 줄을 서고, **잠근 뒤에 번호를 새로 받고 시각도 정한다**(`clock_timestamp()`)
     — 기본값으로 먼저 받은 번호는 잠금 순서와 달라 체인과 번호 순서가 어긋나고, 넣는 쪽이 시각을 주면 체인을 지키면서 과거·미래의 기록을 만들 수 있었다.
     머리가 없으면 INSERT 를 거부한다(조용히 체인 없이 쌓이지 않게). 머리는 지울 수 없고 마지막 번호는 앞으로만 간다(트리거).
  2. **행의 글 모양:** 칸마다 NULL 이면 `N`, 아니면 '글자 수:값', `|` 로 잇는다 — 칸 사이로 글자를 옮기거나 NULL 과 빈 글을 바꿔도 같은 글이 되지 않게.
     시각은 UTC 마이크로초, detail 은 jsonb 의 글 모양. SQL 함수는 칸마다 CASE 를 풀어 쓴다(도우미 함수는 인라인되지 않아 7배 느렸다).
  3. **기존 행:** 022 가 이미 있는 행에도 해시를 채운다(내용은 그대로, 해시 칸만 — 이 한 번만 수정 금지 트리거를 끈다). 처음 설계(기존 행을 genesis 해시 하나로
     묶기)는 업그레이드 직후 첫 앵커가 해시 없는 행을 가리키고 그 행들의 만료 삭제를 설명할 수 없어 거짓 경보가 났다(검토에서 재현).
  4. **검증은 파이썬으로 따로**(`app/integrity.py`), **한 시점(REPEATABLE READ)** 에서 — 같은 DB 함수로 다시 계산하면 함수를 바꾼 변조를 못 잡고, 따로 읽으면
     정리와 겹칠 때 거짓 경보가 난다. 모든 행을 본다: 내용(해시), 이어짐, 해시 없음(트리거를 끈 행), 미래 시각, 022 이후 행의 시각 역행(1시간 넘게),
     마지막 행 = 머리, 체인 시작 = 시작 해시 또는 **믿을 만한** 만료 기록(시스템이 남김, 기록한 보관기간·기준 시각이 그 행의 시각과 맞음, 보관기간 365일(또는 설정) 이상).
  5. **DB 밖 앵커:** 매일 마지막 번호·해시·그 행의 시각을 보관 폴더 `integrity-YYYY-MM-DD.json`(외부 저장소 복제로 NAS·WORM 에 한 벌 더, ADR-047)과
     점검 보고서(메일 — 보고서는 고칠 수 없고 서버 밖으로 나간다)에 남긴다. 앵커가 가리키는 행의 시각이 보관기간 안이면 그 행이 있어야 하고 **다시 계산한** 해시가
     같아야 한다(저장된 칸만 보면 머리를 되돌려 그 뒤를 고친 것이 통과했다). 보관기간이 지난 앵커는 '만료'로 센다. 복제본의 앵커로도 대조한다: `cli verify-chain --anchors <폴더>`.
  6. **보관기간 만료 삭제:** 번호 순서의 앞부분만(아직 보관기간 안인 첫 행 앞까지) 지우고, 지우기 전에 지울 행과 남을 첫 행을 체인으로 맞춰 본다 — 맞지 않으면
     지우지 않는다(고친 행의 시각을 과거로 돌려 만료 삭제가 지우게 하는 세탁을 막음 — 검토에서 재현). 지운 마지막 번호·해시는 **같은 트랜잭션**의 감사로그로 남긴다.
  7. **백업으로 되돌리기:** 복원하면 백업 뒤에 남긴 앵커는 사라진 행이나 같은 번호의 다른 행을 가리킨다(실제 `pg_restore` 로 재현 — 복원 한 번으로 검증이 영영 실패).
     backup.sh 가 남기는 복원 기록(`backup.restore`)의 바로 앞 행 시각(= 백업 시점)과 복원 시각 사이에 남긴 앵커가 맞지 않으면 '버려진 갈래'로 따로 보이고 실패로 세지
     않는다(잘못 고른 백업을 안전 사본으로 다시 되돌린 경우도). 그 밖의 앵커, 시각이 없는 앵커는 늘 대조한다. 정상 복원과 가짜 복원 기록(끝을 지우고
     꾸민 것)은 같은 모양이므로 한 달 동안 노란 줄로 사람에게 묻고, 복원 기록 자체도 체인에 남는다.
     보관기간을 줄였다 늘린 경우를 위해, 365일 이상을 적은 믿을 만한 만료 기록은 그 앞 행의 삭제를 설명한다 — 1년 안의 앵커는 만료 기록으로 설명되지 않는다.
  8. **운영:** 정기 정리(1시간마다)에서 하루 한 번 앵커, 20시간마다 검증(`integrity.verify`) — 기동 중·수집 요청 안에서는 하지 않는다(행이 많으면 기동이 늦었다).
     검증이 예외로 멈춰도 실패로 남긴다. 판단은 `integrity.status` 한 곳(검증 실패·만료 삭제 멈춤·이틀 넘게 검증/앵커 없음) — 로그 보관 화면, 점검 보고서 '점검 필요',
     운영 준비도가 같이 쓴다. 마지막 검증·앵커는 시각이 아니라 번호 순서로 고른다(미래 시각의 가짜 '정상' 기록이 최신이 되어 매일 검증을 멈추게 했다).
- **대가:** 감사로그 INSERT 가 머리 한 줄의 잠금으로 줄을 선다(동시 8개면 처리량 약 절반, 실제 감사 기록은 초당 수십 건 이하 — PERFORMANCE.md §2.7). 업그레이드 때
  기존 행에 해시를 채우는 데 행 100만 개에 약 40초(개발 VM). 해시 칸 때문에 감사로그 행이 약 130바이트 커진다. 번호는 INSERT 마다 둘씩 증가한다(기본값 + 트리거).
- **대안:** 행마다 HMAC(서버 키) — 키를 가진 사람이 다시 쓸 수 있고 이어짐(삭제)을 못 잡아 체인으로. pgaudit — 서버 로그로 남을 뿐 증명이 아니고 확장 설치가 필요해 기각.
  해시를 따로 표에 두기 — 감사로그를 다시 쓰지 않지만 표가 하나 더 늘고 지키는 트리거도 둘이 되어, 한 번의 업그레이드 비용을 택했다.
  주기적 다이제스트만 — 그 사이의 변경을 못 잡아 체인으로.
- **보완 (2026-11-01, B-71 2단계 — 수집 로그 다이제스트):** `events` 에는 체인이 없어 슈퍼유저가 로그를 고치거나 지워도 드러나지 않았다.
  수신 시각(서버가 정함, 파티션 키)으로 닫힌 한 시간마다(끝나고 10분 뒤) 그 시간의 모든 행을 해시해 감사로그 `integrity.events_digest` 로 남긴다 —
  감사로그 체인과 DB 밖 앵커가 이 기록을 지킨다(`app/eventdigest.py`).
  - 다이제스트 = SHA-256(행 해시를 번호 순으로 이은 것). 같은 시간 안에서도 동시에 들어온 묶음은 수신 시각과 번호 순서가 다르므로 번호로 정렬해
    보관 파일(수신 시각 순)과 DB 가 같은 값을 낸다. XOR·합처럼 순서와 무관한 결합은 행을 골라 고쳐 상쇄할 수 있어 쓰지 않는다.
  - 행 해시는 보관 파일과 같은 칸(archive.COLUMNS), raw 는 키를 정렬한 JSON — DB(jsonb → dict)와 보관 파일(JSON)이 같은 글을 낸다.
  - 확인: 매일 검증(최근 `WLM_EVENT_DIGEST_VERIFY_HOURS`, 기본 24시간), **보관 파일을 만들 때 그 달 전체**(파티션을 지우기 전 마지막 기회 —
    한 시간씩만 메모리에), `cli verify-chain --events 7d`. 보관할 때 다르면 보관은 하고(파일 = 지금 DB) `integrity.events_mismatch` 로 한 달 동안 빨간 줄.
  - 다이제스트는 이 기능을 켠 다음 시간부터(그 전 로그는 보관 파일의 SHA-256 이 몫). 꺼져 있던 동안의 시간은 켜진 뒤 정기 정리마다 24시간씩 따라잡는다.
  - 대가: 행마다 약 55µs(가져오기 35 + 해시 20, PERFORMANCE.md §2.7) — 매시간 그 시간 분량, 매일 검증에 하루 분량. 하루 천만 건이면 매일 검증이 약 9분
    (스레드에서 해시, 가져오기는 천 행씩 — 수집을 오래 막지 않게). 많으면 `WLM_EVENT_DIGEST_VERIFY_HOURS` 를 줄인다.
  - 복원한 옛 보관 파일(v1)은 공통 필드·EventData 이름을 다시 구해 넣으므로 다이제스트와 다를 수 있다 — 매일 검증 범위(최근)에는 들지 않는다.

## ADR-064 알림의 개체(PC·계정·IP)는 알림을 넣을 때 SQL 함수 하나로 채우고, 관련 알림·개체 페이지는 그 열로 찾는다
- **상태:** 채택 (2026-11-04). BACKLOG B-67 1단계. ADR-062(계정 열쇠)·ADR-025(알림 조회 범위)·ADR-042(접속기록) 위에.
- **배경:** 상세에는 '같은 규칙·대상의 해결 안 된 알림'만 있어 랜섬웨어 흐름(RDP 무차별 대입 → 로그온 성공 → 새 서비스 → 감사 로그 삭제)이 규칙 4개의
  알림으로 흩어진다. 대상 이름(group_key)은 규칙마다 뜻이 달라(IP·사용자 표기·값 조합·'PC · 채널') 그대로 이을 수 없다.
- **결정:**
  1. `alerts` 에 `entity_hosts`·`entity_accounts`·`entity_ips`(text[], 마이그레이션 046). 계정은 표기 통일 열쇠(`wlm_user_key`) — kim·HOSP\kim·kim@hosp.local 이 한 사람.
  2. **채우는 규칙은 SQL 함수 `wlm_alert_entities(payload, 종류, observed)` 하나** — 새 알림(`insert_alert`)과 옛 알림(마이그레이션의 UPDATE)이 같이 쓴다.
     파이썬·SQL 두 곳에 두면 옛 알림과 새 알림의 뜻이 어긋난다. 함수는 고치지 않는다(바꾸면 `_v2`).
     - **대상:** 묶음 기준이 host·ip·user·account 인 대상 이름, PC 끊김의 PC, 채널 끊김·처음 보는 값의 PC, 처음 보는 값 한 조합의 값 — 늘 넣는다.
     - **본 것:** 평가 때 알림 조건에 맞은 로그에서 센 PC·계정·IP(`repository.alert_entities`, 종류마다 11개까지), 처음 보는 값은 본 PC(sightings),
       세지 못했으면(옛 알림·시간 초과) 표본 로그의 PC. 몰려온 묶음의 값도 여기. **종류마다 서로 다른 값이 10개를 넘으면 넣지 않는다** — 수십 대에 걸친 알림
       (서비스 비정상 종료 300대)이 모든 PC 의 관련 알림이 되면 관련 알림이 아무 뜻이 없다. 대상 값은 넘어도 남는다.
     - 256자를 넘는 값은 넣지 않는다(로그에서 온 긴 값이 GIN 색인 한 줄 상한을 넘으면 알림 INSERT 가 실패한다). 깨진 payload 모양은 건너뛴다.
  3. **관련 알림** `GET /api/alerts/{id}/related`: 발생 시각 앞뒤 1시간에 개체가 하나라도 겹치는 다른 알림(최대 50, 겹친 값 `shared_*`). 조회 범위는 목록과 같은
     (규칙, 대상, PC) 로 LIMIT 전에 — 범위 밖 알림의 관련 알림은 404. 발생 시각으로 좁힌 뒤 배열 겹침으로 거른다(1시간 안 알림은 적다).
  4. **개체 페이지** `#/entity/host|user|ip/<값>`(`GET /api/entities/{kind}/{value}`): 기간 안 그 개체의 알림(GIN `@>`)·PC 수신 정보(PC 범위 안일 때만)와
     그 개체를 찾는 검색 문장(`host:`·`account:`·`ip:`, 값은 정규형 따옴표). 로그 쪽(건수·흐름·분류·상대 개체·최근 로그)은 화면이 그 문장으로 검색 API 를 부른다 —
     조회 범위·시간 상한·접속기록을 다시 구현하지 않는다. 사람·IP 를 지목해 보는 조회라 접속기록 `entity.view`(10분 묶음, 실패하면 503).
  5. 알림 상세에 개체 칩(누르면 개체 페이지)·관련 알림 목록, 로그 상세의 PC·계정·IP 옆에 '개체 페이지'.
  6. (검토 보완) **개체 PC 는 읽을 때 사람마다 거른다**(`visibility.scrub_entities` — 그 알림의 규칙 분류로 볼 수 있는 PC 만): 처음 보는 값 알림은 그 값을 본 PC 를
     모두 개체로 두어 알림의 PC 만 보는 사용자에게 범위 밖 PC 이름이 목록·상세·관련 알림·개체 페이지로 보였다(표본을 그 PC 것만 두는 것과 같은 이유).
     저장은 그대로(관리자에게는 PC 사이 연결이 보인다). 관련 알림은 거른 개체로만 잇고, 개체 페이지는 그 PC 를 그 규칙으로 볼 수 있는 알림만(LIMIT 전에).
     PC 수신 정보는 수집 PC 목록과 같은 판단(범위 안 로그가 있었거나 PC 로만 정한 범위에 맞을 때) — 분류로만 정한 범위는 모든 PC 이름에 맞는다.
  7. (검토 보완) **어느 PC 에나 있는 기본 계정**(SYSTEM·LocalSystem·LOCAL/NETWORK SERVICE·ANONYMOUS LOGON·DWM-n·UMFD-n 등, `repository.MACHINE_ACCOUNTS`)은
     본 값으로 세지 않고 관련 알림을 잇지 않는다 — 업데이트가 서비스를 300대에 깔면 '새 서비스 설치'(7045 AccountName = LocalSystem)가 모두 서로의 관련 알림이 되어
     진짜 흐름이 50개 상한 뒤로 밀렸다. administrator·guest 는 두지 않는다(여러 PC 에 같은 이름으로 대입하는 것이 바로 이어 볼 흐름).
  8. (검토 보완) 옛 알림 채우기는 알림 하나에 약 0.5ms(행 30만 개에 약 2.5분) — 함수는 고치지 않으므로(마이그레이션은 추가만) 설치 스크립트가 마이그레이션 중이면
     30분까지 기다린다(마지막 '마이그레이션 적용' 뒤에 기동 줄이 없을 때, 끝난 뒤 1분). 2분에 멈추면 운영자가 다시 띄워 트랜잭션이 처음부터 다시 돈다(022 도 같다).
  9. (검토 보완) **관련 알림 상한(50)은 강하게 이어진 것부터 채운다** — 계정·IP 가 겹친 것 → 겹친 값이 많은 것 → 발생 시각이 가까운 것. 자른 뒤 발생 순서로 보인다.
     발생 순서로 채우면 도메인 컨트롤러처럼 여러 사람의 알림(계정 잠금·4771)이 '본 PC'로 모이는 곳에서 PC 로만 이어진 앞 시각 알림이 자리를 차지해
     5분 뒤 같은 계정의 감사 로그 삭제가 빠졌다. 고르기는 id·겹친 값만으로 하고 전송 상태 등 칸은 고른 것에만 붙인다.
- **대가:** 개체는 알림을 넣을 때의 로그로 정해진다 — 뒤에 늦게 들어온 로그의 PC 는 그 알림에 붙지 않는다. 묶음 기준이 `f.<경로>`(예: `f.EventData.TargetUserName`)인
  대상 이름은 개체로 보지 않는다(뜻을 모름) — 대신 본 것(조건에 맞은 로그의 username)으로 붙는다. 옛 알림은 표본(최대 5건)의 PC 뿐이다.
- **2단계(남음):** 같은 개체에서 1시간 안에 서로 다른 전술(MITRE 태그 → 전술 표) 3개 이상이면 상관 알림.

## ADR-063 처음 보는 값은 엔진이 받은 시각 구간을 이어서 훑어 seen_terms 에 한 문장으로 — 수집 경로는 건드리지 않음
- **상태:** 채택 (2026-11-03). BACKLOG B-47. ADR-062(account) 위에. ADR-045(평가와 전송)·ADR-046(수집 트랜잭션 집계)·ADR-052(저장한 검색)·ADR-053(관찰 모드) 보완.
- **배경:** 병원 서버는 접속 패턴이 안정적이라 '처음 보는 것'(관리자 계정의 새 출발지, 새 서비스, EMR DB 의 새 SQL 로그인)이 강한 신호다. 건수 규칙은 임계값을
  정하기 어렵고 첫 1건을 놓친다. Elastic new terms·Wazuh FTS·Sentinel FirstTime* 와 같은 것.
- **결정:**
  1. `kind: new_terms` — `fields` 1~3개(검색 키·`f.<경로>`, 값은 `repository._field_expr` — account 는 `wlm_user_key`), `history`(다시 새로 볼 기간, 1~180일),
     `learn`(배우는 기간), `burst`, `max_terms`. window·threshold·group_by·distinct·cooldown·`resolve: auto` 는 거부(뜻이 없거나 오해를 부른다).
  2. **엔진 쪽에서 받은 시각(`received_at`) 구간을 이어서 훑는다**(`new_terms_state.cursor_at`, 앞 구간과 2분 겹쳐 — 받은 시각은 트랜잭션 시작 시각이라 늦게
     커밋된 행). 수집 트랜잭션에 넣으면 규칙마다 쿼리가 늘고 규칙을 바꿀 때 지난 로그를 다시 볼 수 없다. 발생 시각(ts)은 PC 시계·밀린 로그에 흔들린다.
     한 번에 볼 구간(`chunk_sec`)은 시간 초과면 반, 2초 안이면 두 배(1분~6시간), 한 주기 8초까지(남은 것은 다음 주기).
  3. 조합의 열쇠는 `wlm_terms_hash(text[])`(SHA-256, 마이그레이션 039, 고치지 않음 — 바꾸면 모든 조합이 새 값). 표시용 값은 256자로 자르지만 열쇠는 전체 값.
     값이 없는(NULL·빈) 조합은 세지 않는다.
  4. **한 문장(CTE)으로** 모으기 → 본 값과 맞추기 → 쓰기 → 상태(terms_n·overflow_n·cursor_at)까지 — 멈췄다 다시 떠도 같은 구간을 두 번 세지 않는다.
     한 시간 안에 이미 본 조합은 쓰지 않는다(평소 쓰기가 거의 없게, agent_events 와 같은 방법). Bloom 필터는 두지 않는다(DB 로 충분, 틀린 '이미 봄'이 없다).
  5. **배우기:** 처음 켜면 DB 에 있는 만큼(learn 까지) 거슬러 배우고(최근부터 거꾸로) 모자란 만큼 앞으로(`learn_until` — 그 규칙이 보는 소스·PC 기준, 22). 조건 지문(저장한 검색 문장 + match,
     예외는 넣지 않음)이 바뀌면 본 값은 두고 다시 거슬러 배우며 그동안 **알림을 미룬다** — 배우다 더 먼저 본 것을 찾으면 '알릴 것'이 '배운 것'으로 바뀐다.
     3일 넘게 멈췄으면 그 사이는 배우기만(밀린 것을 한꺼번에 알리지 않게). 이 경우들 모두 `learn_until` 은 지금 이후로만 늘린다(검토에서: 조건을 바꾼 직후
     겹쳐 본 구간의 남은 값이 알림으로 나갔다).
  6. **조합마다 한 번 — 알림을 넣는 것과 조합을 '알림'으로 바꾸는 것은 한 트랜잭션**(`insert_alert(claim=…)`, pending → alerted·aggregated, 못 바꾸면 알림을
     넣지 않음). 엔진이 두 번 돌거나 겹쳐 봐도 두 번 알리지 않는다. 무음·관찰 모드는 다른 규칙처럼 엔진의 `fire` 가 처리.
  7. 한 주기에 `burst` 개보다 많으면 한 통 '처음 보는 값 n개'(앞의 20개). 상한(`max_terms`)을 넘는 새 조합은 두지 않고 세기만 하고 규칙 오류(`CappedError`) —
     지우면(LRU) 그 값이 다시 '처음 보는 값'으로 나와 거짓 알림이 된다.
  8. 정리: 본 값은 history + 1일 넘게 안 보이면(알릴 차례인 것은 남김) 6시간마다, 7일 동안 평가하지 않은 상태(지운·끈 규칙·바꾼 필드)는 본 값과 함께.
  9. 본 값은 계정·IP — 미리보기가 그 값을 보여 주면 접속기록 `alerts.preview`(건수 규칙 미리보기도 묶음이 계정·IP·원본 필드면 함께). 알림 상세는 알림 조회 범위로.
  10. 기본 팩에는 '원격 데스크톱 새 출발지'(4624 LogonType 10, account+ip) 하나를 **관찰 모드**로 — 현장마다 정상 출발지가 달라 오탐을 먼저 본다.
  11. (검토 보완) **진행·상한:** 거슬러 배우기는 구간마다 진행(backfill_to)을 남기고, 구간 크기는 꽉 찬 구간을 2초 안에 끝냈을 때만·시간 초과가
      난 크기 아래로만 키운다(이어서 훑기는 늘 짧아 빨라서 줄인 크기를 매 주기 되돌려 같은 자리에서 영영 멈췄다). 상한 오류는 **이번 평가에서**
      두지 못한 수로(`overflow_n` 을 누적하면 max_terms 를 올려도 오류가 영영 남았다).
  12. (검토 보완) **배우기 경계:** 조건을 바꿔도 아직 훑지 않은 [cursor_at, 지금) 은 알릴 수 있게(`learn_until = max(예전, cursor_at)`), 겹쳐 보다
      찾은 더 이른 행은 그 시각으로 다시 판단(배우는 기간 뒤면 pending 그대로), 오래 멈춤은 멈춘 때부터(history 까지)·거슬러 배우던 구간과 합쳐서,
      정리는 이어서 훑은 곳 기준(밀린 구간에 다시 보인 값을 지우지 않게), 기동 정리는 켜진 규칙의 상태를 지우지 않고, `name:` → `sid:` 열쇠는 옮긴다.
  13. (검토 보완) **알릴 때 다시 보기:** 처음 본 때부터 한 시간 안에 지금 조건(예외·저장한 검색)에 맞는 로그가 없으면 알리지 않고 배운 것으로
      (미뤄 둔 동안 건 예외). 처음 본 PC·발생 시각은 **같은 첫 행**(가장 작은 id)에서 — 각각 min() 이면 이름 순 최솟값 PC 로 무음·경로·조회 범위가
      갔다. 표본은 그 PC 것만(조회 범위·PC 경로). 여러 PC 에서 보인 조합은 PC 로 건 무음이 그 PC 모두에 걸려야 무음, 무음 중에 알린 조합이
      무음이 끝난 뒤에도 보이면 다시 알린다(last_seen 은 한 시간마다라 최대 한 시간 늦음).
  14. (검토 보완) 조회 범위는 `payload->'terms'->>'host'`(`terms_host`)를 목록·숫자·처리(`alert_group_counts`·`alert_rule_groups`·`alert_refs`)에도 —
      상세만 보여 PC 범위 사용자가 확인·해결하지 못했다. 경로 표본(`reachable`·탐지 약화)은 `AlertConfig.sample_targets`(PC 를 host= 로).
      대상 이름의 값은 100자까지(알림 색인 2704 바이트), 잘린 값(256자)은 같음으로 찾지 않는다(표본·링크에서 그 칸을 뺌). 몰린 묶음의 대상 이름에
      처음 본 시각(초)을 넣어 수만 같은 다른 사고가 함께 해결·무음되지 않게. 미리보기는 앞의 하루로만(7일이면 30초 상한을 넘었다).
      미리보기 접속기록에 조건(match·저장한 검색 문장)을, 심사 증적의 규칙 글에 new_terms 기준을.
  15. (2차 검토 보완) 상한 오류는 **자리가 다시 생길 때까지**(terms_n < max_terms 면 0 으로) — 한 평가만 오류로 두면 평가 간격이 60초를 넘을 때
      감시가 알리지 못한 채 두지 못한 값이 사라졌다. 겹쳐 본 2분은 앞 구간에서 셌으니 빼고 센다. 조건을 바꾸면 **이미 훑은 곳(cursor_at)까지**
      거슬러 배운다(지금부터 거슬러 배우면 밀린 이어서 훑기보다 먼저 새 값을 배웠다). 3일 넘게 멈춘 채 조건까지 바뀌었으면 멈춤 쪽으로(그 사이는
      배우기만). 알림의 대상은 **(규칙, 대상 이름, 처음 보는 값의 PC)** 셋 — 목록·묶어 보기·CSV·'함께 해결'·같은 대상 수(`repository.ALERT_HOST`).
      둘만 보면 history 뒤 다른 PC 에서 다시 난 같은 값 조합 알림이 PC 범위 사용자의 목록·함께 해결에 섞였다. 자른 값의 대상 이름에는 조합 열쇠
      앞 10자리를 붙인다. 무음 중에 몰려 한 통으로 묶은 조합은 하나라도 무음 뒤 이어지면 함께 다시 열어 다시 한 통으로(하나씩 열면 수백 통),
      PC 무음으로만 보내지 않은 조합은 5분마다 다른 PC 로 번졌나 보고 번졌으면 다시 알릴 차례로(50개까지).
  16. (3차 검토 보완) 처음 보는 값의 PC 를 칸으로(`alerts.terms_host`, 마이그레이션 040 — payload 에서 읽으면 목록·'함께 해결'마다 모든 알림의
      payload 를 풀어 5배 넘게 느렸다). 묶어 보기도 같은 셋으로 묶고 PC 를 보인다(둘로 묶으면 '모두 확인'이 다른 PC 의 알림을 남겼다).
      사고관리로 보내는 `dedup_key` 에도 PC 를(다른 알림은 예전과 같은 값). 다른 PC 로 번져 다시 알리는 알림의 PC 는 번진 PC — 점검 중인 첫
      PC 로 두면 그 PC 의 경로·조회 범위로 가서 번진 PC 쪽 사람은 못 봤다. 표본도 처음 본 때부터 지금까지 그 PC 의 것.
  17. (3차 재검토 보완, 18 에서 다듬음) **무음은 본 때로:** 처음 보는 값의 PC 무음은 그 PC 에서 마지막으로 본 때 무음이었는지로(규칙·대상·전체 무음은
      지금으로) — 지금으로 보면 점검 중에만 보인 값이 다른 PC 의 무음이 먼저 끝나는 순간 알림이 됐다. 그래서 끝난 무음으로 기록된 알림이
      생기므로 무음 뒤 다시 열기는 '알림 뒤에도 봤을 때'(last_seen > max(무음 끝, 알림 시각))만. 몰려온 묶음도 알리기 전에 한꺼번에 지금
      조건으로 다시 보고(전체 값 열쇠로, 시간 초과면 모두 알림), 묶음의 PC 들이 모두 그때 무음이면 무음. 번짐 확인은 (알림 번호, 열쇠)
      차례로 돌아가며(늘 최근 50개만 보면 오래된 조합은 차례가 오지 않았다), 몰린 묶음도 대상. 범위 밖 PC 의 무음은 상세에 이름·사유 없이,
      처음 보는 값 규칙의 무음 대상 자리는 PC 로도 보고 범위를 판단(범위 안 PC 의 무음을 걸고 풀 수 있게). 목록·대시보드·알림 CSV·심사
      증적 알림.csv 에 PC(마지막 칸 — 기존 칸 순서 그대로).
  18. (4차 검토 보완) 무음 판단의 재료를 한 곳으로: PC 와 그 PC 에서 마지막으로 받은 때는 **늘 로그에서**(`repository.term_sightings`·
      `hosts_last_seen` — seen_terms 의 첫 PC·한 시간 단위 last_seen 으로 대신하면 다른 PC 를 못 보고 옛 시각으로 판단해 묶음이 묻히거나
      다시 열 때마다 무음 알림이 되풀이됐다). 본 때로 판단하는 것은 **PC 무음만**(`repository.pc_silence` — 규칙·대상·전체 무음은 지금).
      번짐 확인은 알림 단위(묶음은 한 번에)·새 알림 먼저·나머지는 차례로, 알림마다 지난번에 본 뒤 받은 로그만, 무음이 끝난 지 한 시간 안의
      알림도(last_seen 은 한 시간 단위라 무음 뒤 다시 열기가 그동안 못 본다). 묶음을 다시 볼 구간은 하나씩과 같게(처음 본 때 한 시간 + 최근
      하루). 범위가 정해진 사용자가 거는 무음은 **PC 로만 맞춘다**(`alert_silences.host_only`, 마이그레이션 041) — 대상 이름으로도 맞추면
      PC 모양인 값 조합(계정 'ws-ops'·IP)으로 범위 밖 PC 의 알림을 막을 수 있었다. 관리자가 건 처음 보는 값 규칙의 무음은 그 사용자에게
      안 보인다(예전처럼 막음). 알림 상세에서 그 알림의 규칙·대상 그대로 건 무음은 숨기지 않는다.
  19. (5차 검토 보완) PC 로만 맞추는 무음은 **PC 범위가 정해진 사용자**의 것만(분류만 정해진 사용자는 모든 PC 를 보므로 예전처럼), 그리고
      대상 이름이 PC 에서 나온 알림(PC 별 묶음·끊김·채널 끊김 'PC · 채널')이면 대상 이름과도 맞춘다 — 모두 PC 로만 맞추면 IP·사용자로 묶은
      알림과 채널 끊김에 건 무음이 '적용 중'으로 보이면서 아무 데도 걸리지 않았다. 무음 수 표시도 host_only 를 읽어 목록과 같게 센다.
  20. (6차 검토 보완) PC 로만 맞출지는 **사용자·규칙마다** — 그 규칙을 모든 PC 에서 보는 범위(PC 제한 없는 범위가 그 규칙의 분류를 덮음)가
      없을 때만(분류 범위도 함께 가진 사용자의 IP 묶음 무음이 걸리지 않았다). PC 로만 맞추는 무음은 대상 자리가 PC 일 때만 받는다(422 —
      걸리지 않을 무음을 '적용 중'으로 남기지 않게). 알림 상세의 무음 범위에 처음 보는 값 알림은 'PC' 를 먼저. **배우는 동안 상한으로
      두지 못한 값**이 있었으면(`new_terms_state.learn_dropped`, 마이그레이션 042) 자리가 다시 생길 때 배우는 기간을 다시 거슬러 배운다 —
      늘 보이던 값이 상한을 올린 뒤 거짓 '처음 보는 값'이 됐다. 번짐 확인은 조합 하나면 그 값으로 좁혀(색인) 찾고, 한 차례 8초까지,
      시간 초과 수는 규칙 상태에.
  21. (7차 검토 보완) **한 평가에 한 예산**(`newterms._budget()` — 규칙 시간 상한의 절반 아래, 8초까지): 이어서 훑기·거슬러 배우기·번짐
      확인이 함께 쓴다(거슬러 배우기만 16초를 써 배우는 동안 내내 '느림'·알림 기능 경고였다). 번짐 확인은 본 데까지만 차례를 넘기고 시간
      초과 난 알림은 다음에 맨 뒤로(맨 앞에서 매번 예산을 다 써 그 뒤 알림이 영영 차례가 안 왔다), 시간 초과 수는 규칙 표에. 배우다 넘친
      기간을 다시 배울 때 history 보다 오래된 부분은 빼고, '더 먼저 본 것'은 그 사이가 history 안일 때만(오래전 기록이 history 넘게 안 보이던
      새 값을 배운 값으로 돌리지 않게). 새 규칙이 지운 규칙의 번호를 다시 받으면 그 번호의 상태를 지우고(이어받으면 바로 알리거나 놓쳤다),
      번호 없는 규칙을 처음 저장하면 이름을 함께 바꿔도 옛 이름의 상태를 옮긴다. PC 로만 맞추는 무음을 처음 보는 값 규칙에 걸 때는
      'PC' 로 고른 것(target=pc)이나 볼 값이 PC 하나인 규칙만 — 값 하나짜리 IP·계정은 모양으로 PC 와 구분할 수 없다.
  22. (8·9차 검토 보완) **배우는 기간은 그 규칙이 보는 소스 기준:** 처음 켠 규칙의 거슬러 배우기가 끝나면, 규칙의 source·channel 조건에
      맞는 소스를 배우는 기간의 시작보다 늦게 처음 받았으면(`agent_streams.first_at`) 그때부터 learn 을 채운다(`repository.fit_first_learning`)
      — DB 전체에서 가장 오래된 로그로 정하면 새로 모으기 시작한 소스(어제 연결한 MSSQL)의 규칙은 하루 치만 배우고 바로 알렸다(1차 검토에서
      설계로 보았으나 운영 문제로 다시 확인). 규칙에 맞는 로그로 정하면 오래 모아 온 소스의 드문 이벤트 규칙(7045 새 서비스)이 '새 소스'가
      되어 공격자의 첫 서비스를 배운 값으로 삼켰다(9차). 소스·채널·PC 를 정하지 않은 규칙은 알 수 없어 예전처럼(DB 전체 기준).
      (10차) agent_streams 는 35일만 두고 마이그레이션 018 전의 것은 없다 — 그 소스를 처음 받은 날이 **표가 아는 가장 이른 날**(min(day))과
      거의 같으면 실제 시작을 모르는 것이라 예전부터 모아 온 것으로 본다(그렇지 않으면 learn 35일 넘는 규칙·올린 직후 만든 규칙이 몇 주 침묵).
      PC 조건도 본다(같은 소스의 다른 서버가 오래됐어도 오늘 연결한 서버의 규칙은 그때부터). 맞추기는 `new_terms_state.fit_pending`
      (마이그레이션 043 — 처음 켤 때·조건을 바꿀 때 켬)으로: 거슬러 배우기가 끝난 뒤 맞추고, 그 소스가 아직 안 들어왔으면 1분마다 다시 봐
      들어오는 때부터 배운다(규칙을 먼저 만들고 에이전트를 나중에 설치하면 정상 값이 모두 알림이었다). (11차) 맞추기 전에는 알리지 않고,
      알릴 차례인 값이 생기면 1분 간격을 기다리지 않고 바로 맞춘다(30초 주기에서 맞추기 직전 주기에 정상 값이 알림으로 나갔다).
      (12차) '표가 아는 가장 이른 날' 예외는 DB 에 그보다 오래된 로그가 있을 때만 — 새로 설치한 서버에서는 그 날이 모든 수집의 시작이다.
      배우는 기간의 시작·길이를 남겨(`learn_from`·`learn_sec`, 마이그레이션 044) learn 을 바꾸면 배우는 중인 기간에 바로 적용한다(줄이면
      끝나고 늘리면 늘어남, 이미 끝났으면 다시 배우지 않음 — 고쳐도 처음 정한 끝이 그대로라 '배우는 중'이 이어졌다).
      (13차) 소스를 정하지 않은 규칙도 DB 가 비었으면(새로 설치) 첫 로그가 들어올 때부터 배운다(지금으로 두면 에이전트를 늦게 붙인 만큼
      배우는 기간이 줄거나 사라졌다 — 기본 RDP 규칙이 그 경우).
      (14차, 규칙을 하나로) **연결된 때가 지금 배우는 기간의 시작(learn_from)보다 늦을 때만 앞으로 늘린다.** 연결된 때 = 소스·PC 를 정하지
      않은 규칙(채널만 정한 규칙 포함)은 DB 의 첫 로그, PC 만이면 agents.first_seen, 소스면 agent_streams(위 예외 포함).
      채널은 보지 않는다 — 오래 연결된 PC 의 조용한 채널을 '새로 연결'로 보아 첫 접속을 삼켰다.
      (15차) **맞추기는 처음 켤 때(과 그 소스를 기다리는 동안)만.** 조건을 바꾸면 앞으로 배우던 것은 그 자리에서 끝내고
      (`learn_until = min(예전, cursor_at)`) 다시 맞추지 않는다 — 옛 조건의 배우는 기간(새 서버의 14일)을 넓힌 조건에 물려주거나, 보관기간으로
      움직인 '첫 로그'로 다시 늘려 몇 주 동안 새 값을 삼켰다. 대신 조건을 바꾼 직후 DB 에 없는 정상 값은 알림이 될 수 있다(놓치는 쪽보다
      알림). 소스 기준에서는 그 소스(정한 PC 안)의 로그가 표의 첫 줄보다 하루 넘게 먼저 있으면 예전부터(표 앞쪽의 빈 날).
      (16차) PC 만 정한 규칙도 같은 검사(목록에서 지웠다 다시 등록된 PC 의 first_seen 은 새로 시작한다). 배우다 상한으로 두지 못한 값의
      받은 시각 구간을 남겨(`dropped_from`·`dropped_to`, 마이그레이션 045) 자리가 생기면 그 구간을 그대로 다시 배운다(learn_until 로 짐작하면
      조건을 바꾼 뒤의 다시 배우기에서 엉뚱한 구간을 찾았다). 거슬러 배우는 중에 learn 을 늘리면 그만큼 더 거슬러 배운다.
      (17차) 배우는 기간을 늘릴 때는 그 기간 안에서 이미 알릴 차례가 된 값도 함께 배운 것으로(`repository.extend_learning`). 무음으로
      보내지 않은 알림의 조합은 last_seen 을 볼 때마다 고쳐 쓴다(한 시간 단위면 무음이 끝난 뒤 한 시간 안에만 이어진 활동을 놓쳤다). 규칙 번호를 바꾸면 상태를 새 번호로 옮긴다(새 번호에 남은 다른
      규칙의 상태는 지움). 무음 탭에서도 처음 보는 값 규칙은 대상 종류(PC 이름·값 조합)를 고른다.
- **대안:** 수집 때 seen_terms 갱신 — 규칙마다 수집 쿼리가 늘고(ADR-046 의 13% 교훈) 규칙을 바꾸면 지난 값을 다시 배울 수 없다. 발생 시각 기준 — PC 시계가 틀리면
  구간을 건너뛴다. 메모리(집합) — 다시 시작하면 모두 '처음'. 상한에서 오래된 값 버리기 — 거짓 '처음 보는 값'. 모두 기각.
- **알려진 한계:** 배우는 기간에 이미 있던 공격자 출발지는 '본 값'이 된다(모든 new terms 방식의 한계 — 켜기 전 점검을 권함). 미리보기는 앞의 며칠(최대 7일)로
  배웠다 치는 근사다(앞의 하루). account 는 공격자가 이름을 정하는 이벤트(4625·IIS·sshd)에서 다른 표기로 비켜 갈 수 있어 화면이 `user` 를 권한다.
  조건을 바꿔 다시 배우는 것은 learn 까지 — history 안이지만 learn 밖에서만 본 값은 새 값으로 나올 수 있다. 경로·조회 범위는 처음 본 PC 하나로 본다.

## ADR-062 계정 표기 통일은 읽을 때 만드는 열쇠(wlm_user_key) + 새 검색 키 account:
- **상태:** 채택 (2026-11-02). BACKLOG B-54. B-47(처음 보는 값)·B-67(개체 페이지)·B-72 의 선행. ADR-033(검색 문장)·ADR-050(행을 고치지 않음) 보완.
- **배경:** 같은 사람이 소스마다 다르게 저장된다 — Windows `TargetUserName` 은 `kim`, IIS·MSSQL 은 `HOSP\kim`, Kerberos 는 `kim@HOSP.LOCAL`.
  `user:` 검색·distinct·상위 값이 같은 사람을 여러 명으로 봤다.
- **결정:**
  1. 열쇠 = SQL `wlm_user_key(username)`(마이그레이션 038, IMMUTABLE·표현식 하나라 플래너가 펼침)·Python `querylang.account_key`·JS `accountKey` — 세 곳이 한 글자도 같다
     (케이스 표 `account_key`, node↔Python 교차 퍼징 3,000개, SQL↔Python 3,000개). 끝의 역슬래시를 빼고 본 마지막 `\` 뒤 → 첫 `@`(둘째 글자 이후, 뒤에 `.`)의 앞 →
     A-Z 만 소문자(lower() 는 glibc 로캘이라 이미지를 올리면 색인이 조용히 깨진다). 두 번 해도 같다(설계안의 '마지막 @'·'끝이 \ 면 그대로'는 `p\q@r.s\`→`p\q`→`q`
     로 두 번 하면 달라 고쳤다). 컴퓨터 계정 `$` 는 지우지 않는다(noPac 이 노리는 혼동). 이 함수는 고치지 않는다 — 뜻을 바꾸면 새 이름·새 색인.
  2. **열을 더하지 않고 읽을 때 만든다** — `events` 행을 고치지 않으니 다이제스트·보관 파일 형식이 그대로이고, 옛 행·복원한 달도 같은 열쇠다.
  3. 새 키 `account:` — `user:` 는 그대로 정확히(배포된 규칙·예외 `-user:` 의 뜻이 바뀌지 않게). 주소 파라미터 `account=`·`match.account` 도 다른 키처럼
     (검토 보완: 처음에는 문장에만 두어 상위 값 위젯을 누르면 조건이 빠진 검색이 열렸고, 알림 링크가 문장 한도 500자를 넘었다).
     group_by·distinct·상위 값·자동완성은 `account` 를 받는다(`COLUMN_EXPR`). 계정 열쇠도 개인정보 — 상위 값·자동완성은 접속기록.
  4. **탐지에서 `-account:` 거부** — IIS cs-username·sshd·4625 TargetUserName·MSSQL 18456 처럼 공격자가 정하는 이름에도 열쇠가 걸려 `svc_backup@evil.co` 로
     로그인을 시도하면 `-account:svc_backup` 예외로 빠진다. 규칙·규칙이 쓰는 저장한 검색·예외 어디서든(`Rule.event_filter`·규칙 검증·예외 API). 포함·묶음은 괜찮다.
  5. 색인 하나로 둘 다: `events_account_ts_idx (wlm_user_key(username), ts DESC) WHERE username IS NOT NULL`. `user:` 도 `(username IS NOT NULL AND
     wlm_user_key(username) = ANY(열쇠) AND username = ANY(표기))` 로 이 색인을 쓴다(뜻은 같다 — 이름이 같으면 열쇠도 같다). 예전 `events_user_ts_idx` 를 함께 두면
     수집 쓰기가 10% 느려(PERFORMANCE.md §2.10) 모든 파티션에 계정 색인이 붙으면 지운다. `test_where_snapshot` 의 user 두 줄은 이 때문에 일부러 바꿨다.
  6. 마이그레이션은 부모 색인만(`ON ONLY`, 카탈로그만) — 있던 월 파티션은 서버가 뒤에서 하나씩 `CREATE INDEX CONCURRENTLY` 후 `ATTACH`(최신 달부터, 한 시간마다,
     자문 잠금 727_007, INVALID 조각은 지우고 다시). 마이그레이션 트랜잭션에서 한꺼번에 만들면 행 1억 개에 기동이 몇십 분 멈춰 설치 스크립트의 기동 대기(2분)를 넘는다.
     새 파티션(다음 달·복원)은 PostgreSQL 이 바로 함께 만든다. 다 붙기 전에는 운영 준비도 '계정 표기 색인 n/m'(warn).
  7. (검토 보완) **파티션마다 식 통계**(`CREATE STATISTICS <파티션>_account_stx ON (wlm_user_key(username))` + ANALYZE) — 부분 색인의 통계는 플래너가 쓰지
     않아 늘 0.5% 로 어림해 40% 인 `SYSTEM` 도 색인으로 훑었다(예전 색인을 지운 뒤 `user:` 가 수백 배 느려질 수 있었다). 색인 붙이기(ATTACH)는 잠금 대기
     5초 — 백업이 읽는 동안 기다리면 수집·검색이 줄을 섰다. 규칙 시험기·`group_by: user` + `distinct: account`(늘 1개) 거부·계정 묶음 알림의 '예외로…' 숨김.
- **알려진 합쳐짐:** 로컬·도메인의 같은 이름, 바깥 주소 `kim@gmail.com` 과 `kim`, SQL 로그인과 같은 이름의 AD 계정 — `user:`·`f.EventData.TargetDomainName:` 으로 가른다.
  **합치지 않음:** UPN 앞부분과 sAMAccountName(사번 로그인), SID 와 이름, `LocalSystem` 과 `SYSTEM`, 비ASCII 대소문자 — B-53(목록·자산 등록부)에서.
- **대안:** 수집 때 채우는 열 — 옛 행이 보관기간 내내 NULL 이거나 금지된 UPDATE, 보관·다이제스트 형식이 바뀜. `GENERATED STORED` — 표 전체를 다시 씀. `user:` 의 뜻을 바꿈 —
  배포된 `-user:` 예외·distinct 규칙의 수가 조용히 바뀜. 모두 기각.

## ADR-061 이벤트 보관 등급은 보관 파일을 만들 때 나누고, 파일마다 약속한 기간보다 일찍 지우지 않는다
- **상태:** 채택 (2026-11-02). BACKLOG B-70. ISMS 2.9.4. ADR-016(로그 로테이션)·ADR-040(기록 종류별 보관기간)·ADR-047(외부 복제) 보완.
- **배경:** 로그 보관기간은 `WLM_RETENTION_DAYS` 하나라 민감정보 처리 시스템의 접속기록을 2년 두려면 IIS·상세 로그까지 2년이 됐다(보관 공간이 크게 는다).
- **결정:**
  1. `config/retention.yaml` 의 등급(id·name·검색 문장·keep_days). 한 로그가 여러 등급에 맞으면 **가장 긴 쪽**(우선순위 칸 없음 — 접속기록이 '웹 요청'
     등급에도 맞아 짧아지는 실수를 구조로 막는다), 어디에도 안 맞으면 기본(`WLM_RETENTION_DAYS`).
  2. 나누는 때는 **보관 파일을 만들 때**(DB 보관기간이 지난 달). DB 는 월 파티션째 지운다 — `events` 행을 지우면 수집 로그 다이제스트(ADR-050)가
     '고쳐짐'으로 잡고 파티션 DROP 보다 훨씬 비싸다. 그래서 등급 기간은 DB 보관기간보다 짧게 할 수 없다(짧으면 파일을 만들지 않을 뿐, 화면이 안내).
  3. 파일은 `events_YYYY_MM.<id>.jsonl.gz` + 메타(tier·keep_days·query·SHA-256). 만료 = 그 달 끝 + max(만들 때 기간, 지금 설정의 같은 등급 기간) —
     늘리면 이미 만든 파일도 늘고, 줄이거나 등급을 지워도 만들 때 약속한 기간보다 일찍 지우지 않는다. 기본 파일은 예전처럼 지금의 `WLM_RETENTION_DAYS`.
     기본 기간이 이미 지난 달(더 긴 등급 때문에 보관하는 달)은 기본 파일을 만들지 않고, 만들 때 이미 기간이 끝난 등급의 로그는 쓰지 않고 센다(`skipped`).
  4. 외부 복제본(B-17)의 등급 파일은 날짜로 계산하지 않고 **api 의 파기 기록**(`retention.delete_archive`, 등급·기간 포함)이 있을 때만 지운다 — 기간이
     설정으로 바뀌는 것을 backup.sh(busybox)가 따로 계산하면 원본보다 먼저 지울 수 있다. 기본 파일은 예전처럼 이름의 달로.
  5. 설정이 틀리면(YAML·id·검색 문장·기간) **보관 파일 만들기·삭제를 멈춘다** — 로그는 DB 에 그대로, 감사로그 `retention.archive_failed`(하루 한 번)·
     법정 보관 경고(화면·점검 보고서·운영 준비도). 틀린 설정으로 접속기록을 짧은 등급에 넣거나 일찍 지우는 것보다 DB 가 커지는 쪽이 되돌릴 수 있다.
  6. 화면은 조회만(등급 표·파일마다 등급·만료). 설정 파일은 git·백업 설정 묶음에 함께 남는다.
  7. (검토 보완) **기본 메타는 늘 완료 표시** — 기본 파일이 없는 달(기본 기간이 이미 지남)도 메타만 쓰고, 기본 파일이 먼저 만료돼도 그 달의 등급 파일이
     남아 있는 동안은 메타를 표시(`file: null`, `expired_default`)로 남긴다. 표시가 있는 달은 복원했다가 보존 기간이 끝나도 다시 보관하지 않고 지우기만 —
     표시가 없어 지금 설정으로 다시 보관하면 등급 파일을 덮어써 행이 사라지고(문장을 좁혔을 때) 약속한 기간이 줄었다(기간을 줄였을 때). 만들다 멈춘 달을
     다시 만들 때도 등급 메타의 기간은 앞서 약속한 것보다 줄이지 않는다.
  8. (검토 보완) 파기 기록을 **먼저**(`required=True`, 실패하면 지우지 않고 다음 주기) 남기고, 등급 파일은 지운 표시 파일(`<이름>.destroyed.json`)도 남긴다 —
     backup.sh 는 그 표시나 감사로그가 있으면 복제본을 지운다(DB 를 백업으로 되돌려 감사로그의 파기 기록이 사라져도).
  9. (검토 보완) 설정 읽기: UTF-8(BOM 허용)만, 같은 키 두 번·알 수 없는 키·맞을 수 없는 문장은 오류(조용히 등급 0개가 되어 접속기록이 기본 기간에 지워질 수 있었다),
     읽기·해석 예외(CP949·없는 날짜·깊은 중첩)는 서버를 멈추지 않고 설정 오류로. 기본 파일의 예시는 `tiers:` 아래 주석으로(풀어도 키가 겹치지 않게).
     민감정보 처리 시스템이면 730일 이상 등급이 있을 때 2년 미달 경고를 내지 않는다(그 등급이 맡는지 확인하라는 안내로). 메시지 접기는 로그마다 한 번.
  10. (3차 검토) 격리한 수집 레코드(`ingest_quarantine`)는 등급을 가릴 수 없어(등급 문장이 보는 칸이 없음) **가장 긴 등급 기간**까지, 설정이 틀리면 지우지 않는다.
     복원은 임시 표에 모은 뒤 `ON CONFLICT DO NOTHING` — 만들다 멈춘 달을 등급 이름을 바꾼 뒤 다시 만들면 같은 행이 두 파일에 있었다. 같은 이름의 파일을 다시 만들면
     지운 표시를 치우고, backup.sh 는 원본이 있는 등급 파일을 지운 것으로 보지 않으며, 등급 파일이 남은 달의 기본 메타(완료 표시)를 복제본에도 둔다.
     만료 파일은 지운 뒤 표시를 쓴다(디스크가 차도 정리가 멈추지 않게). 기본 파일 복제본의 만료는 api 처럼 UTC 달 시작으로.
- **대안:** 저장한 검색(B-64)으로 등급 고르기 — 화면에서 문장이 바뀌면 보관기간이 조용히 바뀐다, 다음에 보호된 검색만으로 검토. 행 단위 삭제 — 다이제스트·비용 때문에 기각.
  등급마다 다른 DB 보관기간(별도 표) — 파티션 구조를 바꿔야 해 기각. 우선순위 칸 — '긴 쪽' 규칙보다 실수하기 쉬워 기각.
- **남은 것:** 화면에서 등급 편집, 보호된 저장한 검색으로 고르기, 의료법 개정(B-39) 보관기간 확정 뒤 기본 예시.

## ADR-060 접속기록 점검 결과서는 근거 스냅샷 + 항목별 결과 + 2단계 결재 (권한 검토와 같은 모양)
- **상태:** 채택 (2026-11-02). BACKLOG B-72 3단계. ISMS 2.9.5. ADR-032(점검 보고서)·ADR-058(권한 검토) 보완.
- **배경:** 점검 보고서는 숫자를 모아 보내고 '확인' 한 번만 남았다. 접속기록 점검은 항목마다 적정·부적정과 조치, 점검자·책임자 결재가 있어야 증적이 된다.
- **결정:**
  1. 점검 항목 8개(`app/inspection.CHECKLIST`)와 근거 조항. 시작할 때 그 기간의 근거(다른 화면·보고서와 같은 원천 — 보관기간 경고·위·변조 상태·내려받기 사유·
     감사로그의 로그인·실패·권한 작업·개인정보 조회 접속기록)를 `inspections.items` 에 스냅샷 — 나중에 숫자가 바뀌어도 그때 본 것이 남는다.
  2. 판단은 사람이 한다 — 시스템은 근거와 요약만. 결과·서명·승인·반려는 `inspection_entries` 한 줄씩(트리거로 고칠 수 없음), 상태는 줄을 읽어(`state`),
     쓰기는 점검 행을 잠근 채 다시 판단. 부적정은 조치 필수, 서명한 사람과 다른 사람이 승인.
  3. 권한은 점검 보고서와 같은 `reports.view`(조회 범위 없는 사용자) — 관리자가 아닌 개인정보 보호 담당자도 점검자로.
  4. 주기는 내부 관리계획 값(기본 31일) — 고시가 2026-10-31 부터 내부 관리계획으로 넘겼다(ADR-048). 마지막 승인한 점검의 **기간 끝**부터 센다.
  5. 업무시간(평일 08~19시)·대량 조회 기준(300회)은 근거 요약의 기준일 뿐 판정이 아니다 — 병원마다 다르면 코드 상수를 바꾼다.
  6. (검토 보완) 기한은 기간 끝 + 한 주기 + **여유**(주기 절반, 최대 14일) — 기간 끝에서 31일만 재면 지난달 점검을 그달이 끝난 뒤 1~4일 안에 승인까지 마쳐야 했다.
     위·변조 근거는 **기간 안의** 감사로그(검증 실패·앵커 실패·만료 삭제 멈춤·보관 때 불일치·백업·복구 시험·복제 실패·DB 복원, 하루 넘게 빈 구간)로 — 지금 상태만 보면
     기간 중에 있었다가 풀린 실패가 '정상'으로 남았다. 같은 기간의 승인 전 점검은 하나만(지울 수 없어 영영 '진행 중'), 기간은 하루 이상·끝은 지금까지, 점검 열람은 접속기록.
     (5차) 기간 시작은 2000년 이후(1년은 UTC 기원전이 되어 저장 뒤 읽을 때마다 실패 — 행을 지울 수 없어 화면이 영영 깨졌다). 빈 구간은 기간 시작(설치 뒤)부터도 재고
     빈 구간·기록 없음을 실패 기록보다 앞에 둔다(스냅샷 30건·요약 3건에서 빠지지 않게).
     2단계 결재는 '서명한 사람 ≠ 승인한 사람'만 본다 — 결과를 적은 사람이 승인해도 다른 사람이 그 결과에 서명해야 하고 항목마다 적은 사람이 남는다(검토에서 정책 문제로 기각).
- **남은 것:** 한글 문서(HWPX, B-83), 점검 항목 사용자 정의, 심사 증적 묶음(B-73)에 결과서, 점검 취소(지금은 겹쳐 시작을 막기만).

## ADR-059 수집 품질은 채널별 수신 집계 줄의 칸으로, 표시는 저장하지 않는 Event.flags
- **상태:** 채택 (2026-11-02). BACKLOG B-56 1단계. ADR-046(채널별 수신) 보완.
- **배경:** 규칙이 조용히 데이터를 못 받는 두 번째 경로는 '들어오는데 해석이 깨진 것'이다 — Windows 업데이트로 이벤트 버전이 바뀌어 템플릿 이름이 어긋남,
  IIS 열 순서를 몰라 원문 그대로 둔 줄, 정규화 오류. 늦게(밀린 로그)·미래 시각(PC 시계)으로 오는 것도 몰랐다.
- **결정:**
  1. 정규화기가 `Event.flags`(parse_error·unparsed·template_mismatch)를 단다 — **저장하지 않는다**(원본·raw 그대로, 다이제스트 영향 없음). 수집 트랜잭션이 센다.
  2. 세는 곳은 이미 있는 `agent_streams` 의 (PC, 소스, 채널, 날) 줄에 칸 6개 — 문장 하나를 그대로 두어 수집 비용이 묶음당 약 0.75ms(PERFORMANCE.md §2.9).
     지연은 받은 시각 기준 1시간 넘게 앞(late)·5분 넘게 뒤(future)와 가장 늦음(초). 35일 뒤 함께 지워진다.
  3. 템플릿 불일치 = 서버 템플릿이 있는 이벤트인데 StringInserts 수가 다르고 에이전트가 이름 맵을 보내지 않은 것(`win_templates.mismatch`). 템플릿이 없는 이벤트는 문제가 아니다.
  4. 판단·문구는 `app/quality.py` 한 곳(보고서·준비도). 늦게 온 로그는 장애 뒤 흔하므로 100건 이상·20% 넘을 때만 '점검 필요'.
  5. (검토 보완) 템플릿 불일치는 **실측한 버전**(`win_templates.VERIFIED`, 윈도 CI 레코드와 대조)·VERSIONED 버전인데 길이가 다르거나 **처음 보는 새 버전**의
     길이가 다를 때만 — 옛 버전은 앞부분이 같아 표시하지 않는다(Server 2016·2019 의 4697 v0 이 매일 남았다). 보고서는 날(UTC)마다 **정오가 기간 안인 날**만
     센다 — 경계를 둘 다 넣어 한국 시간 하루 보고서가 이틀을 세고 같은 문제가 이틀 연속 나왔다(시간대 차이만큼 어긋남).
- **남은 것 (2단계):** EventRecordID 누락(채널 커서·하트비트 뒤 1시간 대기, B-28 GPO 배포 뒤), 수집기가 버리는 PRI 없는 syslog 줄(B-23), 수집 PC 화면에 PC 별 품질.

## ADR-058 권한 검토는 시작 때의 스냅샷 위에 고칠 수 없는 결재 줄
- **상태:** 채택 (2026-11-02). BACKLOG B-72 2단계. ISMS 2.5.6. ADR-032(점검 보고서 증적) 보완.
- **배경:** 계정·권한이 아직 필요한지 분기마다 보는 증적(누가 언제 무엇을 보고 유지·회수했나)이 없었다 — 사용자 화면과 감사로그로 '보았다'고 말할 수만 있었다.
- **결정:**
  1. 시작하면 그때의 모든 계정(꺼진 계정 포함)·역할·그룹·권한·조회 범위·마지막 사용·2단계 인증을 `access_reviews.users`(JSONB)로 남기고 그 목록으로 검토한다 —
     검토하는 사이 권한을 바꿔도 무엇을 보고 판단했는지가 남는다. 사용자 표를 참조하지 않아 계정을 지워도 기록은 남는다.
  2. 결정(유지·회수·조정, 회수·조정은 사유)·서명·승인·반려는 `access_review_entries` 에 한 줄씩, 트리거로 수정·삭제·TRUNCATE 금지(감사로그·알림 처리 기록과 같음).
     같은 계정을 다시 정하면 줄이 하나 더 — 마지막 줄이 지금 결정. 상태는 줄을 차례로 읽어 정하고(`review.state`, DB 없이 시험), 쓰기는 검토 행을 잠근 채 다시 읽어 판단.
  3. 2단계 결재: 켜진 계정을 모두 정해야 서명, **서명한 사람이 아닌** 관리자만 승인·반려(반려는 사유, 다시 진행 중). 승인하면 끝.
  4. 회수는 결정만 남긴다 — 계정을 자동으로 끄지 않는다(사람이 사용자 화면에서, 감사로그). 대신 승인한 검토의 회수인데 켜진 계정을 운영 준비도(bad)·점검 보고서가 알린다.
  5. 주기는 내부 관리계획의 값(`WLM_ACCESS_REVIEW_DAYS`, 기본 92일 = 분기) — 고시가 주기를 정하지 않는다(ADR-048 과 같은 판단). 0 이면 주기 알림만 끈다
     (승인한 회수인데 켜진 계정은 그래도 알림 — 검토 보완: 운영 준비도가 'skip' 으로 가렸다).
  6. 보관: 지우지 않는다(검토마다 몇 KB). 결과 CSV 는 개인정보 내려받기와 같이 사유 필수·감사로그(`access_review.export`).
- **남은 것:** 접속기록 점검 결과서(항목별 적정/부적정·2단계 결재 — 같은 표 모양을 쓸 수 있음), 외부 업체·서비스 계정 점검, 심사 증적 묶음(B-73)에 권한 검토 결과.

## ADR-057 묶음 전송은 전송기가 보낼 때 — 사람이 읽는 받는 곳만, 증적은 알림마다
- **상태:** 채택 (2026-11-02). BACKLOG B-41. ADR-029·045 보완.
- **배경:** 대상 키마다 알림 한 행·전송 한 통이라 윈도 업데이트 재부팅 물결로 300대에서 같은 오류가 나면 메일 300통, 두레이는 주소별 1.1초 간격이라
  5분 넘게 걸리며 같은 때 난 다른 심각 알림이 묻혔다.
- **결정:**
  1. 묶음은 **평가가 아니라 전송기**에서 — 알림 행·전송 행(받는 곳마다)은 지금처럼 하나씩 남고(ADR-029 증적), 전송기가 같은 (받는 곳, 규칙, action) 의 대기 행을
     한꺼번에 잡아 한 통으로 보낸다. 엔진의 평가 주기는 영향받지 않는다. 묶음 전송 기록 표(`notifications`)는 두지 않는다 — 같은 통의 알림은 같은 sent_at·`batch_size`.
  2. 시간은 Alertmanager 와 같은 뜻: `group_wait`(처음 알림부터 모으는 시간, 기본 30초)·`group_interval`(같은 묶음을 마지막으로 보낸 뒤 다음 통까지, 기본 5분).
     **심각은 모으지 않고 간격 1분** — 한 통이 이미 갔으니 같은 규칙의 다음 대상은 1분 안에. 규칙·경로별 시간은 두지 않는다(필요해지면 경로 단위로).
     모으는 동안은 `next_attempt_at` 을 미래로 미루기만 한다(시도로 세지 않음) — 알림 기능 상태의 '밀린 전송'이 되지 않는다.
  3. **사람이 읽는 받는 곳만 묶는다**(메일·text·slack·teams·dooray·jandi). json 웹훅·Oracle 은 알림마다 `dedup_key`·알림 번호로 사고를 여닫는 연동이라
     묶으면 기계가 한 건만 본다 — 지금처럼 알림마다, 모으는 시간도 없이.
  4. 보내기 직전에 행마다 다시 본다(`_stale`·최소 수준) — 모으는 사이 자동 해결·확인된 알림은 '건너뜀'으로 빠지고 나머지만 묶는다. 실패하면 묶음째 같은 때 다시.
  5. 묶음 메시지는 대상 목록(20줄 + '외 n건')과 그 규칙의 알림 목록 링크. 혼자면 예전과 같은 알림 — 스냅샷이 바뀌지 않는다.
  6. 설정을 늘리면(늦게 감) 탐지 약화(ADR-043). 0 이면 묶지 않음(예전 그대로).
  7. (검토 보완) **내장 알림(설정 변경·관리 작업·감시)은 묶지 않는다** — 알림마다 무엇이 바뀌었나가 본문인데 묶음 본문에서 빠졌고, 범위 사용자·메일만 받는
     사람은 화면에서 볼 수도 없었다. 받는 쪽이 묶음을 알림 하나의 내용 때문에 거절하면(웹훅 400·413·422, SMTP 5xx 데이터 거절) **반으로 나눠 다시 보낼 차례로**
     돌린다(`alert_deliveries.split_key` = 그 반쪽 첫 알림 번호, 마이그레이션 037, 시도로 세지 않음) — 반쪽끼리만 다시 묶여 나쁜 알림 하나에 약 2·log2(n)통이고,
     혼자 남은 알림만 시도를 쓴다. 그 자리에서 나눠 보내면 전송 자리를 쥐고 오래된 잡힘 정리가 보내는 중인 행을 풀었고(2차 검토), 하나씩(035 의 solo,
     지금은 쓰지 않음) 보내면 300건 거절이 300통이 돼 묶음 전송의 뜻이 사라졌다(3차 검토). 나머지 응답(401·404·410·408·429·넘김·5xx·SMTP 4xx·발신자 거절·
     시간 초과)은 받는 곳 문제(target_down)라 묶음째 미룬다. 403 은 토큰이 막혔거나 방화벽·DLP 가 본문을 막았거나라 여러 건이면 나누고, 혼자도 403 이면 받는 곳 문제.
     (4·5차 검토) 403 이 본문 때문인지는 **내용 없는 확인 메시지**(테스트 알림 모양)로 가린다(`_content_403`): 통하면 받는 곳은 살아 있으니 본문 때문 —
     여러 건은 나누고 한 건은 그 알림만 실패(이 곳의 다른 알림은 미루지 않음), 한 시간 동안 다시 묻지 않는다(확인 메시지는 채널에 보인다). 거절되면 토큰·주소 문제라
     보통 실패(묶음째 다시 보낼 차례·다른 알림 미룸), 10분 동안 다시 묻지 않는다. 403 마다 나누면 토큰이 막힌 곳에서 500건이 3분에 272통·고친 뒤 271통이었고,
     '잘 되던 곳의 첫 403 만 나누기'(4차)는 막힌 알림이 두 반쪽에 다 있거나 앞서 다른 실패가 있으면 좋은 알림까지 버렸다(5차).
     (6차) 본문 문제로 보는 한 시간 안에도 보낸 것 없이 403 이 12번 이어지면 다시 확인한다(통하면 다음 기준은 두 배) — 그 사이 토큰이 막히면
     64건 묶음이 127통·고친 뒤 64통이었다. 확인이 거절되면 본문 문제 판단을 바로 끝낸다.
- **대안:** 평가에서 묶어 알림 행 하나에 여러 대상 — 처리 상태·종료 분류·해소 통지·에스컬레이션이 모두 대상마다라 기각. Alertmanager 를 붙이기 — 서비스·설정이 하나 더(비교 §6).

## ADR-056 받는 곳 경로는 규칙 notify 위의 순서 있는 목록
- **상태:** 채택 (2026-11-02). BACKLOG B-26.
- **배경:** 규칙마다 `notify` 목록이라 새 팀(DB팀·보안팀·EMR 협력사)을 더하려면 규칙을 하나씩 고쳐야 했다.
- **결정:**
  1. `alerts.yaml` 의 순서 있는 `routes:` — `{match: {group, tags, severity, rules, hosts}, notify, continue, replace}` (Alertmanager route 를 평평하게). 트리가 아니라 목록 — 병원 규모에는 충분하고 읽기 쉽다.
  2. 규칙의 `notify` 는 기본 받는 곳으로 그대로(호환). 경로는 더하거나(replace 면 대신), continue 가 아니면 멈춘다.
  3. 받는 곳은 **발생 때** 정해 알림마다 전송 행으로 남고(ADR-029·045), 거친 경로 이름을 payload 에(증적). 해소 통지도 같은 계산.
  4. `hosts` 는 대상 이름이 PC 일 때만(PC 로 묶는 규칙·끊김 규칙) — IP·사용자로 묶는 규칙의 대상 이름을 PC 패턴으로 견주지 않는다.
  5. 경로 변경은 순서까지 뜻이 있어 넓힌 것만인지 단정하기 어렵다 — 빼거나·바꾸거나·가리거나·갈아 끼우면 약화로 알린다.
  6. (검토 보완) 받는 곳 목록은 규칙 notify 가 아니라 **경로까지 계산한 것**(`AlertConfig.reachable`·`delivery_targets`)으로 본다 — 시험 전송·알림 기능 상태·
     운영 준비도·관리 작업 알림·설정 변경 알림의 받는 곳. PC 패턴은 패턴마다 맞는 대표 이름 하나로 계산한다(모든 PC 를 셀 수 없음).
     규칙의 태그·묶음·심각도·이름을 바꿔 경로로 받던 곳이 빠지면 약화(`route_targets`), 남은 경로끼리의 순서는 늘 비교. 같은 받는 곳을 두 번 쓰면 한 번으로.
- **남은 것:** 사용자 그룹 구성원에게 메일(사용자 이메일 칸)을 경로의 받는 곳 종류로, 규칙 편집 미리보기에 '이 규칙 → 받는 곳 (경로)'.

## ADR-055 에스컬레이션은 기존 전송 대기열의 한 줄, 판단은 보낼 때
- **상태:** 채택 (2026-11-02). BACKLOG B-43 1단계.
- **배경:** 누구나 확인할 수 있는데(ADR-029) 확인 뒤나 확인 전이나 아무 타이머가 없어 새벽 3시의 '관리자 그룹 구성원 추가'·'보안 감사 로그 삭제'가 아침까지 묻혔다.
- **결정:**
  1. 정책은 `alerts.yaml` 의 `escalations`(심각도·규칙으로 고르고 단계마다 after·unless·notify). 규칙과 같은 파일이라 판본·약화 판단·감사로그(ADR-043)를 그대로 탄다.
  2. 엔진은 평가 주기마다 기한이 된 단계를 **기존 전송 대기열에 한 줄**로 넣는다(action `escalate:<초>:<조건>`, 기본 키로 단계마다 한 번).
     재시도·받는 곳 상태·최소 수준·전송 기록이 알림과 같다. 정책 스냅샷을 알림에 남기지 않는다 — 정책을 고치면 아직 넣지 않은 단계는 새 정책을 따른다.
  3. 확인·해결은 넣을 때와 **보낼 때** 모두 본다(`dispatcher._stale`) — 그 사이 확인했으면 보내지 않는다. 남은 단계를 지우지 않으므로 처리 기록이 거짓이 되지 않는다.
  4. 무음 중 알림·관찰 모드·내장 알림은 제외. 기한이 6시간 넘게 지난 단계는 넣지 않는다(새 정책·서버 중단 뒤 폭주 방지).
  5. (검토 보완) 대기열의 '하루 지나면 버림'은 다시 알림을 **넣은 시각**으로 잰다(해소 통지와 같음 — 발생 시각으로 재면 '하루 미해결' 단계가 넣자마자 버려졌다).
     Oracle 은 `:escalation` 바인드를 쓴 SQL 에만 보낸다(기본 INSERT 는 같은 알림 번호라 중복으로 사라지고 '보냄'으로 남았다). 단계를 resolved → acked 로 바꾸는 것도 약화.
  6. (2단계) `ack_timeout` — 확인만 하고 잊힌 알림: 정책마다 시간, 넘으면 시스템이 '처리 안 됨'으로 되돌리고(처리 기록 `ack_timeout`, 사람이 다시 연
     `reopen` 과 달리 자동 해결 대상) 첫 단계 받는 곳에 한 줄(`acktimeout:<초>:<회차>`, 마이그레이션 034). 되돌림·기록·대기열은 한 트랜잭션, '아직 확인 상태이고
     그 확인이 기한 전'일 때만 — 그 사이 해결·다시 확인을 덮지 않는다. PagerDuty 처럼 단계를 처음부터 다시 돌리지는 않는다(단계 키가 알림마다 한 번).
     (검토 보완) 다시 열기 전에 기한이 된 미확인 단계는 보내지 않는다(그 기한에는 확인돼 있었다 — 틀린 '아무도 확인하지 않음'과 겹친 알림),
     기한이 지난 지 6시간 넘은 확인 알림은 다시 열지 않는다(단계와 같은 상한 — 정책을 새로 켜거나 줄일 때 몇 달 묵은 알림이 쏟아지지 않게).
- **남은 것:** 월별 당직표 CSV → 가상 받는 곳 '당직자', 점검 창(B-42) 존중, 정책 화면 편집.

## ADR-054 알림 종료 분류는 해결의 일부, 묶어 보기는 기존 '함께 해결' 위에
- **상태:** 채택 (2026-11-02). BACKLOG B-44. ADR-029 보완.
- **배경:** 알림 이력은 발생마다 한 행이라 장애 때 같은 규칙이 수십 PC 에서 터지면 다른 심각 알림이 묻혔고, 닫을 때 정탐·오탐을 남기지 않아 어떤 규칙을 고치거나 끌지 데이터로 정할 수 없었다.
- **결정:**
  1. 해결(`resolve`)은 종료 분류가 **필수**(422). 다섯 가지(정탐-의심 행위·정탐-예상된 관리 작업·오탐-규칙 문제·오탐-데이터 문제·판단 불가) + 엔진의 '자동 해소'.
     분류는 알림(`alerts.resolution`, 지금 값)과 처리 기록(`alert_notes.resolution`, 그때 값 — 고칠 수 없음)에 둘 다. 다시 열면 알림의 값만 비운다.
     옛 해결 알림은 비워 둔다(판단을 지어내지 않음). 자동 해결된 옛 알림만 '자동 해소'로 채운다(확실하므로).
  2. 묶어 보기는 새 처리 경로를 만들지 않는다 — 묶음의 가장 최근 알림 + `with_related`(같은 규칙·대상 전부)가 곧 묶음 처리다. 감사로그에 대상 수.
     조회 범위는 GROUP BY·LIMIT 전에(목록과 같은 pairs).
  3. (검토 보완) 묶음의 심각도·누를 알림은 해결 안 된 것을 먼저 — 가장 최근 알림이 해결됐어도 남은 알림을 열어 묶음을 해결할 수 있게.
  4. 오탐률 = 오탐 / (정탐 + 오탐), 최근 90일. 판단 불가·자동 해소·분류 없는 옛 알림은 빼고 표본 수와 함께 보인다. 모든 알림을 센 숫자라 조회 범위가 없는 사용자만.
- **대안:** 분류를 선택 사항으로 — 대부분 비워 두게 되어 통계가 쓸모없어 기각. 묶음 전용 상태 — 알림마다 증적(ADR-029)과 이중 관리라 기각.

## ADR-053 규칙 시험기는 매처를 조건별로 풀고, 관찰 모드는 무음 경로로
- **상태:** 채택 (2026-11-02). BACKLOG B-52.
- **배경:** 규칙 미리보기는 24시간 건수만 보여 줘 특정 로그가 왜 안 걸렸는지(경로 오타·제외 조건·값 형식) 알 수 없었고, 새 규칙을 켜면 바로 메일이 나갔다.
- **결정:**
  1. `EventFilter.explain(event)` 가 `matches` 의 조건 하나하나를 `{key, op, expected, actual, ok}` 로 돌려준다. 따로 구현하되 **케이스 표 전체 × 조회 범위 3종 × 고정 이벤트**로
     '모두 ok ⇔ matches' 를 시험한다(`test_explain_agrees_with_matches`) — matches 를 explain 위에 다시 쓰면 실시간 경로가 느려진다.
  2. 시험 API 는 엔진과 같은 조건(`engine.rule_filter` — 저장한 검색·걸린 예외)을 쓰고, 원본 붙여넣기는 수집과 같은 정규화(`normalize_safely`, Windows 템플릿 포함)를 거치되 저장하지 않는다.
     저장된 이벤트를 시험하면 실제 사용자·IP 를 돌려주므로 상세 보기와 같은 접속기록(`events.view`)을 남긴다. SQL 로 다시 세지 않는다 — 건수·기간은 미리보기의 몫.
  3. 관찰 모드(`mode: observe`)는 알림을 **기록**하고 전송만 건너뛴다(무음과 같은 길: `alert_deliveries.status = skipped`, 사유 '관찰 모드', payload `observe`).
     그래서 재알림 간격·알림 이력·처리가 실제와 같고, 승격하면 바로 다음 알림부터 보낸다. 해소 통지도 보내지 않는다. 시험 발송은 받는 곳 시험이라 보낸다.
  4. (검토 보완) 시험기는 조건 말고도 묶음 기준(`group_by`) 값이 있는지 본다 — 값이 없는 로그는 엔진이 세지 않는다. 붙여 넣은 원본의 짝 없는
     서로게이트는 수집처럼 U+FFFD 로.
  5. 켜진 규칙을 관찰로 돌리는 것은 끄는 것과 같으므로 탐지 약화(ADR-043 판본·관리자 알림), 운영 준비도에 '관찰 모드 규칙'으로 남긴다.
- **대안:** 관찰한 발생을 별도 표에 — 재알림 간격·이력 로직을 둘로 나눠야 해 기각. 새 규칙을 기본 관찰로 — 알려진 공격을 막으려 만든 규칙이 조용해질 수 있어 화면 기본은 '바로 보냄'(팩 규칙의 기본 관찰은 B-51 에서).

## ADR-052 저장한 검색: 이름으로 재사용, 규칙이 쓰면 탐지 조건으로 다룸
- **상태:** 채택 (2026-11-02). BACKLOG B-64.
- **배경:** 정기 점검(ISMS 2.9.5)의 반복 검색을 담당자마다 따로 적어 두면 사람이 바뀔 때 점검 기준이 달라진다. 같은 조건을 알림 규칙에도 쓰려면 문장을 두 곳에 복사해야 했다.
- **결정:**
  1. `saved_searches`(이름 고유·문장·설명·만든 사람·공유·보호). 문장은 querylang 으로 검증해 **정본 표기**로 저장한다. 기간은 저장하지 않는다(점검 주기마다 다르다).
     공유하지 않은 검색은 만든 사람과 관리자만 본다. 고치고 지우는 것은 만든 사람·관리자, 보호(점검 기준)는 관리자만.
  2. 알림 규칙은 `match.saved: <이름>` 으로 쓴다. 엔진이 평가마다 이름을 문장으로 바꿔 규칙 문장 앞에 붙인다(AND, `engine.rule_filter` — 엔진·미리보기·알림 뒤 이벤트 수·예외 미리 보기가 같이 쓴다).
     없으면 그 규칙만 오류(조용히 '모든 이벤트'가 되지 않게), 저장할 때는 422.
  3. 규칙이 쓰는 검색은 **탐지 조건**이다: 알림 규칙을 고칠 수 있는 사람(`alerts.manage`)만 고치고, 문장을 바꾸면 관리 작업 알림(B-36)을 보낸다. 이름 바꾸기·지우기는 막는다.
     — 그러지 않으면 만든 사람(조회자)이 문장을 바꿔 규칙 파일의 판본·약화 알림(ADR-043)을 거치지 않고 탐지를 끌 수 있다.
  4. 조회 범위 판단(`alerts/visibility`)은 규칙 자체의 분류만 본다 — DB 의 문장은 바뀔 수 있어 지난 알림의 범위가 흔들린다. 저장한 검색만 쓴 규칙은 분류가 없는 규칙처럼 범위 사용자에게 보이지 않는다(닫힌 쪽).
  5. 최근 검색은 따로 저장하지 않고 접속기록(`events.search`)에서 읽는다(이미 남는 기록, 같은 문장은 한 번).
  6. (검토 보완) 보호가 먼저다 — 규칙이 쓰는 보호 검색도 관리자만. 규칙이 가리키는데 없는 이름(파일 직접 수정·DB 복원)으로 만들거나
     이름을 바꾸는 것도 그 규칙의 조건을 정하는 일이라 `alerts.manage`·관리 작업 알림. 저장한 검색 + 규칙 문장 + 예외를 합친 조건이
     검색 문장 한도를 넘으면 규칙 저장(422)·검색 저장(400)에서 막는다. 알림 본문의 링크는 이름이 아니라 합친 문장(예외 포함)으로.
- **대안:** 규칙에 문장을 복사 — 고칠 곳이 둘이 되어 기각. 저장한 검색을 판본으로 남기기 — 감사로그에 전·후 문장이 남아 1단계에서는 충분하다고 봄.

## ADR-051 알림 규칙 예외: 조건 하나, 제외 항으로 합치기, 지우지 않음
- **상태:** 채택 (2026-11-02). BACKLOG B-46.
- **배경:** 백업·의료장비 연동 서비스 계정, 유지보수 업체 IP 같은 영구적 제외를 규칙 문장에 `-user:` 로 직접 쓰면 누가·왜·언제까지 뺐는지 남지 않고, 업그레이드의
  `alerts.yaml.new` 와 손으로 합쳐야 했다. 무음은 (규칙, 대상) 단위·30일 이내라 맞지 않는다.
- **결정:**
  1. 예외 = 검색 조건 **하나**(포함 조건, 정본 표기로 저장). 엔진이 평가할 때마다 그 규칙의 걸린 예외를 읽어 문장에 `-조건` 으로 덧붙인다(`Rule.event_filter(exceptions)`).
     검색 문장의 제외 의미를 그대로 쓰므로(값이 없는 이벤트는 남김) 케이스 표가 SQL·매처의 같은 결과를 보장한다. 예외끼리는 각각 뺀다.
     여러 조건의 'AND 를 빼기'(예: 이 계정이면서 이 PC)는 제외 항으로 나타낼 수 없어 받지 않는다 — 잘못 넓게 빼는 것보다 막는 편이 안전하다.
  2. 사유 필수, 만료·검토일 선택. 지우지 않는다 — 끝내기(`ended_at`, 한 번)만, 트리거로 내용 수정·삭제·TRUNCATE 를 막는다(처리 기록 ADR-029 와 같은 방식).
  3. 탐지를 약하게 하는 변경이므로 추가하면 관리 작업 알림(B-36)으로 다른 관리자에게 알리고 감사로그(`alerts.exception.add`·`end`)에 최근 24시간 영향 건수까지 남긴다.
  4. 규칙 미리보기·알림 뒤 이어진 이벤트 수도 같은 예외를 반영한다(실제 평가와 같은 결과). 끊김 규칙에는 쓰지 않는다(대상·무음으로).
- **대안:** 규칙 파일에 예외 절 — 업그레이드 합치기 문제가 그대로라 기각. 이벤트에 '예외' 표시를 붙이기 — 원본 보존(절대 규칙 2)과 맞지 않아 기각.
