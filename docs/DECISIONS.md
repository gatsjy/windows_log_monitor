## ADR-001 수집 에이전트: Fluent Bit
- **상태:** 채택 (2026-10-03)
- **결정:** 모든 OS의 에이전트와 syslog 수신기에 Fluent Bit(Apache 2.0)를 씁니다.
- **이유:**
  - Windows 이벤트 로그(`winevtlog`), journald, 파일 tail, syslog 수신을 하나의 도구로 처리합니다.
  - 서버 장애 시 디스크 버퍼와 재시도를 기본으로 지원하고, 가볍습니다(C, 수 MB).
- **대안:**
  - Winlogbeat는 Elastic 라이선스 혼재 문제가 있습니다.
  - NXLog CE는 독자 라이선스입니다.
  - Vector는 Windows 이벤트 로그 지원이 약합니다.
  - OpenTelemetry Collector는 무겁습니다.

## ADR-002 저장소: PostgreSQL + JSONB 원본 보존
- **상태:** 채택
- **결정:** 공통 컬럼과 `raw JSONB` 를 함께 저장합니다.
- **이유:**
  - 유지보수 인력이 익숙한 SQL을 그대로 씁니다.
  - 백업 도구(`pg_dump`)가 표준이고, 트랜잭션·권한 관리가 성숙했습니다.
  - 원본을 보존하므로 정규화 규칙이 바뀌어도 다시 해석할 수 있습니다.

## ADR-003 파티션 키는 `received_at`
- **상태:** 채택
- **결정:** `events` 는 서버 수신 시각 기준 월별 RANGE 파티션으로 나눕니다. 시간 검색은 `ts` 인덱스로 합니다.
- **이유:**
  - 발생 시각(`ts`)은 PC 시계 오차, 과거 로그 일괄 전송 등으로 범위를 예측할 수 없습니다.
  - 그러면 DEFAULT 파티션 관리가 복잡해집니다.
  - 수신 시각은 항상 '지금' 근처라서 파티션을 미리 만들기 쉽습니다.
  - 보관기간 만료를 파티션 DROP 한 번으로 처리할 수 있습니다(빠르고 감사 기록이 명확).
- **대가:**
  - `ts` 조건 검색에서 파티션 프루닝이 안 되고, 월별 인덱스를 모두 탐색합니다.
  - 보관 1년이면 13개 파티션이라 허용할 만합니다.

## ADR-004 대용량 검색: 지금은 PostgreSQL, 필요할 때 검색 엔진 추가
- **상태:** 채택
- **결정:**
  - Elasticsearch/OpenSearch를 처음부터 도입하지 않습니다.
  - 이벤트 SQL을 `repository.py` 한 곳에 모아 두어 백엔드를 교체할 수 있게 합니다.
- **전환 신호 (하나라도 해당하면 검토):**
  - 지속 수집량이 초당 수천 건을 넘습니다.
  - 보관 데이터가 수십억 건 규모입니다.
  - 수개월 범위의 자유 텍스트 검색이 자주 필요하고, 응답이 수 초 이상 걸립니다.
- **후보:**
  - **ClickHouse** (Apache 2.0): SQL 그대로, 압축률 높음, 집계 빠름. 유지보수 관점 1순위입니다.
  - **OpenSearch** (Apache 2.0): 자유 텍스트 검색이 핵심일 때. JVM 메모리와 샤드 관리 부담이 있습니다.
  - Elasticsearch는 2024년부터 AGPL 선택지가 있지만, 같은 기능의 OpenSearch(Apache 2.0)가 라이선스 측면에서 단순합니다.
- **방식:** PostgreSQL은 메타데이터(agents, audit_log, 알림 이력)와 최근 데이터를 맡고, 검색 엔진은 대량 이벤트를 맡습니다.

## ADR-005 UI: 빌드 없는 순수 JS, 차트 직접 구현
- **상태:** 채택
- **결정:** 프레임워크, npm, CDN 없이 ES 모듈과 직접 만든 SVG 차트를 씁니다.
- **이유:**
  - 파일을 고치고 새로고침하면 바로 반영되어 수정이 쉽습니다.
  - 폐쇄망에서도 동작하고, 공급망(npm) 보안 점검 대상이 없습니다.
  - 차트 종류가 적어서(누적 막대, 가로 막대, 스파크라인) 직접 구현하는 비용이 낮습니다.
- **재검토 조건:** 화면 수가 크게 늘어 상태 관리가 복잡해지면 경량 라이브러리(Preact, MIT)를 검토합니다.

## ADR-007 대시보드 정의: JSON 파일
- **상태:** 채택
- **결정:** `config/dashboards/*.json` 파일로 관리합니다. UI 편집기로 저장하면 파일이 바뀌고 `audit_log` 에 해시와 함께 기록됩니다.
- **이유:**

## ADR-008 보안 로그 '감사 실패'를 경고로 승격
- **상태:** 채택
- **결정:** Keywords에 감사 실패 비트(0x10000000000000)가 있고 Level이 정보 이하이면 `level=3` 으로 저장합니다.
- **이유:**
  - Windows 보안 로그는 거의 모두 Level 0(정보)이라, 로그온 실패(4625) 같은 중요 이벤트가 정보 속에 묻힙니다.
  - 원래 값은 `raw.Level` 에 남아 있습니다.

## ADR-010 대시보드 실시간 갱신: SSE 증분 반영 + 주기적 전체 동기화
- **상태:** 채택 (2026-10-03)
- **결정:**
  - 대시보드가 `/api/live` 를 구독합니다. 새 이벤트를 1초 단위로 모아 위젯별 `live()` 로 제자리 갱신합니다.
  - 정확도는 `refresh_sec`(기본 60초)마다 하는 전체 재조회로 맞춥니다.
- **이유:**
  - 몇 초마다 폴링하면 위젯 수 × 접속자 수만큼 24시간 집계 쿼리가 반복되고, 그래도 몇 초씩 늦습니다.
  - SSE는 이미 실시간 화면에서 쓰고 있어서 추가 인프라가 없고, 깜빡임 없이 즉시 반영됩니다.
- **대가:** 브라우저가 모든 이벤트를 받습니다.
  - 초당 수천 건 규모가 되면 서버가 위젯 조건별로 집계한 값만 보내는 방식으로 바꿉니다(`/api/live` 에 집계 모드 추가).

## ADR-011 알림 엔진: 앱 내장, 규칙은 YAML 파일
- **상태:** 채택 (2026-10-03)
- **결정:**
  - 별도 서비스 없이 api 프로세스 안의 백그라운드 작업으로 30초마다 평가합니다.
  - 규칙과 알림 대상은 `config/alerts.yaml` 에 두고, 바뀌면 자동으로 다시 읽습니다.
  - 여러 인스턴스는 PostgreSQL advisory lock 으로 한 곳에서만 평가합니다.
- **집계 기준은 `received_at`** 입니다. `ts` 로 세면 장애 후 몰아서 들어온 오류를 놓치기 때문입니다.
- **중복 방지:**
  - (규칙, 대상) 별 `cooldown` 을 두고, `cooldown` 은 `window` 이상으로 강제합니다(같은 이벤트로 반복 알림 방지).
  - Oracle 은 ALERT_ID PK 로 재시도 시 중복 INSERT 를 막습니다.
- **재시도:** 실패하면 1분, 5분, 15분, 1시간 간격으로 다시 보내고, 5회 실패하면 `gave_up` 입니다. 이력은 `alert_deliveries` 에 남습니다.
- **대안:**
  - Grafana Alerting / Alertmanager: 메트릭 중심이고 별도 구성요소라 운영 부담이 늘어납니다.
  - ElastAlert2: Elasticsearch 가 필요합니다.

## ADR-012 비밀값은 환경변수로만
- **상태:** 채택 (2026-10-03)
- **결정:**
  - SMTP 비밀번호, Oracle 비밀번호, 웹훅 토큰은 `.env` → 컨테이너 환경변수로만 전달합니다.
  - `alerts.yaml` 은 `${VAR}`·`password_env` 로 참조만 합니다.
  - Oracle `password:` 를 파일에 쓰면 설정 검증에서 거부합니다.
- **이유:**
  - 설정 파일은 git 과 화면 편집 대상이라 노출 위험이 큽니다.
  - ISMS 2.7(암호화)과 2.5(인증정보 관리)에 대응합니다.

## ADR-013 인증: 자체 구현 서버 세션 (외부 IdP 없이)
- **상태:** 채택 (2026-10-03)
- **결정:**
  - 아이디/비밀번호와 서버 세션(DB)을 씁니다. 비밀번호는 scrypt(표준 라이브러리)로 해시하고, 세션은 HttpOnly·SameSite=Strict 쿠키입니다.
  - 역할은 관리자/조회자 2개입니다.
- **이유:**
  - 외부 의존성 없이 ISMS 통제(잠금, 세션 타임아웃, 비밀번호 정책, 접속기록)를 코드로 바로 보여 줄 수 있습니다.
  - 서버 세션이라 계정 비활성화나 비밀번호 초기화 즉시 강제 로그아웃이 됩니다(JWT 보다 단순).
- **유휴 판정:** 브라우저가 보내는 '마지막 조작 후 경과 초'로 판단합니다. 자동 새로고침이 세션을 연장하지 않게 하기 위해서입니다.
- **확장:** 사내 SSO(LDAP/AD, SAML/OIDC)가 필요하면 `auth/service.login` 앞단에 인증 공급자를 추가합니다.
  - 오픈소스 후보: Keycloak(Apache 2.0)
  - 세션·권한·감사 부분은 그대로 씁니다.

## ADR-014 알림 대상은 DB(환경설정 화면), 규칙은 YAML
- **상태:** 채택 (2026-10-03). ADR-011 의 '알림 대상도 YAML' 부분을 대체합니다.
- **결정:**
  - 수신자·수신 그룹·외부 연동(웹훅/Oracle)·메일 서버는 화면에서 관리합니다(DB).
  - 규칙은 계속 `config/alerts.yaml` 이고, `notify` 에 그룹·연동 이름을 씁니다.
- **이유:**
  - 받는 사람 목록은 운영자가 자주 바꾸고 화면이 편합니다.
  - 규칙은 리뷰·이력 관리가 중요해서 파일(git)이 낫습니다.
- **보완:**
  - 규칙 저장 시 없는 이름은 거부합니다.
  - 규칙에서 쓰는 그룹·연동은 삭제나 이름 변경을 막습니다.
  - 그룹·연동마다 '받을 최소 수준'을 둡니다.

## ADR-012 개정 (2026-10-03): 화면에서 입력하는 비밀값은 암호화해서 DB 에
- 환경설정 화면에서 SMTP·Oracle 비밀번호와 웹훅 주소·헤더를 입력할 수 있게 되었습니다.
- 이 값은 `WLM_SECRET_KEY` 로 Fernet 암호화해서 저장하고, API 로는 내보내지 않습니다.
- 서버 기동에 필요한 값(DB 비밀번호, 수집 API 키, 암호화 키 자체)은 계속 `.env` 에만 둡니다.

## ADR-015 Oracle 접속: python-oracledb thin, 4가지 접속 방식, 조회는 읽기 전용
- **상태:** 채택 (2026-10-03)
- **결정:**
  - Oracle Client 설치 없이 thin 모드를 씁니다.
  - 접속 방식은 TNS 이름(tnsnames.ora 를 화면에서 편집), SID, 서비스 이름, 접속 문자열 4가지입니다.
  - 조회 쿼리 실행기는 SELECT/WITH 한 문장만 허용하고, `SET TRANSACTION READ ONLY` 로 실행하며 최대 500행입니다. 모든 실행은 감사로그에 남깁니다.
- **이유:**
  - 사내 DBA 가 주는 정보 형태(TNS 별칭 또는 SID)가 제각각이라 모두 받습니다.
  - 관리자가 연동 결과를 바로 확인할 수 있어야 하지만, 운영 DB 변경 위험은 없어야 합니다.

## ADR-016 로그 로테이션: DB(검색) → 압축 보관 파일(SHA-256) → 삭제
- **상태:** 채택 (2026-10-03)
- **결정:**
  - DB 보관기간(기본 90일)이 지난 월 파티션은 `jsonl.gz` 로 내보낸 뒤 DROP 합니다.
  - 해시는 메타 파일과 감사로그 양쪽에 남깁니다.
  - 전체 보관기간(기본 365일)이 지나면 파일도 지웁니다.
  - 필요하면 파일을 같은 파티션으로 복원하고, 일정 기간 자동 정리에서 제외합니다.
  - → **ADR-040 로 보완:** 보관 파일 형식 v2(공통 필드 포함, v1 은 복원 때 다시 구함), 기록 종류별 보관기간.
- **이유:**
  - 1년치를 모두 DB 에 두면 저장 공간, 백업 시간, 인덱스 크기, 검색 속도가 모두 나빠집니다.
  - 실제로 자주 검색하는 범위는 최근 몇 주입니다.
  - 보관 파일은 형식이 단순해서(JSON Lines) 이 시스템 없이도 읽을 수 있습니다.
  - 해시로 위·변조를 확인할 수 있습니다(ISMS 2.9.4).
- **대안:**
  - pg_dump 로 파티션 백업: 복원에 PostgreSQL 이 필요하고, 형식이 열려 있지 않습니다.
  - 객체 스토리지(MinIO, AGPL): 필요하면 `archive/` 를 그쪽으로 동기화합니다.

## ADR-017 시간 조건에 수신 시각 하한을 함께 거는 파티션 가지치기 — 기각
- **상태:** 시험 후 기각 (2026-10-03)
- **시도:** `ts >= since` 에 `received_at >= since - 1일` 을 함께 붙여 오래된 월 파티션을 건너뛰게 했습니다(파티션 키는 received_at, ADR-003).
- **측정 (500만 건, docs/PERFORMANCE.md):** 오히려 크게 느려졌습니다.
  - 7일 시계열: 0.6초 → 11.3초
  - 30일 건수: 0.4초 → 4.8초
  - 원인: 조건이 늘면서 인덱스만 읽던 조회가 테이블 본문을 읽게 바뀌었습니다.
- **결론:**
  - 로그 로테이션(ADR-016)으로 DB 에는 파티션이 3~4개만 남습니다. 기간 밖 파티션의 인덱스 탐색 비용은 무시할 만합니다.
  - 대신 DB 설정 튜닝(병렬 4, shared_buffers, JIT 끔)을 채택했습니다.
  - 긴 기간 집계는 시간별 집계 테이블(로드맵)로 해결합니다.

## ADR-018 PostgreSQL 설정 튜닝을 compose 기본값으로
- **상태:** 채택 (2026-10-03)
- **결정:** `shared_buffers=1GB, effective_cache_size=3GB, work_mem=32MB, max_parallel_workers_per_gather=4, random_page_cost=1.1, jit=off, shm_size=1g` 을 기본값으로 둡니다. 서버 메모리에 맞게 `.env` 의 `WLM_PG_*` 로 조정합니다.
- **효과:**
  - 원본 필드 7일 검색: 1.8초 → 0.3초
  - 30일 PC·이벤트 조건 검색: 0.25초 → 0.05초

## ADR-019 공통 필드(분류·사용자·IP)를 컬럼으로
- **상태:** 채택 (2026-10-04)
- **결정:** `events` 에 `category`, `username`, `src_ip` 컬럼을 추가합니다(007). 정규화기가 소스별 원본에서 뽑아 채웁니다.
  - Windows 에이전트는 `event_data_as_map: true` 로 EventData 를 이름 있는 맵으로 보냅니다. 구버전 에이전트는 StringInserts 위치표로 보완합니다.
  - → **ADR-038 로 개정:** Fluent Bit 4.0 에 그 설정이 없어 에이전트는 StringInserts 만 보낸다(857359e). 이름은 서버가 붙인다.
- **이유:**
  - '이 IP 가 어디를 두드렸나', '이 계정이 어디서 실패했나' 는 Windows·IIS·MSSQL·SSH 를 가로지르는 질문입니다. 소스마다 원본 경로가 달라 `f.` 필터로는 묶을 수 없습니다.
  - 알림 규칙의 `group_by: ip` (출발지별 무차별 대입) 를 인덱스로 빠르게 셀 수 있습니다.
  - Wazuh·Graylog·Elastic(ECS) 모두 같은 방식의 공통 스키마를 둡니다(COMPARISON.md).
- **대안:** jsonb 표현식 인덱스만 두기 — 소스별 경로가 달라 조건이 길어지고, 화면·규칙이 소스를 알아야 합니다.
- **주의:** 원본은 그대로 `raw` 에 있습니다. 추출 규칙을 바꾸면 기존 행은 마이그레이션 UPDATE 로 다시 채웁니다.

## ADR-020 IIS·MSSQL 텍스트 로그는 서버에서 해석
- **상태:** 채택 (2026-10-04)
- **결정:** 에이전트(Fluent Bit tail)는 줄을 그대로 보내고, 서버의 `normalizers/iis.py`, `normalizers/mssql.py` 가 해석합니다.

- **이유:**
  - 에이전트 쪽 파서(Fluent Bit regex parser)는 PC 마다 배포해야 하고, 열 구성이 사이트마다 달라 고치기 어렵습니다. 서버 한곳에서 고치고 테스트할 수 있습니다.
  - 해석이 틀려도 원본이 남아 있어 나중에 다시 처리할 수 있습니다(ADR 원본 보존 원칙).
- **한계:** 머리줄 기억은 프로세스 메모리입니다(워커 1개 전제, ADR-006). 재시작 직후 사용자 지정 열 순서 IIS 파일은 다음 머리줄까지 기본 순서로 읽습니다. 영속화는 BACKLOG 에 있습니다.
  - → **ADR-037 로 개정:** IIS 열 순서는 DB(`iis_layouts`)에 두고, 추정한 순서는 값 모양으로 확인합니다. MSSQL 여러 줄은 에이전트가 묶고 서버는 첫 줄로 해석합니다.

## ADR-027 메모리 기본값 4GB 서버 기준 + 컨테이너 상한
- **상태:** 채택 (2026-10-15)
- **결정:** compose 기본값을 4GB 서버에 맞춥니다(shared_buffers 512MB, 병렬 2, shm 512m). db·api 컨테이너에 `mem_limit`(1536m / 768m), api 에 `MALLOC_ARENA_MAX=2`. 에이전트는 `storage.max_chunks_up: 16` 으로 메모리 조각 수를 제한합니다.
- **이유:** 이전 기본값(8GB 기준)으로 4GB 서버에서 db 가 2GB 가까이 차지했습니다. shared_buffers 는 돌려주지 않는 캐시이고 `docker stats` 는 페이지 캐시까지 세어 '정리가 안 되는' 것처럼 보입니다. 상한을 두면 커널이 캐시부터 비우고, 넘쳐도 그 컨테이너만 재시작됩니다(에이전트는 디스크 버퍼로 재전송).

## ADR-029 알림 처리 기록과 무음: 상태는 알림에, 기록은 지울 수 없는 타임라인에
- **상태:** 채택 (2026-10-14)
- **결정:**
  - 알림에 처리 상태(`open` 처리 안 됨 → `acked` 확인함 → `resolved` 해결됨)와 처리자·처리 시각을 둡니다(009). 해결은 확인을 겸합니다(확인한 사람이 없으면 해결한 사람·시각으로).
  - 확인·해결·다시 열기·메모는 `alert_notes` 타임라인에 쌓습니다. DB 트리거로 **수정·삭제·TRUNCATE 를 막고**(009, 010), 알림이 보관기간 만료로 지워질 때만 함께 지워집니다.
  - **확인·메모**는 알림을 볼 수 있는 사람 누구나, **해결·다시 열기·무음**은 관리자 또는 `alerts.handle` 권한 그룹만 합니다.
    - '확인'은 넓게 열어 둡니다. 누구든 '보고 있다'를 남겨야 대응이 빨라집니다. 대신 누가 확인했는지 감사로그에 남고, 담당자는 **확인함을 처리 안 됨으로 되돌릴 수 있습니다**(다시 열기). 확인으로 대기열을 비우는 오용을 되돌리기 위해서입니다.
    - 해결된 알림은 '확인'으로 되살아나지 않습니다(권한 없는 다시 열기 우회 방지).
  - 상세에서 '같은 규칙·대상의 해결 안 된 알림도 함께 해결'은 서버가 한 문장으로 처리합니다(`with_related`, 개수 제한 없음).
  - **무음(silence):** 규칙·대상(비우면 전체)·기간·사유. 끝 시각은 **지금부터 30일 안**이어야 합니다(길이만 묶으면 미래 무음을 이어 붙여 늘릴 수 있음). 더 길게 끌 일이면 규칙을 끕니다(규칙 관리 권한, 변경 이력).
    - 무음 중에도 알림은 **기록하고 전송만 건너뜁니다**(`alerts.silence_id`, 전송 상태 `skipped`).
    - 무음이 끝난 뒤 이벤트가 **새로** 들어오면(문제가 계속되면) 재알림 간격을 기다리지 않고 다음 평가에서 다시 알립니다. 무음 중에 쌓인 이벤트(점검 잡음)만으로는 다시 울리지 않습니다. PC 수신 끊김(`agent_silent`)은 무음이 끝났을 때 여전히 끊겨 있으면 다시 알립니다.
  - 무음 해제는 행을 지우지 않고 끝 시각을 앞당깁니다 → 언제 무음이었는지가 증적으로 남습니다. 보관기간이 지나 무음을 지울 때도 개수를 감사로그에 남깁니다.
  - **조회 범위(ADR-025)와 함께:** 범위가 있는 사용자에게는 자기 알림에 걸릴 수 있는 무음만 보입니다(모든 규칙·모든 대상 / 내 PC 대상 / 내 분류의 규칙). 무음을 걸고 풀 수 있는 것은 볼 수 있는 규칙·대상 한 개뿐입니다. 이력 목록은 보이는 (규칙, 대상)으로 **LIMIT 전에** 거릅니다.
  - **CSV 증적:** 처리 기록을 포함해 내보내고, 로그에서 온 값이 `= + - @` 로 시작하면 앞에 `'` 를 붙여 엑셀 수식 실행을 막습니다(감사로그 CSV 도 같은 `app/csvexport.py`). 1만 건에서 잘리면 파일·응답 머리글·감사로그에 표시합니다.
  - 사이드바 숫자는 '확인하지 않은 알림 수'로 바꾸고, 누르면 그 목록을 엽니다.
  - 마이그레이션 이전 알림은 `open` 으로 둡니다. 처리하지 않은 알림을 처리한 것처럼 꾸미지 않기 위해서입니다.
- **이유:** ISMS 2.11.5(사고 대응)는 인지 → 조치 → 종료를 누가·언제 했는지 남기라고 요구합니다. 점검·배포 중 예상된 알림이 쏟아지면 진짜 알림을 놓칩니다.
- **대안:**
  - 재발한 알림을 기존 열린 알림에 합치기: 건수는 줄지만 '언제 몇 번 났는지'가 흐려지고 전송 이력과 맞추기 어려워 보류. 알림은 발생마다 한 행입니다.
  - 무음 중 알림을 아예 만들지 않기: 감사 증적이 사라져 채택하지 않음.

  - 형식은 각 서비스 공식 문서와 실제 응답으로 확인한 것만 씁니다(2026-10-15 조사·교차 확인). Slack 은 머리글 + 색 막대 첨부 안의 Block Kit, Teams 는 워크플로 웹훅의 Adaptive Card 1.4 봉투, 두레이는 평문 + 첨부, 잔디는 `body`/`connectInfo` + 전용 Accept 헤더.

- **이유:**

  - 두레이는 1초 1건을 넘으면 성공을 주고도 버려서 재시도로도 찾을 수 없습니다 — 보내는 쪽에서 간격을 지켜야 합니다.
  - 두레이·잔디·Slack 은 http 주소로도 받거나(두레이) 응답 없이 멈춰서(잔디) 토큰이 평문으로 나가거나 전송이 늦어집니다.
  - Slack 의 링크 버튼은 앱에 상호작용 설정이 없으면 누를 때 오류 표시가 떠서 글자 링크를 씁니다.
- **대안:** Teams 옛 MessageCard — 워크플로 템플릿이 `attachments` 를 돌며 카드를 올려서 실패하는 경우가 있어 쓰지 않습니다. 카카오워크·네이버웍스는 요구가 생기면 같은 방식으로 추가합니다.

## ADR-031 DB 백업: db 와 같은 이미지의 backup 서비스, 결과는 감사로그
- **상태:** 채택 (2026-10-16)
- **결정:** compose 에 `backup` 서비스(`postgres:17-alpine`, `deploy/backup/backup.sh`)를 둡니다. 매일 `pg_dump -Fc` + SHA-256 + `config/` 묶음, 최근 N개 보관, 매주 임시 DB(`<DB>_restore_check`)에 실제로 복원해 해시·마이그레이션 버전·주요 테이블 행 수를 확인합니다.
  - 결과는 스크립트가 `audit_log` 에 직접 INSERT 합니다(`backup.create/failed/verify/restore`). api 는 그 기록으로 화면 상태와 경고를 만듭니다 — 백업 파일을 api 컨테이너에 보일 필요가 없습니다.
  - 장애 복구는 `backup.sh restore <파일> --yes` 한 명령으로(해시가 맞는 파일만, 복원 사실도 기록). 손으로 치는 절차보다 실수가 적습니다.
    - 운영 DB 에 연결된 세션(api 등)이 있으면 거부합니다. `dropdb --force` 로 끊으면 api 가 곧바로 다시 붙어 반쯤 복원된 DB 에 쓰기 때문입니다.
    - 지금 DB 를 `before-restore-<시각>.dump`(+해시)로 먼저 남기고, 임시 DB(`<DB>_restoring`)에 복원이 끝난 뒤에만 이름을 바꿔 끼웁니다. 파일을 잘못 골랐거나 복원이 실패해도 되돌릴 수 있습니다.
  - 행 수는 `pg_dump --snapshot` 과 **같은 스냅숏**에서 셉니다(내보낸 스냅숏의 트랜잭션 안에서 psql `\!` 로 pg_dump 실행). 그래서 복구 시험이 '백업에 든 행 수와 정확히 같은가'를 볼 수 있습니다. 따로 세면 매시간 정리 작업이 그 사이에 지운 행 때문에 거짓 실패가 납니다.
  - 일정은 '시각이 지났고 오늘 아직 안 했으면'으로 돕니다(마지막 날짜는 `backups/.last-run`). 정확히 그 1분에만 돌면 긴 복구 시험이 다음 날 시각을 넘기거나 서머타임으로 그 시각이 없는 날 하루를 건너뜁니다.
  - 복구 시험·복원 전에 DB 디스크(db 볼륨을 읽기 전용으로 붙여 `df`)의 남은 공간을 봅니다. 모자라면 시험하지 않고 '실패(공간 부족)'로 남깁니다 — 운영 DB 디스크를 채우지 않게.
  - 보관 개수(`WLM_BACKUP_KEEP`)는 1 이상만 받습니다. 0 을 '무제한'으로 알고 넣으면 방금 만든 백업까지 지워지기 때문입니다. 방금 만든 파일은 어떤 경우에도 정리하지 않습니다.
  - 파티션 만들기·지우기는 잠금을 5초만 기다립니다(`partitions.DDL_LOCK_TIMEOUT`). pg_dump 가 events 를 읽는 동안 배타 잠금을 줄 서서 기다리면 그 뒤의 수집이 모두 멈추기 때문입니다. 파티션은 미리 만들어 두므로 다음 주기로 미뤄도 됩니다.
  - `.env`(암호화 키)는 묶지 않습니다.
- **이유:**
  - db 와 같은 이미지라 폐쇄망 반입 묶음이 늘지 않고, `pg_dump`·`pg_restore` 버전이 서버(17)와 항상 같습니다. api 이미지(Debian 의 PostgreSQL 15 클라이언트)로는 17 서버를 덤프할 수 없습니다.
  - ISMS 2.9.3 은 백업만이 아니라 **복구 시험 기록**을 봅니다. 파일이 있다는 것만으로는 복원된다는 보장이 없어서(잘린 파일·권한·확장 기능) 실제로 복원해 봅니다.
  - 키를 백업과 같이 두면 백업만 빼 가도 화면에서 넣은 비밀값(SMTP·Oracle·웹훅)을 풀 수 있습니다(ISMS 2.7.2).
- **대가:** 복구 시험 동안 DB 크기만큼 디스크와 I/O 를 씁니다(새벽, 주 1회). 부족하면 '공간 부족'으로 실패를 남기므로, 디스크를 늘리거나 `WLM_BACKUP_VERIFY_WEEKDAY=0` 으로 끄고 시험 서버에서 수동으로 합니다. 복원도 안전 사본과 임시 DB 만큼 공간을 더 씁니다(DB 가 망가져 덤프가 안 되면 `--no-safety-dump`).
- **대안:** 호스트 cron + 스크립트 — 설치마다 cron 설정이 필요하고 결과가 화면에 안 보여 보류. WAL 보관·특정 시점 복구(PITR) — 규모가 커지면 검토.

## ADR-032 정기 점검 보고서: 서버가 만든 하나의 문서를 저장·발송·열람, 사람이 '점검 확인'
- **상태:** 채택 (2026-10-16)
- **결정:** 앱 안의 작업(1분마다, advisory lock)이 정한 시각에 일간(어제)·주간(지난주 월~일) 보고서를 만들어 `reports` 에 저장하고 받는 곳(수신 그룹 메일·웹훅 요약)으로 보냅니다(`app/reports/`).
  - 같은 기간의 정기 보고서는 고유 색인으로 하나만 — 재시작·여러 대에서도 중복 발송이 없습니다. 꺼져 있다가 켜지면 가장 최근 기간만 만듭니다.
  - 내용(`payload`)은 만들 때 모두 담고 **고칠 수 없게**(트리거) 저장하며, 감사로그에 내용 해시를 남깁니다. 메일·화면·인쇄본은 모두 이 payload 를 서버의 같은 렌더러로 그린 HTML 입니다(화면은 sandbox iframe, CSP 로 스크립트 차단).
  - 담당자가 화면에서 **점검 확인**(의견·조치)을 한 번 남깁니다.
  - 받는 곳이 없어도 만들어 저장합니다. 보고서 자체가 점검 증적입니다.
  - 조회 범위가 정해진 사용자는 볼 수 없습니다(전체 PC·분류가 들어 있음).
  - 전송은 '적어 두고 보내기'입니다. 보고서를 저장할 때 받는 곳을 '보내는 중'으로 같이 적고, 결과는 덧붙입니다(덮어쓰지 않음). 자동 발송은 감사로그 `report.deliver` 에도 남깁니다.
    - 보내다가 서버가 멈추면 다음 주기에 그곳만 이어서 보냅니다(하루가 지나면 실패로). 고유 색인 때문에 같은 기간을 다시 만들지 않으므로, 이게 없으면 그날 보고서가 영영 안 갑니다.
    - 다시 보내기는 기본으로 못 받은 곳만 — 받은 사람에게 같은 메일이 또 가지 않게.
  - 비교는 '일주일 전 같은 시간'(일간 = 지난주 같은 요일)입니다. 바로 전날과 비교하면 PC 를 끄는 주말·휴일 다음마다 '로그가 줄었다'는 거짓 경고가 나서, 보는 사람이 경고를 무시하게 됩니다.
  - 추이 칸은 표시 시간대의 실제 시각(일간 1시간)·달력 날짜(주간 하루)로 나눕니다. 서머타임 날은 23·25시간이라 고정 길이로 나누면 칸이 빠지거나 뭉칩니다.
  - 렌더러는 예전 형식의 payload 도 그려야 합니다(고칠 수 없으므로). 예: 무결성 확인 결과 `bad` 가 개수(예전 CLI)든 파일 이름 목록이든 받습니다.
- **이유:**
  - ISMS 2.9.5 는 '정기적으로 점검하고 결과를 남길 것'을 봅니다. 자동 메일만으로는 사람이 실제로 보았다는 근거가 약해서 점검 확인을 따로 남깁니다.
  - 화면을 JS 로 따로 그리면 메일·인쇄본과 내용이 어긋날 수 있어 렌더러를 하나로 두었습니다.
  - 보고서마다 '점검 필요'(로그 0건, 로그 삭제, 백업 문제, 해결 안 된 심각 알림 등)를 맨 위에 모아, 매일 몇 초 안에 이상 여부를 판단할 수 있게 했습니다.
- **대가:** 주간 보고서는 7일치 이벤트를 몇 번 집계하므로 큰 DB 에서 수 초~수십 초 걸릴 수 있습니다(새벽·아침 1회). 보고서 표는 보관기간만큼 쌓입니다(1건 수 KB~수십 KB).
- **대안:** 대시보드 PDF 스냅숏 — 브라우저 렌더링이 필요해 폐쇄망·서버에서 어렵고, '점검 필요' 판단이 없어 보류.

## ADR-033 검색 문장: 새 파라미터 query, 같은 뜻이면 같은 SQL, 서버·화면 파서는 한 표로 시험
- **상태:** 채택 (2026-10-16, BACKLOG B-01)
- **결정:** 한 줄 검색 문장 `event_id:4625 ip:10.0.0.5 -user:svc_backup level:오류,심각 "잘못된 암호"` 를 새 파라미터 `query` 로 받습니다. URL·API·알림 규칙 `match.query`·대시보드 위젯 `query.query` 가 같은 이름·같은 문법입니다(PROJECT.md §4.1).
  - 기존 파라미터(`host … q f.*`)는 뜻·SQL 모두 그대로이고 `query` 와 AND 입니다. `q` 를 문장으로 다시 해석하지 않습니다 — 배포된 규칙의 `q: "…|IEX (|…"`, 옛 링크의 `q=다시 부팅`(구절)의 뜻이 바뀌기 때문입니다.
  - 파서는 표준 라이브러리만 쓰는 `server/app/querylang.py` 와 import 없는 `web/js/querylang.js` 한 쌍입니다(한 줄씩 같은 스캐너). 상수·오류 문구는 `@sync` 블록 하나 — 컨테이너 pytest 가 두 언어를 비교합니다.
  - **포함 조건은 기존 `EventFilter` 필드에 교집합으로 합칩니다** → 같은 뜻이면 SQL 이 바이트 단위로 같습니다(`same_sql` 시험, 옛 조건 80개 SQL 스냅숏). 새 색인·마이그레이션이 없고 '기존 검색보다 느려지지 않음'이 구조로 보장됩니다. 겹치지 않으면(`host:A host:B`) `never` → `FALSE`.
  - **제외는 `(포함식) IS NOT TRUE`** — 값이 없는(NULL·경로 없음·JSON null) 이벤트는 남깁니다. 백로그 초안의 `NOT IN`/`<> ALL` 은 NULL 행을 버려 `-user:svc_backup` 이 사용자 없는 대다수 로그를 숨기고, `NOT (raw @> …)` 는 타입을 엄격히 따져(숫자 4625 ≠ "4625") 포함식의 여집합이 되지 않아 기각했습니다.
  - `f.*` 는 지금처럼 글자 비교(`raw #>> 경로`)입니다. 실시간 매처의 글자 표현도 `#>>` 와 같게 — 배열·객체는 `', '`·`': '`, 실수는 PostgreSQL numeric 처럼 지수 표기 없이(저장 때 Python repr 이 그대로 jsonb 숫자가 되므로 `Decimal(repr(x))` 를 펼친다). 메시지는 PostgreSQL ILIKE(글자마다 towlower)와 맞춘 `fold`(İ→i, Σ→σ 후 소문자)로 비교합니다 — Python·JS 의 lower 는 어말 시그마와 İ 만 다릅니다(`casefold` 는 ß→ss 라 기각).
  - 엄격한 문법: 키처럼 생긴 이름 + `:` 는 키여야 하고(오타는 위치·힌트와 함께 오류), 와일드카드·괄호·`|`·`AND/OR/NOT` 은 예약해 오류로 알립니다. 나중에 넣어도 지금 문장의 뜻이 바뀌지 않게, 그리고 오타가 조용한 메시지 검색이 되지 않게. `C:\Windows`, `http://…`, `12:30`, `fe80::1` 은 따옴표 없이 메시지 단어입니다(콜론 규칙).
  - 위치는 코드 포인트(한국어 'N번째 글자'와 맞음), 입력 칸에서만 UTF-16 으로 바꿉니다. 오류는 처음 하나, 400 응답은 `detail`(문자열, 기존 그대로) + `query_error{code,start,end}`.
  - 화면: 문장이 조건의 정본이고 드롭다운·수준 칩은 문장을 보여 주고 고치는 창입니다(span 단위로 고쳐 사용자 표기 보존). 옛 링크는 들어올 때 문장으로 접고, 뜻이 똑같이 옮겨지지 않는 값은 옛 파라미터로 남깁니다.
  - 알림 규칙의 조회 범위(ADR-025)는 `Rule.categories`(문장 속 `category:` 포함)로 판단합니다.
- **검증:** 케이스 표 하나(`server/tests/querylang_cases.json`: 정상·오류 문장, 고정 이벤트 매칭, 같은 SQL, 옛 링크 접기, 문장 편집)를 Python 파서·실제 SQL·Python 매처·JS 파서·JS 매처가 함께 씁니다. 무작위 300문장으로 SQL ≡ 매처, node 와 python3 교차 퍼징 3,000문장으로 두 파서를 비교합니다. JS 시험은 npm 없이 `node --test`(컨테이너에는 node 가 없어 개발 PC·CI).
- **이유:** 조사할 때 "이 IP 인데 이 계정은 빼고" 같은 조건을 한 줄로 쓰고 공유할 수 있어야 합니다. 서버·실시간(대시보드)·알림이 같은 규칙을 쓰지 않으면 같은 문장이 화면마다 다른 결과를 냅니다.
- **대가:** 제외·`-단어` 는 색인을 쓰지 못해, 제외만 있는 긴 기간 건수·시계열은 본문을 읽어 느립니다(PERFORMANCE.md §2.1, 화면 린트로 안내). 엄격한 문법이라 `Error:` 같은 말은 따옴표가 필요합니다(빠른 고침 단추). 분류처럼 닫힌 어휘를 바꾸면 SYNC 두 곳·케이스 표를 함께 고칩니다(불일치는 시험이 잡음).
- **되돌리기 위험:** 이 기능 이전 버전은 `query` 를 조용히 무시합니다 — 공유 링크·위젯 문장이 '전체'로 넓어지고, 알림 규칙의 `match.query` 는 ConfigError 로 거부되어 이전 규칙을 유지합니다.
- **대안:** 타입을 따지는 jsonb 비교(배포된 규칙의 `"10"` 비교가 바뀜), 와일드카드(btree 색인 못 씀·세 엔진의 glob 일치 위험), 한글 키 별칭, 쉼표·`|` 를 단어 OR 로 쓰기(`1,024` 같은 로그 값과 충돌), 화면 안의 자체 시험 페이지(운영 이미지에 들어감), 최근 검색어 저장(계정·IP 가 브라우저에 남음 — ISMS) — 모두 기각.

## ADR-034 CI: 개발 이미지 안에서 시험, 외부 action 은 커밋 해시 고정
- **상태:** 채택 (2026-10-16, BACKLOG B-15)
- **결정:** GitHub Actions(`.github/workflows/ci.yml`)가 모든 push·PR 에서 돌린다.
  - 서버 시험·린트는 `server/Dockerfile` 의 `dev` 이미지 안에서(PostgreSQL 17 서비스 컨테이너). 시험이 컨테이너 배치(`/app/app`·`/app/web`·`/app/config`)를 전제하고, 운영과 같은 Python·의존성으로 돌기 위해서다.
  - 백업 스크립트는 compose 와 같은 `postgres:17-alpine` 이미지로 `selftest`, 화면 모듈은 npm 없이 `node --test`(교차 퍼징에 python3).
  - 에이전트 설정은 설치 스크립트와 같은 규칙으로 틀을 채워(`tools/ci/render_agent_configs.py`) `fluent-bit --dry-run`. 윈도 설정의 `winevtlog` 은 윈도 빌드에만 있어 윈도 러너에서 폐쇄망 묶음과 같은 4.0.14 zip 을 받아 **저장소의 SHA-256 으로 확인**한 뒤 돌린다.
  - 운영 이미지는 Trivy 로 점검: 고칠 수 있는 CRITICAL 은 실패, HIGH 는 기록만.
  - 외부 action 은 **커밋 해시로 고정**(태그는 옮겨질 수 있다 — 공급망), 토큰 권한은 읽기만. ruff 는 정확한 버전으로 고정 — 새 버전이 규칙을 바꾸면 이유 없이 CI 가 깨진다(실제로 0.16→0.17 에서 `noqa` 판정이 바뀜).
- **이유:** ISMS 2.8.5(소스 변경 관리)·2.10.x(시스템 보안)는 변경이 검증을 거쳤다는 증적을 본다. 사람이 '시험 돌렸다'고 적는 것보다 CI 기록이 증적이 된다. B-01 처럼 두 언어가 같은 규칙을 지켜야 하는 코드는 node 시험이 컨테이너 밖에서만 돌아 CI 가 꼭 필요했다.
- **대가:** 개발 이미지 빌드 시간(수 분), 윈도 러너, action·Trivy 해시 갱신을 사람이 챙겨야 한다.
- **대안:** 러너에 직접 pip 설치 — 경로·버전이 컨테이너와 달라 시험이 어긋나 기각. 사내 GitLab CI — 저장소가 GitHub 라 우선 Actions, 사내로 옮기면 같은 단계를 옮긴다.

## ADR-035 화면 조회에 시간 상한과 동시 자리 (503 + 그 화면에 맞는 안내)
- **상태:** 채택 (2026-10-16)
- **배경:** B-01 벤치(PERFORMANCE.md §2.1)에서 2글자 단어 검색이 30일 29초, 결과 없는 7일 검색이 1분을 넘겼다. 검색에는 시간 제한이 없었고, 브라우저를 닫거나 클라이언트를 끊어도 DB 쿼리는 끝까지 돈다(실측: 끊긴 쿼리가 3분 넘게 남음). 연결 풀 10개를 수집과 나눠 쓰므로 느린 검색이 쌓이면 수집이 풀 대기 30초 뒤 실패(500)한다 — 검토에서 느린 문장 20개로 재현.
- **결정:**
  - **시간 상한:** 화면 조회(`routers/query.py` 라우터의 GET 전부 + POST 로 읽는 규칙 미리보기)는 쿼리마다 `statement_timeout` 을 건다 — `WLM_SEARCH_TIMEOUT_SEC`(기본 30초, 0 = 없음). 의존성이 컨텍스트 변수를 켜고, `db.fetch_all/fetch_one` 이 같은 트랜잭션에서 `set_config('statement_timeout', …, true)`(= `SET LOCAL`)를 먼저 보낸다. 풀에 돌려줄 때 트랜잭션이 끝나 같은 연결을 다음에 쓰는 수집·알림 엔진에는 남지 않는다(시험이 풀 연결마다 확인).
  - **동시 자리:** 상한이 걸린 조회는 한꺼번에 `SEARCH_SLOTS`(6)개 연결까지만 쓴다. 나머지 4개는 수집·알림 엔진·상태 확인 몫으로 늘 남는다. 자리를 기다리는 시간에도 같은 상한을 두고, 넘으면 '조회가 몰려 차례가 오지 않았다'로 안내한다.
  - **쓰기는 제외:** PC 삭제처럼 같은 라우터의 쓰기(DELETE·POST)는 잠금을 기다려서라도 끝내야 하므로 걸지 않는다. 알림 엔진·점검 보고서·수집·보관 작업에도 걸지 않는다 — 놓치면 안 되는 작업이고, 느린 규칙은 미리보기(상한 있음)에서 먼저 드러난다.
  - **안내:** 넘으면 `db.QueryTimeout` → **503** + 그 화면에서 할 수 있는 방법(검색: 기간·조건·짧은 단어는 따옴표 / 수집 PC: 기간 / 미리보기: 조건 좁히기). 관리자의 `pg_cancel_backend` 같은 다른 취소는 시간 초과로 바꾸지 않는다(서버 메시지와 걸린 시간으로 구별).
  - **기록:** 끝나지 않은 검색도 접속기록(`events.search`, `timeout_sec`)에 남긴다. 서버 경고 줄은 경로만 — 전체 주소는 같은 요청의 접근 로그 줄에 있다(검색어·계정·IP 가 컨테이너 로그에도 남는 것은 그대로, docs/ISMS.md).
  - 화면은 이전 검색의 건수·막대를 지우고 안내를 보인다. '더 보기'가 실패하면 받은 결과는 두고 '다시 시도'.
- **이유:** 어떤 조회든 끝나는 시간이 정해져 있어야 운영자가 '멈춘 화면'과 '느린 검색'을 구별하고, 한 사용자의 검색이 수집을 멈추지 못한다. 쿼리 단위(SET LOCAL)라 다른 작업에 새지 않고 연결 문자열·DB 설정을 바꾸지 않는다.
- **대가:** 30초가 넘는 정당한 조회(긴 기간의 원본 필드·짧은 단어, 큰 규모의 30일 집계)는 조건을 좁히거나 상한을 올려야 한다(PERFORMANCE.md §2.2). 조회가 7개 넘게 동시에 오면 차례를 기다린다. 쿼리마다 왕복 한 번(set_config)이 늘어난다(0.1ms 안팎). 클라이언트가 끊겨도 상한까지는 쿼리가 돈다. 자리 대기 + 실행이라 한 요청이 상한의 두 배까지 걸릴 수 있다.
- **대안:** DB 역할·연결 단위 `statement_timeout` — 수집·보관·마이그레이션까지 걸려 기각. 수집 전용 풀 분리 — 연결 수가 늘고 실시간·하트비트 경로까지 나눠야 해 자리 제한으로 대신. 끊긴 요청의 쿼리 취소 — 서버 프레임워크가 연결 끊김을 엔드포인트에 알리지 않아 보류. 2글자 색인(pg_bigm) — DB 이미지를 바꿔야 해 보류. 짧은 단어의 SQL 을 바꿔 색인을 피하기 — 캐시 상태에 따라 오히려 느린 경우가 있어(실험) 기각.

## ADR-036 운영 HTTPS·에이전트 TLS: api 가 직접 TLS 를 끝내고, 평문·TLS 수집을 병행한 뒤 닫는다
- **상태:** 채택 (2026-10-16, BACKLOG B-06)
- **배경:** 화면과 수집이 평문 HTTP 였다(ISMS 2.7.1). BACKLOG 원안은 Caddy compose 프로필 + Nginx 예시였다. 폐쇄망 반입 묶음은 compose 의 이미지를 모으므로 이미지가 늘면 반입·Trivy·심사 대상이 함께 는다. 운영 첫 설치(B-25) 전이다. 설계는 관점이 다른 세 안(폐쇄망 운영·보안·전환)을 심사해 종합했다.
- **결정:**
  1. **api 의 uvicorn 이 TLS 를 끝낸다**(`WLM_TLS=on`). TLS 1.2 이상, TLS 1.2 는 ECDHE+AEAD 만(파이썬 기본은 CBC 를 허용 — 실측), 재협상 끔(`tlsutil.server_context`). 새 이미지·의존성 없음(uvicorn 하한만 0.54 — ssl_context_factory).
  2. **포트를 역할로 나눈다:** 화면 8000(→`WLM_PORT`)은 TLS 만(평문 화면 리스너·리다이렉트 없음), 수집은 평문 8001(→6976)과 TLS 8002(→6977)를 **병행**하다가 모든 PC 가 옮기면 `WLM_INGEST_PLAIN=off` 로 평문 리스너를 띄우지 않는다(연결 거부). syslog 수신기는 게시하지 않는 내부 8003 으로 — 평문을 닫아도 syslog 는 계속.
  3. **에이전트는 서버를 확인한다:** 설치 묶음의 `ca.crt` 로 연쇄를(`tls.verify`), 인증서의 **DNS 이름**으로 이름을(`tls.verify_hostname: on` — Fluent Bit 기본값은 off, `tls.vhost`). Fluent Bit 4.0 은 IP SAN 으로 확인하지 못해(실측) 서버 인증서에 DNS 이름이 꼭 있어야 한다(DNS 등록은 필요 없음). 끄는 선택지는 두지 않는다. 설치 스크립트(Windows `CaSha256`, Linux `TLS_CA_SHA256`)는 CA 지문을 대조하고, PC 에는 인증서만 ASCII PEM 으로 둔다. Windows 는 파일을 쓰기 전에 폴더 소유자·권한을 다시 잡는다(일반 사용자가 폴더를 미리 만든 경우).
  4. **확인할 수 없는 묶음은 만들지 않는다:** TLS 서버는 TLS 묶음만 만든다. 인증서 상태는 에이전트와 같은 OpenSSL 로 **메모리 안에서 실제 핸드셰이크**를 해 보고 판단한다(`tlsutil.agent_handshake` — 연쇄·만료·용도(EKU)·이름 제한·중간 CA·키 짝, 파이썬 3.13 의 STRICT·PARTIAL_CHAIN 은 끔). 다른 검증기로 흉내 내면 만료된 CA·중간 CA 를 루트로 둔 경우를 놓친다(검토에서 재현). 실패하거나 CA 없음·DNS 이름 없음·인증서에 없는 이름이면 409/422. CA 파일은 인증서만 다시 써서 넣는다(개인키가 섞인 사내 PKI 파일 방지).
  5. **인증서:** 자체 CA(ECDSA P-256, 10년, **이름 제한** — 준 DNS·IP 만, IP 를 안 주면 모든 IP 금지, 메일 금지, 용도는 서버 인증만)와 서버 인증서(2년, AKI 포함, 하루 앞당김)를 `app.cli tls-init/tls-renew` 로(DB 없이, 설치가 일회성 컨테이너로). CA 개인키는 api 에 마운트하지 않는 `tls-ca/` 에 — 서버가 뚫려도 가짜 인증서를 못 만들게. 사내 PKI 도 같은 자리(`tls/`). 서버 키는 소유자 uid 10001·0600(이미지의 wlm 그룹 번호는 999 로 고정돼 있지 않아 그룹으로 주지 않는다).
  6. **쿠키 Secure 는 요청 scheme 으로 자동**, `WLM_COOKIE_SECURE=true` 는 강제용(그러면 http 로그인은 안내와 함께 400). HSTS 는 선택(비우면 안 보냄, `0` 이면 `max-age=0` 으로 브라우저의 기억을 지움, includeSubDomains 없음).
  7. **프록시 헤더는 `WLM_TRUSTED_PROXIES` 에 적은 주소만 믿는다.** 값을 uvicorn 에 직접 넘겨 `.env` 의 `FORWARDED_ALLOW_IPS` 한 줄로 신뢰 범위가 바뀌던 경로를 막았다. `*`·/0, uvicorn 이 조용히 무시하는 값(호스트 비트가 있는 대역, IPv4 매핑 주소)은 기동 거부.
  8. **PC 별 전송 방식**(마지막 하트비트가 TLS 리스너·신뢰 프록시의 https 로 왔는지, 평문이면 수집 포트인지 화면 포트인지 — `tls`·`plain`·`web`)을 `agents.last_transport` 에 남겨 수집 PC 화면에 보인다 — 평문을 닫을 근거, TLS 를 켜면 끊길 옛 묶음(화면 포트로 보냄 — 설정 버전으로는 구별되지 않음) 찾기, ISMS 증적.
  9. 기동 전 점검(`tlsutil.preflight`)이 실패하면 아무 리스너도 띄우지 않는다(반쯤 뜬 상태 방지). 상태 확인은 `app.healthcheck`(TLS 면 https). 인증서 만료·이름·CA 문제는 기동 때와 하루 한 번 로그 — 기동 때 내보낸 인증서를 기억해, 파일만 바꾸고 재시작을 빠뜨린 경우도 알린다. 폐쇄망 설치는 켜기 전에 api 계정으로 같은 핸드셰이크를 해 보고, 배포된 CA 가 있는데 CA 키가 없으면 새 CA 를 만들지 않고 멈춘다.
- **이유:** 반입·Trivy 대상이 그대로이고, 접속 IP 가 보존되어(로그인 시도 제한·감사 IP·PC 마지막 IP) 신뢰 프록시 설정이 필수가 아니며, 소켓 포트로 판단하는 수집 포트 제한과 한 프로세스 구조(ADR-006)를 지킨다. 병행 후 닫기는 수백 대의 PC 를 끊김 없이 옮기는 유일한 순서다.
- **대가:** 인증서 교체에 api 재시작(기동 때 한 번 읽음). 화면의 http 북마크는 빈 응답. 장비 → 수신기 syslog(514)는 평문. TLS 핸드셰이크도 한 프로세스가 처리(초당 200회 새 연결에서 문제없음 — PERFORMANCE.md §2.3). 이름 제한 때문에 허용 이름 밖으로 바꾸려면 새 CA 와 전체 재배포. Windows 에이전트의 인증서 저장소·PS 5.1 실기 동작은 B-28 에서 확인.
- **대안:** Caddy compose 프로필(원안) — 이미지·반입·Trivy 가 늘고, 프록시 뒤에서는 접속 IP 를 잃어 신뢰 프록시가 필수, api 게시 포트가 남으면 프록시를 우회하는 평문 경로. 같은 포트에서 평문·TLS 자동 판별 — 이미 읽은 ClientHello 를 되돌릴 수 없음. 6976 을 그 자리에서 TLS 로 바꾸기 — 평문 에이전트가 버퍼만 쌓고 서버 로그에는 아무것도 안 남음. 화면 평문 포트 + 308 — 평문 리스너가 남음(HSTS 로 대신). 평문 수집을 403 으로 거절 — 옛 에이전트가 키를 평문으로 계속 보냄. 평문 수집 기한 자동 차단 — 날짜 하나로 수집이 끊기는 사고 위험. CA 없이 서버 인증서를 직접 신뢰 — 갱신마다 전체 재배포. 모두 기각.

## ADR-009 오픈소스만 사용
- **상태:** 채택 (요구사항)

## ADR-037 IIS 열 순서는 DB 에, 추정한 순서는 값 모양으로 확인 · MSSQL 여러 줄은 에이전트가 묶고 서버는 첫 줄로 해석
- **상태:** 채택 (2026-10-19, BACKLOG B-08, ADR-020 의 '한계' 개정). 서버(1단계)와 에이전트 설정 0.4.0(2단계)을 구현했다. 실제 ERRORLOG·IIS 샘플 확인은 B-08 에 남았다.
- **배경:**
  - IIS `#Fields:` 기억이 프로세스 메모리여서, 서버를 다시 시작하면 사용자 지정 열 순서를 기본 순서로 **잘못** 읽었다. 칸 수가 같으면 `src_ip`·`username` 자리가 바뀐 채 저장되었다(재현: `src_ip='lee'`, `username='443'`). `clean_ip` 는 IP 인지 확인하지 않는다.
  - 에이전트 tail 은 db 위치에서 이어 읽어, 에이전트를 다시 시작해도 머리줄을 다시 보내지 않는다. 에이전트가 멈춘 사이 새로 생긴 파일은 끝부터 읽어 머리줄 자체가 오지 않는다(실측).
  - Fluent Bit 4.0.14 의 http 출력은 작업자 2개·재시도라 요청 사이 순서가 보장되지 않는다(실측).
  - ERRORLOG 의 시작 배너·시작 인자·여러 줄 메시지는 줄마다 저장되어, 이어지는 줄에 받은 시각과 단어로 추정한 수준이 붙었다.
  - 설계는 관점이 다른 두 안(서버 중심·에이전트 중심)을 실험(Fluent Bit 4.0.14 컨테이너)으로 심사해 종합했다.
- **결정:**
  1. IIS 열 순서는 표 `iis_layouts(host, file, dir, fields, seen_at)`(마이그레이션 014)에 둔다. 이벤트와 **같은 트랜잭션**에서 upsert 한다. 프로세스 안 캐시(`repository._IIS_FILE`·`_IIS_SITE`)는 정본이 아니며 커밋한 뒤에만 넣는다. 캐시에 없는 파일은 요청마다 한 번의 쿼리로 묻는다.
  2. 줄을 읽을 후보는 이 순서다: 같은 요청의 머리줄 → 그 파일의 저장된 열 순서 → 같은 폴더(`W3SVC<n>`)의 최신 열 순서 → 기본 순서.
     **어느 후보든 칸 수와 값 모양이 맞아야 쓴다.**
     - 그 파일의 순서(같은 요청의 머리줄·저장된 순서)는 서버(IIS)가 만드는 필드만 본다(`iis.plausible`): date·time·sc-status(100–999)·정수 필드·IP(`ipaddress` 로 확인). 요청자가 정하는 값(method·URI·UA·Referer·username)이 무엇이든 해석이 깨지지 않는다 — 해석 실패를 일부러 일으켜 규칙을 피하지 못하게.
     - 추정한 순서(같은 폴더·기본)는 더 엄격하다(`iis.plausible_guess`): IIS 가 늘 쓰는 필드(date·time·s-ip·c-ip·상태·하위 상태·win32·time-taken 등)가 비어 있으면 안 되고, method·URI·HTTP 버전이 요청 모양이어야 하며, 요청자 값 칸(username·UA·Referer·query·Cookie)에 숫자나 IP 만 있으면 안 된다.
       IIS 의 열 순서는 정해져 있어(포함·제외만 고름) 구성이 다르면 칸이 밀리고, 그러면 서버 값(IP·숫자)이 요청자 칸으로도 간다. 검토에서 ①만으로는 요청자가 UA 에 IP 를 넣어 `src_ip` 를 정하고 실제 IP 가 username 에 들어가는 것을 재현했다.
     맞는 것이 없으면 원문으로 저장한다(틀리게 읽지 않는다). 추정한 순서로 읽었으면 `raw.iis._layout` = `site`|`default`.
  3. 머리줄은 필드 이름(인쇄 가능·공백 없음·256자 이하 — 사용자 지정 필드의 한글 이름도, 100개 이하)과 PC·파일 경로(UTF-8 1024바이트, NUL 없음)를 확인한 뒤에만 배운다. 저장할 수 없는 값 때문에 요청 전체(다른 이벤트까지)가 거절되지 않게.
  4. 정리: 35일이 지난 열 순서는 지우되 폴더마다 최신 1개는 남긴다(월 단위·나누지 않는 파일은 머리줄이 처음 한 번뿐). 로그가 아니라 해석용 문맥이라 감사로그는 남기지 않는다.
  5. MSSQL 정규화기는 레코드의 **첫 줄**로 시각·프로세스·오류 번호를 읽고, 나머지 줄은 message 에 붙인다(`raw.mssql.lines` = 줄 수). 줄마다 온 레코드(에이전트 0.3.0 이하)와 묶인 레코드를 같은 방식으로 센다.
     에이전트 0.4.0 은 `multiline.parser`(시각으로 시작하는 줄 = 새 레코드)로 묶는다. 그 tail 은 `storage.type: filesystem` 이어야 한다(메모리면 멈출 때 묶던 레코드를 잃는다 — 실측). — 2단계.
  6. `Error:` 머리줄 짝(`_pending`)은 메모리에 그대로 두되 키에 파일을 더한다(한 PC 의 여러 인스턴스). DB 로 옮기는 것은 B-20.
- **이유:** 서버만 올리면 모든 에이전트 버전의 IIS 재시작 문제가 풀린다. 원본(raw)은 늘지 않는다. 추정에 모양 검사를 더해 '맞게 읽거나 원문으로 남기거나' 둘 중 하나가 되게 했다. multiline 은 원본을 바꾸지 않는다 — 에이전트가 보낸 레코드가 그대로 raw 다.
- **대가:**
  - 첫 설치 당일, 그리고 에이전트가 멈춘 사이 새로 생긴 파일은 머리줄이 오지 않는다(tail 이 끝부터 읽음). 같은 폴더의 열 순서가 있으면 그것으로 읽는다. 없으면 사용자 지정 열 순서 사이트는 다음 파일(00:00 UTC)까지 원문으로 남는다. → B-32.
  - 정수 열끼리만 순서가 바뀐 경우(sc-bytes↔time-taken)는 모양으로 가리지 못한다(보안 판단에 쓰는 필드는 아님).
  - 추정하는 동안(그 파일의 머리줄을 아직 못 받음) 요청자는 UA 등에 IP·숫자를 넣어 자기 줄을 원문으로 남길 수 있다(상태 코드 규칙을 피함). 틀린 IP 로 남는 것보다 낫다고 보았다. 숫자뿐인 사용자 이름·query 도 추정 동안은 원문이 된다.
  - 값 모양으로 가릴 수 없는 구성이 남는다(2차 검토, 기본 순서에서 한 칸 바뀐 구성 전수 탐색): 숫자 필드 하나(time-taken·win32·하위 상태)를 빼고 cs(Cookie) 를 더한 사이트는 추정하는 동안 요청자가 Referer 로 **자기 줄의 상태 코드**를 정할 수 있고, c-ip 를 기록하지 않는 사이트는 UA 의 IP 가 src_ip 가 될 수 있다. c-ip·sc-status 를 모두 기록하는 구성에서 다른 사람의 IP·사용자로 잘못 읽히는 경우는 찾지 못했다.
  - 업그레이드 직후에도 머리줄이 없다(옛 메모리 기억은 저장된 적이 없다): 사용자 지정 열 순서 사이트는 다음 파일(하루 단위면 00:00 UTC = 09:00 KST)까지 원문으로 남는다. 파일을 나누지 않는 사이트는 머리줄이 다시 올 때까지.
  - 한 파일 안에서 열 구성이 바뀐 뒤 옛 머리줄이 든 청크가 재시도로 늦게 오면 최신 열 순서를 덮을 수 있다(같은 파일의 머리줄은 보통 같아 드묾 — 모양 검사가 틀린 해석은 막는다).
  - 업그레이드 직후에는 표가 비어 있다(옛 메모리 기억은 저장된 적이 없다). 기본 열 순서 사이트는 `_layout: default` 로 바로 읽히고, 사용자 지정 사이트는 다음 새 파일까지 원문으로 남는다.
  - 0.4.0 에서는 `Error:` 머리줄과 본문이 다른 요청으로 갈리는 일이 잦다(multiline 이 본문을 다음 시각 줄이나 2초까지 붙잡는다 — 실측 9쌍 중 3쌍).
    짝 맞추기는 메모리라, 그 사이 서버가 다시 시작되거나 장애 뒤 재전송 순서가 바뀌면 본문에 번호가 붙지 않는다.
    순서가 뒤집혀 머리줄이 본문보다 늦게 오면, 그 머리줄이 같은 시각(1/100초)·프로세스의 다음 줄에 붙을 수 있다(드묾 — 같은 시각 줄들이 요청 경계에 걸쳐야 함).
    로그인 실패(18456)는 본문 문장으로 세므로 영향이 없고, 9002·823·824 같은 중요한 오류는 응용 프로그램 이벤트 로그에도 남아 규칙이 그쪽으로 걸린다. 짝을 DB 로 옮기는 것은 B-20.
  - MSSQL 효과는 에이전트를 다시 설치한 PC 부터. 0.4.0 에이전트 + 옛 서버는 묶인 레코드를 잘못 읽으므로(시각=받은 시각, 오류 번호 없음 — 실측) **서버를 먼저** 올린다.
  - 캐시는 워커 1개 전제다(ADR-006). 여러 워커가 되면 TTL 이 필요하다(B-20).
- **대안:**
  - 에이전트 Lua 가 레코드마다 `#Fields:` 를 붙이기 — 기각. Lua 오류는 dry-run 을 통과하고 실제 기동에서 엔진 전체(Windows 이벤트 포함)를 멈춘다. 기억이 없을 때마다 IIS 파일 전체를 엔진 스레드에서 다시 읽는다. IIS raw 가 +25~36% 영구히 커진다. 모든 IIS PC 를 다시 설치해야 효과가 난다.
  - 서버가 이어지는 줄을 붙잡았다가 합치기 — 원본 보존을 어긴다. 200 을 돌려준 뒤 유실될 수 있고, 요청 사이 순서도 믿을 수 없다.
  - 요청 사이 `Error:` 짝을 DB 로 찾기 — B-20.
  - 에이전트에서 `Error:` 머리줄과 본문까지 합치기 — spid·시각을 비교할 수 없어 끼어든 줄을 잘못 합친다. (짝이 요청 사이로 갈리는 문제를 풀 수 있어, 실제 ERRORLOG 에서 끼어드는 줄이 없는지 확인되면 다시 본다 — B-08)

## ADR-038 Windows EventData 이름은 서버가 붙이고, `f.EventData.<이름>` 은 별칭으로 본다
- **상태:** 채택 (2026-10-19, ADR-019 개정). 벤치마킹 조사(Windows 탐지 묶음)에서 드러난 결함을 고침.
- **배경:**
  - 에이전트는 Fluent Bit 4.0 이라 `event_data_as_map`(5.1.0, 2026-08 부터)이 없어 857359e 에서 빼고 `string_inserts` 만 보낸다.
    그런데 문서·UI 예시·기본 규칙 1000007(원격 데스크톱 무차별 대입)·1000009(관리자 그룹 추가)·보안 대시보드 위젯이
    `f.EventData.*` 를 써서 **실제 PC 에서는 맞을 수 없었다**. 시험·시뮬레이터가 EventData 맵을 넣어 보내 아무도 몰랐다.
  - 윈도 CI 러너에서 실제 이벤트(4624·4625·4688·4697·4720·4726·4732·4733·4738·7045·4104)를 일으켜 에이전트 설정으로 받아 보니:
    EventData 키가 없고, StringInserts 는 매니페스트 템플릿 순서이며, LogonType 같은 정수는 숫자로 온다.
    4624 v3 는 RemoteCredentialGuard 를 **중간에** 끼워 '새 필드는 뒤에 붙는다'가 늘 맞지는 않았다.
- **결정:**
  1. 서버가 `(공급자, 이벤트 ID[, 버전])` 템플릿(`normalizers/win_templates.py`)으로 StringInserts 에 이름을 붙여
     `raw.winevtlog.EventData` 에 덧붙인다(원본은 그대로 — AGENTS.md 원본 보존). 에이전트가 EventData 맵을 보내면 붙이지 않는다.
     배열보다 긴 이름은 버린다(옛 버전). 모르는 이벤트는 위치(`f.StringInserts.N`)로만 볼 수 있다.
  2. 검색·규칙·대시보드의 `f.EventData.<이름>` 은 **별칭**이다: 에이전트가 보낸 값이 먼저, 없으면(없음·JSON null) 서버가 붙인 값.
     SQL `COALESCE(raw #>> '{EventData,X}', raw #>> '{winevtlog,EventData,X}')`, Python `querylang.raw_field`,
     JS `rawField` 가 같은 뜻이다(케이스 표 querylang_cases.json, SYNC `raw_alias`). 별칭이 아닌 경로의 SQL 은 그대로다.
  3. 화면에서 값을 눌러 검색하면 `f.EventData.<이름>` 으로 만든다(`aliasPath`) — 이름을 보내는 에이전트의 PC 도 같이 맞는다.
  4. 공통 필드 username 은 이름으로 고른다. 그룹 구성원 변경(4728·4732·4756 등)은 TargetUserName 이 그룹 이름이라 바꾼 사람(SubjectUserName).
  5. 시험·시뮬레이터는 실제 에이전트 모양을 쓴다: `tests/fixtures/winevtlog/agent-fb4.0.14.jsonl`(윈도 CI 실측),
     `tools/simulate.py` 의 기본값은 StringInserts 만(`--event-data` 로 이름을 보내는 에이전트 흉내).
     윈도 CI(`tools/ci/capture_winlog.ps1`)가 매번 실제 이벤트를 받아 고정 자료와 모양(배열 길이·값의 형)을 비교한다.
- **이유:** 이미 설치된 사이트의 `alerts.yaml`·대시보드·사람이 쓴 검색이 고치지 않고 동작한다. Sigma 등 이름 기반 규칙을 들여올 바탕이 된다.
  위치 번호로 규칙을 고치는 안(`f.StringInserts.10`)은 버전마다 위치가 바뀌고(4624 v3) 사람이 읽을 수 없어 기각.
- **대가:** 템플릿이 있는 Windows 이벤트의 원본이 커진다 — 저장 크기(압축 포함) +6~39%(개발 DB 실측, 메시지가 길수록 작음).
  에이전트를 Fluent Bit 5.1(`event_data_as_map`)로 올리고 `string_inserts` 를 끄면 중복이 사라진다(로드맵). 템플릿은 손으로 늘린다
  (윈도 CI 의 실측 레코드로 길이를 확인). 같은 이름이 두 경로에 있어 필드 탐색에는 `winevtlog.EventData.*` 로 보인다(설명은 같음).
- **대안:** 조회할 때 이벤트 ID 별 위치로 바꾸는 SQL(CASE) — 저장은 늘지 않지만 같은 표를 SQL·Python·JS 세 곳에 두어야 하고
  상세·필드 탐색에 이름이 보이지 않아 기각. 에이전트를 지금 5.1 로 올리기 — 이미 설치된 4.0 PC 는 그대로 남아 서버 쪽이 어차피 필요.

## ADR-039 에이전트 하트비트는 전용 출력으로 보내고 2번 재시도 후 버린다 (에이전트 메모리)
- **상태:** 채택 (2026-10-29, ADR-027 의 에이전트 부분 보강). 에이전트 설정 Windows 0.4.1 · Linux 0.2.1.
- **배경:** 에이전트를 설치한 PC 에서 메모리를 많이 쓴다는 보고. Fluent Bit 4.0.14 소스로 확인한 원인:
  - 하트비트(dummy) 입력은 메모리 저장인데 `mem_buf_limit` 이 없어 상한이 없다. `storage.max_chunks_up` 은 filesystem 입력에만 걸린다.
  - 하트비트마다 새 조각이 생기고, 메모리 조각은 내용(약 100B)과 상관없이 **256KB 를 미리 잡는다**(`FLB_INPUT_CHUNK_SIZE`).
  - 하트비트가 로그와 같은 출력(`retry_limit: no_limits`)으로 가서, 서버에 못 보내는 동안(서버 중단·포트 막힘·키 틀림·TLS 오류)
    조각이 버려지지 않고 쌓인다. 30초마다 1개 → **장애 하루에 약 720MB**, 작업 수 상한(16384)까지 약 4GB. Windows 는 힙이 바로 잡는다.
  - 오래된 하트비트는 쓸모가 없다: 서버는 하트비트를 **받은 시각**으로 `last_heartbeat_at` 을 적는다(repository.py).
- **결정:**
  1. 하트비트 전용 http 출력(`match: heartbeat`, `retry_limit: 2`). 로그 출력은 `match_regex: '^(?!heartbeat$).*'` —
     허용 목록이 아니라 제외 정규식이라, 새 입력 tag 를 추가해도 버리지 않는 로그 출력으로 간다.
  2. 하트비트 입력에 `storage.type: memory` + `mem_buf_limit: 64K`(안전장치. 내용 바이트를 세므로 이것만으로는 못 막는다).
  3. `storage.max_chunks_up` 16 → 8, `storage.backlog.mem_limit` 16M → 8M, 출력 `workers: 1`(기본 2). 디스크에 더 남을 뿐 버리지 않는다.
  4. 두 출력 모두 TLS 블록을 둔다(설치 스크립트가 모든 `@@TLS` 블록을 켠다). `render_agent_configs.py` 가 http 출력 **전부**의 TLS,
     그리고 '재시도 제한 출력은 heartbeat 만, 로그 출력은 heartbeat 를 빼고 모든 로그 tag' 를 정적으로 검사한다.
  5. 윈도 CI(`tools/ci/agent_memory.py`)가 실제 Fluent Bit 로 서버 없이 2분(하트비트 1초) → 받는 쪽을 띄워 본다:
     옛 설정(0.4.0, `tools/ci/fixtures/windows-agent-0.4.0.yaml`) 대비 Private Bytes 증가가 절반 이하, 장애 중에 쓴 로그는 도착,
     장애 중 하트비트는 대부분 버려짐.
  6. PC 에서 잴 도구 `agent/windows/check-memory.ps1`(설치 묶음에 포함): Private Bytes·핸들·버퍼 크기를 CSV 로 남기고 판단을 출력.
- **기각:**
  - `storage.pause_on_chunks_overlimit: on` — 장애 중 재시도 조각이 상한을 채워 winevtlog 가 장애 내내 멈추고 디스크 버퍼에 쓰지 않는다.
    Security 로그(클라이언트 기본 20MB, 덮어쓰기)가 돌면 영구 유실. 원본 보존 원칙에 어긋난다.
  - 로그 출력의 `retry_limit` 을 유한값으로 — 4.0 에는 DLQ 가 없어 버려진다.
  - `read_limit_per_cycle` 축소·`flush` 늘리기 — 메모리를 줄이지 못한다(조각은 읽은 양과 상관없이 2MB 단위, flush 를 늘리면 조각이 더 오래 메모리에 남음).
  - Fluent Bit 4.2.8/5.1 로 올리기(winevtlog 렌더 실패 경로 누수·이중 해제 수정) — 렌더 실패가 드물고(로그에 'EvtRender failed') 실제 원인으로
    확인되지 않았다. 레코드 모양·서버 수신기 계열이 바뀌는 큰 변경이라 측정 결과를 보고 결정한다(BACKLOG B-33).
- **대가:** 서버가 돌아온 직후 PC 가 '온라인'이 되기까지 다음 하트비트(최대 30초)를 기다린다. 출력이 둘이라 30초마다 HTTP 요청이 하나 는다(작음).
  이미 설치된 PC 는 다시 설치해야 바뀐다(설치 묶음을 다시 받아 `install.cmd` — 기존 위치 기록 db 는 그대로라 유실·중복 없음).

## ADR-040 기록 종류별 보관기간, 보관 파일에 공통 필드 (형식 v2)
- **상태:** 채택 (2026-10-29, ADR-016 보완). 벤치마킹 조사(국내 법령·상용 제품 묶음)에서 드러난 두 결함을 고침.
- **배경:**
  - `WLM_RETENTION_DAYS` 하나로 로그 보관 파일·알림 이력·감사로그·점검 보고서를 같은 날 지웠다. 이 시스템의 권한 부여·변경·말소 기록
    (`user.*`·`user_group.*`)이 1년 만에 사라지는데, 개인정보의 안전성 확보조치 기준 제5조는 3년 보관을 요구한다.
  - 보관 파일(`archive.COLUMNS`)에 마이그레이션 007 의 `category`·`username`·`src_ip` 가 빠져 있었다. 보관했다가 복원한 달에서는
    `user:`·`ip:`·분류 검색이 0건이 되고(조사자가 '활동 없음'으로 오판), 분류로 범위를 정한 사용자에게는 보이지 않았다.
- **결정:**
  1. 보관기간을 기록 종류별로 나눈다: 로그 `WLM_RETENTION_DAYS`(그대로), 알림 `WLM_ALERT_RETENTION_DAYS`(비우면 로그와 같음),
     감사로그 `WLM_AUDIT_RETENTION_DAYS`(기본 1095), 점검 보고서 `WLM_REPORT_RETENTION_DAYS`(기본 1095).
     감사로그는 접두어별로 나누지 않고 전체를 3년 둔다 — 행이 작아 부담이 없고, 어떤 동작이 '권한 변경'인지 가르다 틀리면 되돌릴 수 없다.
  2. 법정 최소(접속기록 365, 권한 기록 1095)보다 짧으면 기동 로그 경고·로그 보관 화면 빨간 줄·점검 보고서 '점검 필요'.
     민감정보 처리 시스템의 접속기록 2년(제8조)은 어떤 로그가 해당하는지 사이트가 판단하므로 안내만 한다(기본값은 바꾸지 않음).
  3. 보관 파일 형식 v2 는 공통 필드를 넣는다. v1 을 복원하면 원본(+ 서버가 덧붙인 `raw.<소스>`)에서 다시 구한다
     — `normalizers.derive_common`. 정규화기를 다시 돌리지 않는 것은 IIS 열 순서(요청 문맥)·MSSQL 짝(메모리) 없이도
     저장 당시와 같은 값을 얻기 위해서다(모든 소스에 대해 '정규화 값 = 다시 구한 값' 왕복 시험). 복원 감사로그에 다시 구한 행 수.
  4. `events` 의 열과 `archive.COLUMNS` 가 같은지 시험이 본다 — 열을 더하면 보관 파일에도.
- **이유:** 둘 다 '된다고 말하는 것'이 틀린 부분이고, 첫 운영 설치(B-25) 전에 고치면 v1 보관 파일이나 1년 만의 감사로그 파기가 운영에
  한 번도 생기지 않는다. 지운 감사로그는 되돌릴 수 없다.
- **대가:** 감사로그·보고서가 3년 쌓인다(행이 작아 수십 MB 수준). 업그레이드하면 기본값이 3년으로 늘어나므로, 1년보다 오래된 감사로그가
  이미 지워진 사이트는 그만큼 남지 않는다(되돌릴 수 없음).
- **대안:** 감사로그를 동작 접두어별로 다른 기간 — 분류 실수의 대가가 커서 기각. 기본 로그 보관을 730 으로 — 접속기록 해당 여부는 사이트
  판단이고 저장 공간이 두 배라 안내로 대신.
