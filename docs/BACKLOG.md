## 작업 규칙 (사람·AI 에이전트 공통)

1. 항목을 시작하면 아래 요약 표의 **상태**를 `진행 중`으로 바꾸고, 끝나면 항목을 지우고 PROJECT.md·DECISIONS.md 에 반영합니다.
2. 각 항목의 **완료 기준**을 모두 만족해야 끝난 것입니다. 공통 완료 기준(테스트·린트·브라우저 확인·문서)은 [AGENTS.md](../AGENTS.md) 를 따릅니다.
3. 새 의존성은 OSI 승인 라이선스만 씁니다(AGENTS.md 절대 규칙 1). 항목에 적힌 후보 라이선스도 도입 전에 다시 확인합니다.
4. DB 변경은 새 마이그레이션 파일로만 합니다. 번호는 `server/migrations/` 의 마지막 파일 번호 + 1 입니다.
5. 새로 할 일을 발견하면 여기에 **번호를 이어서** 추가합니다. 번호는 재사용하지 않습니다.
6. 다른 제품에서 가져온 것은 **아이디어만** 다시 구현합니다(코드·규칙 파일 복사 금지, COMPARISON.md §1). 예외는 라이선스가 허락하고 표시 조건을 지키는 경우뿐입니다 — Sigma 규칙(DRL 1.1, 저자·출처 표시, B-14), OTRF Security-Datasets·Palantir WEF·sysmon-modular 같은 MIT 자료(고지). 법령·ATT&CK 처럼 '확인 필요'로 적힌 근거는 1차 출처를 확인한 뒤에 씁니다(COMPARISON.md §7).

### B-34 알림 엔진 자체 감시와 전송 분리
- **1단계 완료 (2026-10-29, ADR-045):** 전송 대기열(`alert_deliveries` + 017)과 전송기(lock 727_004, 받는 곳마다 한 줄, 받는 곳 장애는 한 번만 시도),
  보내다 멈춘 행 다시 보내기·하루 지난 행 만료, 규칙 쿼리 시간 상한(`WLM_ALERT_RULE_TIMEOUT_SEC`, 조회 자리 안 씀), 규칙별 상태(일부만·시간 초과·
  평가 공백), 상태 판단 한 곳(`alerts/health.py`) → 화면 상태 띠·'평가' 칸·알림 대상 줄·`/healthz/alerts`·점검 보고서.
- **2단계 완료 (2026-10-30):** 감시 작업(멈춘 평가·전송 작업 다시 시작, 10분에 한 번), 내장 시스템 알림('알림 엔진 멈춤'·'알림 전송 실패'·
  '알림 규칙 동작 안 함')과 `settings.fallback_notify`(비우면 점검 보고서 받는 곳), 감사로그 `alerts.health.*`, 재알림 간격에 든 묶음 SQL 미리 빼기(적대적 검토 반영).
- **남은 것 완료 (2026-10-31, ADR-045 보완):** 주간 정기 시험 전송(`WLM_ALERT_TEST_WEEKDAY`·`TIME`, 실패 → 기존 '알림 전송 실패'·`test_failed`),
  Oracle 생존 신호(연동의 선택 SQL, 1분마다, `heartbeat_failing`). B-36 남은 것(관리 작업 알림)은 `fallback_notify` 경로를 쓴다.
- **왜:**
  - 엔진 상태는 전체에 하나(`last_run_at`·`last_error`·`config_error`)뿐입니다. 규칙 하나가 실패하면 서버 로그 한 줄('규칙 평가 실패')만 남고, 후보가 `alert_candidates` 의 `LIMIT 100` 에 닿아 잘려도 표시가 없습니다(웜이 300대에 퍼지면 100대만 알림).
  - 평가 루프가 전송을 기다립니다. `fire()` 가 알림마다 전송을 await 하고(대상당 최대 30초, `SEND_TIMEOUT_SEC`), 재시도(`retry_failed`)도 같은 주기 안에서 돕니다. SMTP 가 죽은 채 알림이 100건이면 한 주기가 최대 50분 멈추고, 그동안 창(`now - window`) 밖으로 밀린 이벤트는 다시 평가되지 않습니다. 단일 프로세스라 서버가 멈추면 수집도 멈추므로(ADR-006·ADR-011), 평가 공백의 실제 원인은 이것입니다.
  - 알림 경로(SMTP 비밀번호 만료, 웹훅 토큰 폐기)가 깨져도 실제 알림이 나기 전까지 모릅니다. 시험 전송은 사람이 누를 때만 합니다. 폐쇄망 병원에는 외부 감시 도구(NMS)가 없는 경우가 많습니다.
  - `/healthz` 는 DB `SELECT 1` 만 봅니다.
- **규모 (L):** 두 단계로 나눠 합니다. 1단계(M)는 전송 분리·규칙별 상태·잘림 요약 알림, 2단계(M)는 대체 경로·엔진 쿼리 시간 상한·`/healthz/engine`·정기 시험 전송·Oracle 하트비트·보고서 항목입니다.
- **구현 방향:**
  - **전송 분리:** `fire()` 는 `alerts`·`alert_deliveries(pending)` 만 기록하고, 같은 프로세스의 디스패처 작업(advisory lock)이 보냅니다. 재시도도 디스패처가 합니다. 평가 주기는 전송 속도와 상관없이 돕니다. 묶음 전송(B-41)·복구 통지(B-35 2단계)·에스컬레이션(B-43)도 이 경로를 씁니다.
  - **규칙별 상태:** 새 마이그레이션 `rule_state`(규칙, 평가 시각, 상태 정상·오류·느림·잘림, 오류 문구, 소요 시간, 후보 수). 규칙 관리 표에 상태 칩. 잘리면 '규칙 X: 대상 n개 이상, 일부만 알림' 요약 알림 1건.
  - **대체 경로:** 내장 시스템 알림 '규칙 평가 실패(연속 3회)'·'알림 전송 실패: <대상>'은 `fallback_notify`(주 대상과 다른 경로, 예: Oracle·다른 메일)로 보냅니다. 내장 알림 이름은 ADR-043 이 만든 `alerts/builtin.py` 에 더합니다(사용자 규칙과 이름이 겹치지 않게).
  - **엔진 쿼리 시간 상한:** 규칙마다 `SET LOCAL statement_timeout` 을 걸되, 화면 검색용 `SEARCH_SLOTS` 세마포를 거치지 않는 전용 경로로 합니다(ADR-035 가 남긴 수집·엔진 몫을 지킴).
  - **생존 신호:** `/healthz/engine` — 마지막 평가가 주기의 3배보다 오래면 503. `INGEST_PORT_PATHS` 에는 넣지 않습니다(`IngestPortGuard` 는 경로만 보므로 `/healthz?engine=1` 처럼 만들면 수집 포트로도 열림).
  - **정기 시험 전송:** 알림 대상마다 주 1회(결과는 `alert_deliveries`·감사로그). 실패하면 점검 보고서 '점검 필요'.
  - **Oracle 하트비트 행(선택):** 기존 Oracle 연동으로 1분마다 한 행을 써서, 서버 전체가 죽었을 때 병원 DB 감시가 정체를 잡게 합니다.
  - 점검 보고서 '점검 필요'에 오류 규칙 수·전송 포기 수·시험 전송 실패를 넣습니다(옛 payload 도 그림).
  - 나중에: 디스크 소진 예측(B-69 와 함께), 수집기 마지막 수신. 서버 시계 점검은 B-57 이 맡습니다.
- **완료 기준:** 규칙 하나를 일부러 실패·지연시켜도 다른 규칙은 평가되고 상태·대체 알림이 나옴, SMTP 를 막은 채 알림 100건에서도 평가 주기가 늦어지지 않음, LIMIT 초과 요약 알림, 엔진을 멈추면 `/healthz/engine` 503 이고 수집 포트에서는 막힘, 주간 시험 전송 기록, 화면 확인, PROJECT.md §6·ISMS.md 2.11.3·2.9.2 갱신.
- **출처:** COMPARISON.md §5.2 / Prometheus 규칙 health·Alertmanager dispatcher·Watchdog(늘 울리는 알림으로 알림 경로 고장을 잡음), Grafana Error·NoData, Elastic 규칙 실행 감시.

### B-35 알림 수명주기 — 해결 뒤 재발·억제 건수·지연 수신 표시
- **1단계 완료 (2026-10-30, ADR-029 보완):** 해결 뒤 새 이벤트면 재발(확인함은 간격 유지), 다시 알릴 때 '지난 알림 이후 n건', 상세의
  '이 알림 뒤 n건 · 마지막 시각', 지연 수신 표시. **억제 건수는 열·워터마크 대신 볼 때 센다** — 주기마다 세는 비용과 이중 집계가 없다
  (대신 지금 규칙 조건으로 센다, 목록에는 없고 상세·다음 알림에만). 2단계는 아래 그대로.
- **왜:**
  - 재알림 간격은 (규칙, 대상)의 마지막 `fired_at` 만 봅니다(`repository.last_alert` 는 처리 상태를 읽지 않음). 담당자가 '해결'한 EMR 서비스가 다시 죽어도 간격(규칙마다 5분~2시간) 동안 알림이 나지 않습니다.
  - 건너뛴 동안 몇 건이 더 왔는지, 언제까지 계속됐는지 남지 않습니다(ISMS 2.11.5 '언제까지 계속됐나' 증적).
  - 장애가 끝나면 에이전트가 디스크 버퍼의 몇 시간치를 한꺼번에 보냅니다(ADR-039). 평가는 수신 시각 기준이라 '로그온 실패 급증'(20건/10분) 같은 건수 규칙이 실제로는 몇 시간에 흩어진 이벤트에 울립니다.
- **구현 방향 (1단계, S):**
  - **재발:** 가장 최근 알림이 해결됨이고, **`received_at > resolved_at` 인 새 이벤트가 있을 때만** 재알림 간격을 무시합니다. 무음 끝의 `_resumed` 와 같은 방식입니다. 해결 직후 창 안에 남은 같은 이벤트로는 다시 울리지 않습니다. 확인함(acked)은 지금처럼 간격을 지킵니다.
  - **억제 건수:** `alerts` 에 `suppressed_count`·`suppressed_last_at`·워터마크(마이그레이션). 워터마크 이후 수신분만 세어 이중 집계를 막습니다. 목록·상세에 '이후 +342건 · 마지막 3분 전', 다음 재알림 본문에 '지난 알림 이후 n건'. 전송 횟수는 늘리지 않습니다.
  - **지연 수신 표시:** 후보의 `last_ts - first_ts` 가 창보다 훨씬 길면 '지연 수신분 포함 (발생 시각 x~y)'으로 표시합니다(`alert_candidates` 가 이미 first_ts·last_ts 를 돌려줌). 발생 시각 기준으로 다시 판정할지는 규칙 옵션으로 검토합니다.
- **2단계 완료 (2026-10-30, ADR-029 보완):** `resolve: auto|manual`(끊김 규칙 auto 기본, 기본 팩 오류 다발 규칙 둘), 풀림 판단(집계 기간 건수 < 기준,
  마지막 알림 뒤 max(창, 5분), PC 묶음은 PC 가 살아 있어야), `auto_resolved`·처리 기록 `auto_resolve`, 사람이 다시 연 알림은 그대로,
  받은 곳에만 해소 통지(보낼 때 다시 봄: 다시 열림·새 알림·전해지지 않음 / 무음 중·7일 넘은 알림은 해결만, 못 보낸 알림은 건너뜀),
  `alert_deliveries.action`(019), 웹훅 json·Oracle `dedup_key`·`event_action`(Oracle 은 SQL 에 있을 때만), 보고서 자동 해결 따로·중앙값은 사람만.
  남은 것: 사람이 해결한 알림의 해소 통지(필요하면), 규칙별 '오르내림' 통계(B-44 와 함께).
- **2단계 (M, 이어서):**
  - 자동 해소 `resolve: auto` 는 **운영 규칙만**(agent_silent, 서비스 비정상 종료·서버 응답 없음 같은 운영 분류)에 기본값으로 둡니다. 보안 규칙은 사람만 해결합니다 — 사람이 검토하지 않은 보안 알림이 '해결됨'으로 보고서에 남지 않게. 자동 해소는 보고서에서 따로 셉니다.
  - `agent_silent` 는 하트비트가 돌아오면 해소합니다. 복구 통지는 그 알림을 받은 대상에만 보내고, 무음 중 시작한 문제는 생략합니다. 전송은 B-34 경로.
  - 웹훅 json·Oracle 바인드에 고정 키 `DEDUP_KEY`(규칙·대상 해시)와 `EVENT_ACTION`(trigger·resolve) — 사내 사고관리·SMS 가 티켓을 열고 닫게.
  - `alert_notes` 의 action CHECK 를 넓히는 마이그레이션(수정 금지 트리거와 충돌하지 않게). ADR-029 에 보완을 기록합니다.
- **완료 기준:** 해결 직후 같은 이벤트로는 울리지 않고 새 이벤트면 바로 울림, acked 는 간격 유지, 억제 건수 이중 집계 없음, 버퍼 몰아 보내기 시나리오에서 지연 수신 표시, 화면 확인, PROJECT.md §6·ADR-029·ISMS.md 2.11.5 갱신. 2단계는 자동 해소 대상·복구 통지 대상 시험, dedup_key 스냅샷.
- **출처:** COMPARISON.md §5.2 / Elastic 알림 억제, Prometheus `keep_firing_for`, Alertmanager `send_resolved`, Zabbix 복구 식, PagerDuty Events v2 `dedup_key`.

- **2단계 완료 (2026-10-30):** `alerts/adminwatch.py` — 받는 곳 약화(저장 앞뒤 비교)·관리 권한 부여·보관 파일 복원을 '관리 작업 알림'(무음 불가)으로,

  - 수신 그룹의 구성원·채널 변경을 판본·약화 판정에 넣습니다(받는 사람을 빼면 약해진 것).

### B-37 수집 완전성 1단계 — PC×채널 끊김·규칙별 데이터 유무

### B-40 수집 견고성 — 문제 레코드 격리·수집 거절 장부
- **완료 (2026-10-29, ADR-044):** 정규화 예외는 레코드 단위(`raw._ingest.error`), 값 오류는 반씩 나눠 문제 레코드만 `ingest_quarantine`(016),
  짝 없는 서로게이트·글자 그대로의 `\u0000`(재현 — 예전 `_json` 이 JSON 을 깨뜨림) 처리, 수집 거절 장부 `ingest_rejections`(메모리 → 30초마다),
  수집 PC 화면 '수집 거절·격리'(관리자, 원본 열람은 접속기록), 점검 보고서. 남은 것은 아래 '다음(P2)'의 본문 해시 중복 제거.
- **왜:**
  - aeb38bf 로 NUL 은 막았지만, 정규화기에서 예외가 하나라도 나면(새 템플릿 경로 등) 그 요청 전체가 500 이 됩니다. `routers/ingest` 의 정규화 루프에 레코드 단위 예외 처리가 없고, `insert_batch` 는 파티션 없음(CheckViolation)만 다룹니다. 에이전트·수집기는 `retry_limit: no_limits` 라 같은 청크를 끝없이 다시 보내고, Fluent Bit 4.0 에는 처리 못 한 레코드 보관함(dead letter queue)이 없습니다(ADR-039).
  - 서버는 거절한 요청을 어디에도 남기지 않습니다(`_check_key` 는 401 만 돌려줌). 키를 바꾼 뒤 옛 키를 쓰는 PC 는 그냥 '오프라인'으로만 보입니다.
- **규모 (M):** 레코드 단위 예외 처리는 S, 격리 표·거절 장부는 M 입니다.
- **구현 방향:**
  - (S) 레코드 단위 try/except: 정규화가 실패하면 generic 이벤트 + `raw._ingest.error` 로 저장합니다(원본 보존).
    - `raw._ingest` 는 소스가 아니라 서버 수집 단계가 덧붙이는 예약 이름입니다(밑줄로 시작해 원본 키와 겹치지 않음). 도입할 때 PROJECT.md §3.2 와 AGENTS.md 절대 규칙 2 의 `raw.<소스>.*` 옆에 적습니다. B-58 의 `claimed_host` 도 여기에 둡니다.
  - (M) 저장이 데이터 오류로 실패하면 배치를 둘로 나눠 가며 문제 레코드만 `ingest_quarantine` 표(마이그레이션)로 보내고, 나머지는 저장하고 200 을 돌려줍니다.
  - (M) 수집 거절 장부: client_ip·상태(400·401·413·500)·사유·처음/마지막 시각·횟수. 수집 PC 화면과 일간 보고서에 보입니다. 401·TLS 오류를 서버에서 볼 유일한 방법입니다(에이전트 자기 로그는 같은 출력이라 그동안 못 옴 — B-57).
  - 다음(P2): 에이전트는 한 번 이상 전달(at-least-once)이라 같은 청크가 두 번 올 수 있습니다. 압축을 푼 본문의 SHA-256 을 24시간 기억해, 응답이 유실된 뒤 같은 청크가 다시 오면 중복 저장 없이 200 을 돌려줍니다.
- **완료 기준:** 정규화 예외·DB 데이터 오류를 일부러 일으켜도 같은 요청의 다른 레코드는 저장되고 문제 레코드는 격리됨, 잘못된 키 요청이 장부에 남음, 화면·보고서 확인, PROJECT.md §3.1·ISMS.md 2.9.4 갱신.
- **출처:** COMPARISON.md §4·§5.3 / 검토(누락 비평, 실측). 개념: dead letter queue(처리 못 한 레코드 보관함).

### B-08 IIS 열 순서 영속화, MSSQL 여러 줄 합치기
- **왜 (IIS):** `#Fields:` 기억이 프로세스 메모리라 서버 재시작 직후 사용자 지정 열 순서 파일이 기본 순서로 잘못 읽혔습니다(ADR-020, 재현).
- **왜 (MSSQL):** ERRORLOG 의 시작 배너·`Registry startup parameters` 의 이어지는 줄·여러 줄 메시지가 줄마다 따로 저장됩니다. 스택 덤프·교착 그래프는 줄마다 시각이 붙는 형식이라 묶이지 않습니다(형식 지식 — 실제 샘플로 확인 필요).
- **한 것 (2026-10-19, ADR-037):**
  - 서버: 열 순서를 `iis_layouts`(마이그레이션 014)에 이벤트와 같은 트랜잭션으로 저장, 후보(같은 요청 → 파일 → 같은 폴더 → 기본)마다 값 모양 검사(추정한 순서는 더 엄격), 맞는 것이 없으면 원문, `raw.iis._layout`. MSSQL 은 첫 줄 기준 해석(`raw.mssql.lines`), 짝 키에 파일. 재시작·멈춘 사이 새 파일·실패한 요청·정리 통합 시험, 개발 서버 실제 재시작으로 확인. 검토(4관점·반박 검증) 9건 반영.
  - 에이전트 설정 0.4.0: `multiline.parser mssql_errorlog`(시각으로 시작하는 줄 = 새 레코드), 그 tail 은 `storage.type: filesystem`. `render_agent_configs` 의 multiline 정적 검사, `tools/ci/test_fluentbit_mssql.sh`(실제 Fluent Bit: 고정 ERRORLOG 묶음 결과, 서버가 꺼진 채 멈췄다 다시 띄우기 — memory 면 실패), 윈도 CI(윈도 빌드의 같은 결과, ERRORLOG 를 켠 서비스 기동), `tests/test_agent_sync.py`(틀의 정규식 ↔ 서버 `_LINE`, Fluent Bit 출력으로 0.3.0·0.4.0 집계 동등).
- **남은 것:**
  - 실제 샘플: ERRORLOG(UTF-16LE·CRLF 유지, 이름·IP 가림 — 배너·시작 인자·로그인 실패 짝·여러 줄 메시지)와 사용자 지정 필드 IIS `u_ex*.log`(B-25·B-28 실기 때). 'iisreset 뒤 같은 파일에 머리줄 묶음을 다시 쓰는지'도 확인. 샘플은 `server/tests/fixtures/mssql/` 에 두고 `test_fluentbit_mssql.sh … --update`.
  - 같은 샘플로 `Error:` 머리줄과 본문 사이에 다른 줄이 끼는지 확인 — 끼지 않으면 에이전트 multiline 에서 둘을 한 레코드로 묶어 '요청 사이로 갈린 짝'(ADR-037 대가)을 없앤다. 끼면 짝을 DB 로(B-20).
  - 윈도 서비스 정지(SCM) 때 묶던 레코드가 버퍼에 남는지는 실기(B-28)에서 — 리눅스 SIGTERM 으로만 확인했다.
- **완료 기준:** 재시작 시나리오 테스트(완료), 실제 ERRORLOG 샘플(여러 줄 포함)로 회귀 테스트, 에이전트 `--dry-run`·실제 실행 통과.

### B-09 시간별 집계 테이블
- **왜:** 30일 이상 집계는 행 수에 비례해 느려집니다(PERFORMANCE.md: 하루 수백만 건부터 체감). 그 규모에서는 화면 조회 시간 상한(30초, ADR-035)에 걸려 503 이 됩니다.
- **구현 방향:** `events_hourly(hour, host, category, source, channel, event_id, level, n)` 를 매 5분 증분 갱신(마지막 처리 `received_at` 기억). `repository.py` 의 count/timeseries/top 이 기간 ≥ 7일이고 조건이 집계 열만 쓰면 집계 테이블을 씁니다(원본 필드·메시지 조건이면 원본). 로테이션 때 집계는 원본보다 오래 보관(추세용 1~3년).
- **벤치마킹(2026-10-29) — 설계 변경:** 위의 '마지막 처리 `received_at` 기억' 증분에는 경합이 있습니다. `received_at` 의 기본값 `now()` 는 트랜잭션 시작 시각이라, 워터마크 전에 시작해 뒤에 커밋한 수집 트랜잭션의 행이 영원히 빠집니다.
  - 대신 수집 트랜잭션(`repository._write`)에서 (시 단위 ts, host, source, category, channel, event_id, level) 건수를 **같이 INSERT** 합니다(덧붙이기만이라 잠금 경합 없음, 늦게 온 이벤트도 제 버킷에). 정비 주기에 지난 버킷을 합쳐 압축합니다.
  - 질의는 가운데 온전한 시간은 집계 표, 양 끝 조각은 원본으로 합칩니다(겹치지 않아 이중 집계 없음).
  - 출처: COMPARISON.md §5.5 / ClickHouse 증분 MV, TimescaleDB 실시간 집계(개념만, TSL 이라 도입 안 함).
- **완료 기준:** 벤치(`tools/bench`)로 30일·90일 화면 전후 비교를 PERFORMANCE.md 에 기록, 집계와 원본 결과 일치 테스트(케이스 표 조건), 늦게 도착한 이벤트·동시 트랜잭션 시험.

### B-10 원본 필드 검색 색인 (GIN 사전 필터 검토)
- **왜:** `f.EventData.LogonType` 같은 원본 필드 조건은 jsonb 전체를 훑습니다(7일 0.3초, 기간이 길면 증가).
- **구현 방향:** 자주 쓰는 경로에 표현식 인덱스(마이그레이션). 후보: `raw->'EventData'->>'LogonType'`, `raw->'iis'->>'uri_stem'`, `raw->'mssql'->>'error'`. 필드 탐색 화면에 "자주 검색됨" 표시(감사로그의 검색 조건 집계)로 후보를 고릅니다.
- **벤치마킹(2026-10-29):** 경로마다 식 색인을 만들면 경로마다 마이그레이션이 필요하고, 조사자가 새 필드로 찾으면 효과가 없습니다. 또 ADR-038 이후 이름은 `raw.winevtlog.EventData` 쪽에 있으니 위 후보 경로를 다시 봅니다.
  - 대안: 파티션별 GIN(`jsonb_path_ops`, 행마다 다른 키는 뺌)을 두고, `where_clause` 가 `f.경로=값` 마다 원래 조건에 `@>` 사전 필터를 **덧붙입니다**(원래 조건이 남아 결과는 같음, where 스냅샷은 의도적으로 갱신). 제외(`-f.`)에는 붙이지 않습니다.
  - 쓰기 비용이 크면 닫힌 파티션에만 만듭니다. 출처: COMPARISON.md §5.5 / ClickStack 속성 역색인, PostgreSQL GIN.
- **완료 기준:** 벤치 전후 기록(ADR-017 처럼 느려지면 기각 기록), 수집 처리량 저하 5% 이내, 사전 필터를 붙여도 결과가 같음(케이스 표).

### B-11 에이전트 중앙 관리
- **왜:** PC 가 많아지면 설정 변경(채널 추가, IIS 켜기)을 PC 마다 해야 합니다.
- **구현 방향 (단계):**
  1. 수집 PC 화면에 에이전트 설정 버전·Fluent Bit 버전·수집 채널 표시(하트비트 `meta` 확장), 기준 버전과 다르면 표시.
  2. GPO/SCCM/Ansible 배포 가이드와 스크립트(`install.ps1` 무인 설치 옵션 정리).
  3. (필요 시) 서버가 설정 파일을 내려주고 에이전트 쪽 작은 갱신 작업(예약 작업)이 가져가는 방식. 보안 검토 필수(설정 위조 = 수집 중단).
- **벤치마킹(2026-10-29):**
  - 1단계를 '기준 대비 실제 설정 차이'로 구체화: 하트비트의 `config_version` 은 틀에 손으로 올리는 상수 하나라 같은 버전 안의 설치 스위치(IIS·MSSQL·TLS·채널)와 Fluent Bit 버전을 구별하지 못합니다. 설치 때 채운 설정의 SHA-256·프로필·Fluent Bit 버전을 하트비트에 넣고, 서버는 묶음을 만들 때 같은 렌더러로 기대 해시를 계산해 '일치 / 다름(옛 묶음) / 알 수 없음' 을 보입니다.
  - 상태 모델: 정상·지연·오프라인(예상 밖)·꺼짐(예상됨)·비활성(30일)·설치됨·수신 없음(묶음 내려받기 감사로그와 대조). 프로필별 기대 일정(서버 24시간, 단말은 근무 창 B-42) — 지금은 전역 90초/900초라 퇴근하며 끈 PC 까지 일간 보고서의 '연락이 끊긴 PC' 가 됩니다. `agent_silent` 는 hosts 목록 대신 프로필도 받게.
  - 3단계는 설정 '파일'이 아니라 **허용 매개변수만**(채널·IIS·MSSQL·로그 수준) 당겨옵니다. 서버 주소·CA 지문·키·틀은 원격으로 못 바꿉니다. 받은 값을 로컬에서 렌더·`--dry-run`, 마지막 정상 설정(LKG, last known good) 보관, 실패하면 되돌림. Fluent Bit `in_calyptia_fleet` 은 흉내 내지 않습니다(COMPARISON.md §6).
  - 출처: COMPARISON.md §5.3 / Wazuh merged.mg 체크섬, Elastic Fleet 상태 모델, Graylog Sidecar ETag·검증 명령, OpAMP 원격 설정 보안 지침.
- **완료 기준:** 1·2단계 완료로 일단 종료, 3단계는 DECISIONS.md 에 결정 기록 후 착수. 1단계는 설정 해시 일치 판정·프로필별 상태 판정 시험과 윈도 CI 실제 설치로 하트비트 칸 확인.

### B-12 사내 SSO

### B-13 순서·부재 상관 규칙
- **왜:** "로그온 실패 N회 후 성공(계정 탈취 의심)", "새 계정 생성 직후 관리자 그룹 추가" 같은 탐지는 건수 규칙으로 못 합니다.
- **구현 방향:** `rules.py` 의 `RULE_KINDS` 에 `sequence` 추가. 형식(안): `steps: [{match, threshold}, {match}]`, `within: 10m`, `same: [ip]` 또는 `[user]`. `engine.py` 에서 단계별 집계를 `same` 키로 조인(SQL 한 문장). 기본 규칙 2~3개 추가(MITRE T1110 + 성공, T1136 → T1098).
- **벤치마킹(2026-10-29) — 의미 구체화:**
  - 단계는 인라인 match 이거나 **다른 규칙 이름 참조**(Sigma temporal). 단계마다 다른 필드를 같은 키로 맞춤(Sigma aliases — 예: 4720 TargetUserName ↔ 4732 MemberName).
  - `until`(사이에 끼면 무효)과 `absent`(부재, within 필수). 예: '핵심 서비스 중지 뒤 10분 안에 다시 실행되지 않음'.
  - 순서는 발생 시각 ts 로 판단하되 후보는 `received_at ≥ now − (within + 지연 여유)` 로 가져옵니다(ADR-011 유지). 키마다 가장 최근 시퀀스 1개만, (규칙, 키, 마지막 단계 이벤트)로 한 번만 발화(EQL). 묶음 키가 없는 이벤트는 빼고(ADR-041 3-1 과 같게), 넘치면 잘림 기록(B-34).
  - `group_by` 여러 키(ADR-041 '다음 단계')도 이때 함께 — `same: [user, host]` 와 같은 구조.
  - payload 에 단계별 증거 이벤트 id·시각 → 상세 타임라인. 예외(B-46)는 모든 단계에.
  - 기본 규칙 후보에 '감사 정책 변경 뒤 로그 삭제'를 더합니다.
  - 출처: COMPARISON.md §5.1 / Elastic EQL sequence, Sigma correlation(temporal·temporal_ordered), OpenSearch 상관 규칙.
- **완료 기준:** 순서·시간 경계 테스트(정확히 within, 순서 뒤바뀜, until 위치, NULL 키, 늦게 도착, 한 번만 발화), 시뮬레이터에 시나리오 추가(`tools/simulate.py`), 미리보기 지원, 규칙 팩 문서 갱신.

### B-30 앱 수준 접근 IP 제한
- **왜:** 관리 기능(사용자·환경설정·규칙·에이전트 묶음)을 관리 대역에서만 쓰게 하는 것은 지금 방화벽에만 기댑니다(ISMS 2.6.x). Docker 게시 포트는 호스트 방화벽을 우회합니다.
- **구현 방향:** `WLM_ADMIN_ALLOW_CIDRS`(관리 기능), `WLM_WEB_ALLOW_CIDRS`·`WLM_INGEST_ALLOW_CIDRS`(포트별). 관리자 로그인은 **비밀번호를 확인하기 전에** 막아 맞았는지 알려 주지 않습니다. `require_admin` 과 위임 가능한 관리 권한(`require_permission`)에도 같은 검사. 접속 IP 는 소켓 기준(신뢰 프록시면 X-Forwarded-For, ADR-036).
- **순서:** B-25 의 시험 서버 설치에서 접속 IP 실측을 먼저 → 그 결과로 B-30 구현 → 운영(병원) 첫 설치 전에 B-30·B-74 완료. 실측할 것은 운영 Linux 에서 접속 IP 가 실제 PC IP 로 보이는지입니다.
- **벤치마킹(2026-10-29):** 관리자 2단계 인증(B-74)과 함께 위 순서로 합니다. ISMS-P 심사가 현장 실증·모의침투로 바뀐다는 보도가 있어(확인 필요, COMPARISON.md §7) 이 서버 자체가 시험 대상이 될 수 있습니다.
- **완료 기준:** 허용 밖 IP 의 관리 로그인·관리 API 거부 시험, 감사로그에 거부 기록, ISMS.md 2.6.x 갱신.

### B-32 에이전트가 멈춘 사이 생긴 파일을 처음부터 읽기
- **왜:** Fluent Bit tail 은 위치 기록(db)이 없는 파일을 기동 때 끝부터 읽습니다(`read_from_head: false`). 에이전트가 멈춘 사이 새로 생긴 파일도 마찬가지라 앞부분이 유실됩니다(실측, ADR-037). IIS 는 날짜가 바뀐 파일의 `#Fields:` 와 첫 줄들, SQL Server 를 다시 시작해 순환된 ERRORLOG 는 시작 배너가 사라집니다.
- **구현 방향:** `read_from_head: true` + `ignore_older`(4.0.14 에서 파일 수정 시각으로 동작, 실측). 첫 설치 때 하루~이틀 치를 몰아 읽는 적재량, **알림은 수신 시각 기준이라 과거 오류가 한꺼번에 알림이 되는 것**, ERRORLOG 전체를 다시 읽는 크기를 함께 정합니다. 몰아 읽은 과거분의 알림 표시는 B-35 의 '지연 수신 표시'를 씁니다.
- **완료 기준:** 에이전트 정지 → 새 파일 생성 → 재기동 시험(Fluent Bit 컨테이너)에서 머리줄·첫 줄 수신, 첫 설치 적재량·알림 영향 기록. 되면 IIS 머리줄 공백(첫 설치·멈춘 사이 새 파일)도 사라집니다.

### B-26 알림 받는 곳 경로(route) — 라벨로 팀별 알림
- **왜:** 지금 알림 수신 그룹(메일 받는 사람)과 로그인 사용자 그룹이 따로 있습니다. "DB팀 규칙은 DB팀에게" 를 한 번에 설정하고 싶을 수 있습니다.
- **구현 방향:** 수신 그룹에 '사용자 그룹 구성원에게도 보내기' 옵션 (사용자에 이메일 칸 추가) 또는 규칙 묶음 → 기본 받는 곳 지정.
- **벤치마킹(2026-10-29) — 재설계:** 규칙마다 `notify` 목록이라 새 팀(DB팀·보안팀·EMR 협력사)을 더하려면 규칙을 하나씩 고쳐야 합니다. 사용자 그룹 연결보다 **라벨 경로 트리**가 단순하고 넓게 쓰입니다.
  - `alerts.yaml` 에 순서 있는 `routes:` — `{match: {group, tags, severity, host 패턴}, notify, continue, replace}`. 규칙의 `notify` 는 기본 받는 곳으로 계속 동작합니다(호환).
  - 받는 곳은 발생 때 풀어서 payload 에 경로 이름까지 남깁니다(증적). 규칙 편집 미리보기에 '이 규칙 → 운영팀, 보안팀 (경로: 보안 태그)'.
  - 사용자 그룹 구성원에게 메일 보내기(사용자 이메일 칸)는 경로의 한 대상 종류로 둡니다. 시간대별 받는 곳은 B-42.
  - 출처: COMPARISON.md §5.2 / Alertmanager route 트리, Grafana 알림 정책.
- **완료 기준:** 경로 매칭(continue·replace·기본) 시험, payload 경로 기록, 기존 규칙 동작이 바뀌지 않음(호환 시험), 화면에서 연결, 메일 수신 시험, 감사로그.

### B-29 검색 문장 v2
- **왜:** 검색 문장(ADR-033) v1 은 정확히 일치만 됩니다. 운영하며 `host:WEB-*`, `ip:10.0.0.0/24`, `사용자:kim` 같은 입력이 자주 보이면 넣습니다.
- **구현 방향:** 예약해 둔 `*`·`/` 를 열기 — `host` 등은 `LIKE`(색인 `text_pattern_ops` 필요, 벤치 필수), IP 대역은 `src_ip::inet <<= %s`(값이 IP 가 아니면 NULL 처리). 한글 키 별칭은 SYNC 의 `key_hints` 를 키로 승격. 빈 값 검색(`user:""` → `IS NULL`).
- **벤치마킹(2026-10-29) — P3 → P2:** 한국어 핵심어 대부분이 2글자('오류'·'실패'·'계정'·'부팅')인데 trigram 색인을 못 써 30일 검색이 28.8초입니다(PERFORMANCE.md §2.1). 운영자가 가장 자주 칠 검색이 가장 느립니다.
  - 맨 단어 뒤 `*` = 어절 접두: `부팅*` → `to_tsvector('simple', message) @@ to_tsquery('simple', '부팅:*')` + 파티션별 GIN. PostgreSQL 내장이라 확장·이미지 교체가 없습니다(pg_bigm 자체 이미지는 기각, COMPARISON.md §6). 화면 매처와의 어절 경계 차이는 케이스 표로 고정합니다.
  - 필드 접두·접미·포함(`key:값*`, 대소문자 무시), IP 대역, 목록 참조 `user:@목록`·`ip:@목록`(B-53, 실시간 매처에는 서버 전용 표시).
  - Sigma 변환(B-14)과 규칙 팩 2차(B-48)는 별도 YAML 언어 대신 이 문법을 대상으로 합니다.
  - 출처: COMPARISON.md §5.4 / VictoriaLogs 단어·접두 검색, PostgreSQL 'simple' 텍스트 검색, Sigma modifiers.
- **완료 기준:** 케이스 표·교차 퍼징에 새 문법 추가, 기존 문장의 뜻이 바뀌지 않음(케이스 표 그대로 통과), 500만 건 벤치(GIN 쓰기 비용 포함), 수집 처리량 저하 기록.

- **왜 (남은 것):** 개인정보가 보이는데 아직 기록되지 않는 조회가 있습니다.

  - 시계열을 사용자·IP 로 나눠 보는 조회(`/api/stats/timeseries?group=user|ip`) — 상위 값과 같은 정보인데 `events.stats` 대상이 아닙니다.
  - 점검 보고서 열람·인쇄, 감사로그 목록 조회(`audit.list` — 직원 계정·IP 목록).
  - 인쇄본에 출력자·시각 표시가 없습니다(출력·복사 안전조치 — 조항은 확인 필요, COMPARISON.md §7).
- **구현 방향:** 위 조회를 `events.stats` 처럼 같은 사람·같은 조건은 묶어서 기록하고, 개인정보가 보이는 것은 `required=True`(실패하면 거부). 인쇄 HTML 에 출력자·시각·IP 표시(escape). 점검 보고서에 '사유가 짧은 내려받기' 절(옛 payload 도 그림). 앞으로 생길 이벤트 CSV(B-62)·증적 묶음(B-73)·HWPX(B-83)도 같은 사유 방식.
- **완료 기준:** 각 조회의 기록·묶음·fail-closed 시험, 인쇄 표시 확인, ISMS.md 2.9.4(자체 로그) 갱신.

### B-41 알림 묶음 전송
- **왜:** 대상 키마다 알림 한 행·전송 한 통입니다. 윈도 업데이트 재부팅 물결로 서비스 오류가 300대에서 나면 메일이 300통 가고, 두레이는 주소별 1.1초 간격이라 5분 넘게 걸리며 진짜 신호가 묻힙니다.
- **구현 방향:** B-34 의 디스패처 위에서 (대상, 규칙)으로 묶습니다. 첫 전송은 `group_wait`(기본 30초, critical 은 0초) 뒤 한 통('[오류] 서비스 비정상 종료 · 37대 (PC-001 … 외 34대)' + 목록 링크), 이후 `group_interval`(5분) 안은 '추가 n대' 한 통. `notifications` 표가 묶음 전송 기록, `alert_deliveries` 는 알림별 증적으로 유지(ADR-029). 메신저 빌더에 목록형(항목 상한·'외 n건').
- **완료 기준:** 300건 폭주 시나리오에서 전송 n통 이하·평가 주기 지연 없음, 4개 메신저·메일 묶음 스냅샷, 알림별 증적 유지, PROJECT.md §6.2·6.3.

### B-42 무음 v2 — 반복 점검 창·공휴일·라벨 매처·시간대별 받는 곳
- **왜:** 무음은 한 번짜리(끝이 지금부터 30일 안)이고 규칙·대상만 맞춥니다. 매주·매월 정기 점검을 매번 다시 만들어야 하고, ip·user 로 묶는 규칙(무차별 대입·SQL 로그인 실패·계정 잠금)은 'DB-01 점검' 무음에 걸리지 않습니다. 근무시간과 야간에 받는 곳을 바꿀 수 없습니다.
- **구현 방향:**
  - 반복 시간 창 `time_windows`: Alertmanager `time_interval` 과 같은 필드를 씁니다. 공휴일 제외는 연 1회 반입하는 특일 자료로 하고, 검토 기한을 필수로 둡니다. `in_window` 는 케이스 표로 시험합니다.

  - 받는 곳마다 active·mute 창을 둡니다(예: 근무시간에는 두레이, 야간에는 당직 SMS·Oracle).
  - ADR-029 를 개정합니다.
- **완료 기준:** `in_window` 케이스 표(말일, 끝 제외, 공휴일), ip 규칙에 host 매처 무음, 범위 사용자 제한, 반복 창 전송 건너뜀·종료 후 동작, 화면 확인.

### B-44 알림 대기열 묶어 보기·종료 분류
- **왜:** 알림 이력은 발생마다 한 행이라 장애 때 같은 규칙이 수십 PC 에서 터지면 다른 심각 알림이 묻힙니다. 닫을 때 정탐·오탐을 남기지 않아 어떤 규칙을 고치거나 끌지 데이터로 정할 수 없습니다.
- **구현 방향:**

- **완료 기준:** 범위 적용(LIMIT 전)과 묶음 처리 감사로그 시험, 분류 없으면 422, 오탐률 계산 시험, 넓은·좁은 화면, ADR-029 보완, ISMS.md 2.11.4.

- **왜:** 기본 규칙에서 Linux 는 SSH 무차별 대입 하나뿐입니다. 병원 EMR DB 는 Linux/Unix 의 Oracle 이 흔하고, DBA·업체가 도구로 환자 표를 직접 조회하는 것이 DB 접근(ISMS-P 2.6.4) 접속기록의 사각지대입니다. 로드맵 초안에 Linux·DB 항목이 없었습니다.

### B-51 기본 규칙 팩과 현장 수정 분리
- **왜:** 기본 규칙과 현장 규칙이 한 `config/alerts.yaml` 에 있어, 업그레이드 때 `install.sh` 가 `alerts.yaml.new` 만 두고 사람이 합칩니다. 규칙 팩 개선(B-48)이 현장에 전달되지 않는 '탐지 노후화'가 생깁니다. 규칙 블록 편집은 블록 안 주석을 잃습니다.
- **구현 방향:** `config/rules.d/00-builtin.yaml`(이미지에, 읽기 전용, pack_version), `alerts.yaml` 은 현장 규칙 + `overrides:`(sid 별 enabled·threshold·window·cooldown·severity·notify 만 — match 는 예외 B-46 으로만 바꿔 탐지 의도 보존). 직전 기본 팩을 보관해 3-way 비교 화면(현장이 덮은 키가 바뀌면 충돌 표시), 승인 감사로그.
- **완료 기준:** 병합·허용 키 시험, 3-way 충돌 표시, 업그레이드 시나리오(AIRGAP.md), 화면 규칙 편집(`ruleedit.py`)과 호환.
- **출처:** COMPARISON.md §5.1 / Wazuh `ruleset/`·`local_rules.xml`+overwrite, Elastic 사전 규칙 3-way 비교, Security Onion Rule Mismatch.

### B-52 규칙 시험기·관찰 모드
- **왜:** 규칙 미리보기는 최근 24시간 건수만 보여 줍니다. 특정 이벤트가 왜 안 걸렸는지(경로 틀림, 제외 조건, 값 형식) 알 방법이 없고, 새 규칙을 켜면 바로 메일이 나갑니다.
- **구현 방향:** `filters.explain(event)` — 조건 항목별 기대·실제·참거짓(케이스 표로 `matches` 와 같은 뜻 보장). 이벤트 상세 '규칙 시험', 편집 패널 '표본 붙여넣기'(원본 JSON → normalize → explain). 규칙 `mode: observe`(기록하고 전송은 '관찰'로 건너뜀 — 무음 경로 재사용), 한 번에 active 로 승격(감사로그). 새로 들어온 팩 규칙은 기본 observe.
- **완료 기준:** explain 케이스 표, 관찰 모드 전송 건너뜀·승격 감사로그, 화면 확인.
- **출처:** COMPARISON.md §5.1 / wazuh-logtest, Hayabusa proven/noisy, SigmaHQ 패키지 단계.

### B-53 목록·자산 등록부
- **왜:** PC·IP·계정이 원문으로만 보여 어느 부서·용도(EMR DB, PACS, DC)·담당자인지 모릅니다. 퇴직자·서비스 계정·유지보수 업체 IP 같은 목록을 규칙에 쓸 수 없습니다. 같은 '경고'라도 EMR DB 서버와 병동 PC 를 구분하지 못합니다.

- **완료 기준:** CIDR·CSV·Oracle 동기화 시험, 규칙·상향 시험, 범위 있는 사용자가 인사 목록을 못 봄, PROJECT.md §8·ISMS.md.

### B-54 계정 표기 통일 (user_key)
- **왜:** 같은 사람이 소스마다 다른 문자열로 저장될 수 있습니다 — Windows `TargetUserName` 은 `kim`, IIS·MSSQL 은 `HOSP\kim`, Kerberos 는 UPN(`kim@hosp.local`). `clean_user` 는 원문을 그대로 둡니다. 그래서 `user:` 검색, distinct(ADR-041), 처음 보는 값(B-47), 개체 페이지(B-67), 퇴직자·장기 미사용 대조(B-72)가 같은 사람을 여러 명으로 봅니다.
- **구현 방향:** 파생 열 `user_key`(소문자, 도메인 접두·UPN 접미 제거)를 마이그레이션으로 추가하고 raw·`username` 은 그대로 둡니다. `user:` 를 user_key 로 맞출지는 ADR-033 절차(케이스 표 → `querylang.py`·`querylang.js` → repository)로 정하고, 기존 SQL 스냅샷 변경은 의도적으로 합니다.
- **완료 기준:** 표기별 왕복 시험(실측 IIS·MSSQL 표본으로 표기 확인), 케이스 표, 색인 벤치, PROJECT.md §3.2.
- **출처:** COMPARISON.md §5.1 / 검토(누락 비평). 개념: Splunk ES identity, Sentinel Identity Correlation.

### B-56 수집 품질 지표·레코드 누락(EventRecordID)
- **왜:** 규칙이 조용히 데이터를 못 받는 두 번째 경로는 '들어오는데 해석이 깨진 것'입니다 — Windows 업데이트로 이벤트 버전이 바뀌어 템플릿 이름이 안 붙음, generic 으로 떨어진 레코드, IIS 추정 순서 거부, 수집기가 PRI 없는 syslog 줄을 버림(B-23). 또 Windows 채널이 덮어써져 생긴 누락도 모릅니다(catalog 는 EventRecordID 를 '누락 확인에 사용'이라 설명하지만 확인 코드가 없음).
- **구현 방향:**
  - 소스·PC 별 해석 실패율·템플릿 미적중·잘림·격리(B-40)·지연(`received_at − ts` 분위수)·미래·아주 오래된 ts 를 field_stats 처럼 같은 트랜잭션에서 세고 주간 보고서에 절을 둡니다.
  - EventRecordID: (PC, 채널)별 커서는 DB(`channel_cursor`)가 정본. 번호가 건너뛰면 **그 PC 의 다음 하트비트 이후 1시간 이상** 기다린 뒤 `ingest_gaps` 에 기록합니다(Fluent Bit 재시도 백오프·조각 순서 뒤바뀜 때문 — 10분은 거짓 누락). 번호가 줄면(로그 재생성)·1102/104 직후·XPath 로 거른 채널(B-59)은 제외. 착수는 B-28 GPO 배포에 맞춥니다.
- **완료 기준:** 재정렬·재시작·로그 재생성에서 거짓 누락 없음, 수집 처리량 측정, 보고서 절, ISMS.md 2.9.4.
- **출처:** COMPARISON.md §5.3 / Chainsaw analyse gaps, Hayabusa 이벤트 ID 지표, 검토(판정자·누락 비평).

### B-57 에이전트 상태 신호
- **왜:** 하트비트는 30초마다 설정 버전 하나뿐입니다. 채널 구독 실패·IIS 경로 없음 같은 오류는 PC 의 `fluent-bit.log` 에만 남고, 디스크 버퍼가 차서 지워진 조각은 증거 없이 사라집니다. 하트비트의 발생 시각(`date`)은 정규화기가 meta 에서 버려, 밀린 데이터와 PC 시계 오차를 모릅니다.
- **구현 방향 (싼 것부터):**
  1. 하트비트 발생 시각(`date`)을 버리지 않고, 서버가 PC 시계 오차·지연을 계산해 수집 PC 화면에 보입니다. 여러 PC 의 오차가 한쪽으로 쏠리면 서버 시계를 의심합니다(ISMS 2.9.6) — 서버 시계 점검은 이 항목이 맡습니다. 설정 해시·프로필·Fluent Bit 버전 같은 고정 값은 B-11 1단계입니다.
  2. 자기 로그 tail 로 '전송은 되는' 오류(채널·경로)만. 401·TLS 오류는 같은 출력이라 그동안 오지 않습니다 → B-40 거절 장부.
  3. (L) `fluentbit_metrics` + `prometheus_remote_write` — 규격 본문이 snappy 압축이라 해석기(순수 Python 또는 BSD 라이브러리), 새 수집 경로(`INGEST_PORT_PATHS`)와 공격 면을 함께 검토합니다.
- **완료 기준:** 시계 오차 계산 시험(정상·쏠림), 화면 확인, AIRGAP.md(재설치 필요 안내), ISMS.md 2.9.6.
- **출처:** COMPARISON.md §5.3 / Fluent Bit `fluentbit_metrics`, Graylog Sidecar 상태 메시지, OpAMP ComponentHealth, Zabbix `fuzzytime`.

### B-58 에이전트 신원·배포 무결성
- **왜:** 모든 에이전트가 공용 수집 키(`WLM_INGEST_API_KEYS`)를 쓰고, PC 이름은 레코드의 `agent_host` 가 스스로 주장합니다. 키를 가진 PC(단말의 로컬 관리자)는 'DC-01' 이름으로 하트비트를 보내 장애를 가리거나 다른 PC 이름으로 이벤트를 위조할 수 있고, 키를 바꾸려면 전 PC 를 재배포해야 합니다. GPO 가 공유 폴더의 `install.ps1` 을 SYSTEM 으로 실행하는데 스크립트 서명이 없습니다.
- **구현 방향:**
  - 묶음에는 등록 토큰(만료·폐기·허용 대역)만 넣고, 설치 때 PC 전용 키를 발급합니다. 서버는 키의 해시와 MachineGuid 만 기록합니다.
  - 수집 때 키로 PC 를 확인합니다. 레코드가 주장하는 이름과 다르면 원본은 그대로 두고 `raw._ingest.claimed_host` 를 덧붙입니다(`raw._ingest` 는 B-40 의 예약 이름).
  - 수집 PC 화면에 키 폐기 버튼(감사로그).
  - 설치 묶음 매니페스트 서명·되돌리기 방지·단계 배포.
  - 공용 키 PC 와 섞이는 전환 기간을 둡니다.
- **완료 기준:** 사칭 시나리오 시험, 폐기, 전환 기간 혼합 시험, AIRGAP.md·ISMS.md 2.6.x, ADR.
- **출처:** COMPARISON.md §5.3 / Elastic Fleet 등록 토큰, osquery `enroll_secret`→`node_key`, Wazuh client.keys, Fleet(fleetd) TUF.

### B-62 검색 '통계' 탭
- **왜:** top(필드 하나, 건수만)과 timeseries 뿐이라 점검의 전형적인 질문('계정별 로그온한 PC 수와 처음/마지막 시각', 'IP 별 실패 횟수와 시도한 계정 수')을 표로 만들 수 없습니다. 이벤트 CSV 도 없습니다.

### B-64 저장한 검색

### B-69 저장 운영 기본값과 벤치 현실화

### B-71 위·변조 증명
- **왜:** `audit_log`·`alert_notes`·`reports` 는 트리거로 수정을 막지만, DB 슈퍼유저는 트리거를 끄고 고칠 수 있고 그 흔적도 같은 DB 에만 남습니다. DB 에 있는 `events` 파티션에는 해시가 없습니다. '위·변조되지 않았음을 어떻게 증명하나'는 2.9.4 심사의 단골 질문입니다.
- **구현 방향:** `audit_log` 해시 체인(prev_hash·row_hash, INSERT 트리거에서 순서 직렬화, PostgreSQL 내장 `sha256()`), 닫힌 시간의 events 다이제스트(보관 파일을 만들 때 대조), 매일 DB 밖 앵커(점검 보고서 payload·Oracle 표·B-17 복제 위치), `python -m app.cli verify-chain`. ADR-042 의 fail-closed(기록 못 하면 거부)와 함께, 기록이 있다는 것뿐 아니라 고쳐지지 않았음을 보입니다.
- **완료 기준:** 변조 시나리오 탐지 시험, 감사 INSERT 처리량 벤치, ISMS.md 2.9.4.

### B-72 정기 점검 보고서 확장

### B-74 관리자 2단계 인증 (TOTP)
- **왜:** 이 서버는 병원 전체의 보안 로그와 감사 증적을 쥔 자산인데 OTP·MFA 가 없습니다. 사내 SSO(B-12)만으로는 MFA 가 생기지 않습니다. ISMS-P 가 현장 실증·모의침투를 도입한다는 보도와, 개정 고시가 안전한 인증수단 대상을 넓혔다는 조사가 있습니다(둘 다 확인 필요, COMPARISON.md §7).
- **구현 방향:** RFC 6238 TOTP(`hmac`·`hashlib` — 새 의존성 없음). 비밀값은 `app/secrets.py` 로 암호화, 복구 코드는 해시. 관리자와 `settings.manage`·`alerts.manage` 권한에 필수(설정), 감사로그 `auth.mfa.*`, 비상 계정 절차. B-30 과 함께 운영(병원) 첫 설치 전에(순서는 B-30).
- **완료 기준:** 시간 창·재사용 방지·복구 코드 시험, 로그인 잠금 정책과 연동, ISMS.md 2.5.x.

### B-20 다중 워커

### B-82 국산 보안 제품 파서 팩
- **왜:** 장비 syslog 는 `syslog` 분류에 원문만 남고, 백신 규칙은 Windows Defender 만 봅니다. 국산 백신(V3·알약)·NAC·방화벽·DLP 로그를 규칙에 쓸 수 없습니다.
- **구현 방향:** 제품별 정규화기 + 대시보드 + 규칙 묶음을 백신 → NAC → 방화벽·DLP 순으로. 실제 표본이 있을 때만 만듭니다.
- **완료 기준:** 제품별 실제 표본 정규화 시험, 규칙 pos/neg(B-45).
- **출처:** COMPARISON.md §5.6 / Logpresso Store 연동 앱, 이글루 SPiDER TM.

### B-83 점검 결과서 HWPX(한글) 내보내기
- **왜:** 병원·공공 결재 문서는 한글(HWPX)이 기본인 곳이 많은데, 보고서는 HTML 과 인쇄만 됩니다.
- **구현 방향:** OWPML(KS X 6101) 패키지(XML + ZIP, 표준 라이브러리)로 점검 결과서(B-72)·권한 검토를 내보냅니다. 같은 렌더 데이터를 쓰고 로그에서 온 값은 escape 합니다.
- **완료 기준:** 한글에서 열리는지 확인, 내려받기 감사로그(ADR-042 사유 방식).
- **출처:** COMPARISON.md §5.6 / Logpresso 보고서 hwpx, 한컴 OWPML.
